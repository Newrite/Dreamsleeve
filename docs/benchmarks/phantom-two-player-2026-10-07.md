## Изменения

- `PhantomAgent`: durable transfer ACK/control отправляются на runtime tick,
  а не только на tick репликации поз. Старое окно4×16КиБ при10Гц ограничивало
  загрузку примерно640КиБ/с ещё до учёта RTT.
- Default `WindowChunks=32` (512КиБ) покрывает примерно100мс RTT при5MiB/s.
  Это допустимый прежним wire контрактом размер, без изменения budget5MiB/s.
  Окно на transfer; модельный server budget общий для upload+download,
  дополнительный такой же per-player. Client upload/download budgets отдельные.
  При64 transfers окно payload может занимать до32MiB; это не оценка всего RSS.
- Серверная репликация сохраняет сетку периода. `LastTick=at` ранее добавлял
  задержку позднего вызова к каждому периоду; при тиках около16мс100мс
  превращались примерно в110мс. Пропущенные периоды не воспроизводятся пачкой.
- `Playback` использует общий Domain::Motion::SourceTime. Приход более быстрого
  пакета больше не меняет offset всей истории одним скачком. SourceTime
  обобщён по duration, чтобы Phantom сохранял большой микросекундный диапазон.
  История принадлежит Exchange/Playback; Game не держит второй сетевой clock.
- Сохраняемые skinned BSEffect surfaces получают новую нативную lighting
  property **на отделённом клоне до фильтрации**. Геометрия и skin остаются
  нативными. Общий Ghostify, NiStream и whitelist NIF те же. Shared source
  properties не мутируются; другие неподдержанные материалы явно отвергаются
  с RTTI/skin в сообщении. Это покрывает конкретный ранее запрещённый класс;
  материал `shades` без нового игрового лога не считаем доказанно проверенным.
- В диагностической DLL раз в5с логируются gaps/age/запас текущего pose buffer.
  После успешного Apply/Attach отдельно логируется показ поколения.

Новые factories/ABI находятся только в Hooks; статический SE/AE/VR аудит
описан в [PhantomRuntimeRu.md](../PhantomRuntimeRu.md). Изменений собственного
renderer, native vertex uploads или neutral schema нет.

## Сравнение через настоящий ENet сервер

Один publisher, один receiver,65с,10Гц, dense AOI, холодный cache, одна и та же
модель13288628 compressed bytes /27740619 raw bytes,327channels. Asset взят из
существующей записи movement. Полный SHA256 и результаты сохранены в
[JSON](phantom-two-player-2026-10-07.json). Сервер выполняет production actor,
storage и transport; генератор не вызывает native decoder/render. Это loopback
на одной Windows машине; WAN прогноз по этим временам не делается.

| Измерение | Прежняя сборка, окно4 | ACK+окно32 | Также сетка таймера |
|---|---:|---:|---:|
| Модель принята сервером, с от публикации |23.614|1.608|1.597|
| Модель проверена получателем, с от публикации |25.743|4.120|4.124|
| Поз/с на активную подписку |8.747|9.067|10.008|
| Arrival gap p95, мс |149.65|116.47|110.77|
| Arrival gap max, мс |338.83|296.31|112.05|
| Отказы/нарушения протокола |0|0|0|

Второе время — весь путь от публикации, не отдельное время download.
Первоначальный token credit даёт burst:1.6с не означает устойчивую загрузку
выше5MiB/s. Это по одному прогону; параллельно местами шли проверки/сборка,
поэтому CPU и малые различия этих трёх прогонов не интерпретируются.
Payload модели не уменьшен, полный размер поз не изменён; ускорение получено
устранением ожидания ACK и расширением окна. Пересылка редкого нового native
asset пока полная, NIF delta остаётся отдельной будущей оптимизацией.

Регрессионный тест воспроизвёл старый клиентский скачок: сохранённая позиция5
менялась на10 при получении пакета с уменьшившейся на50мс задержкой без
продвижения времени кадра. С новым mapping остаётся5. Это установленный дефект,
но исходные игровые логи не содержат arrival trace: он не объявляется
единственной причиной субъективно рваного изображения.

## Проверка512 игроков

30с,512 publishers/ENet hosts,8 workers, sparse-группы максимум25, максимум4
выбранных фантома на получателя,10Гц, actor values4Гц. Те же301 production
pose payloads movement, что в предыдущем отчёте. Модели/кеши подготовлены до
измеряемого потока; во время него model upload/download0. В warmup ушло
23199744байта upload: cache hit может завершиться после отправки первых
chunks.832 временных ответа transfer limit при одновременном старте512
публикаций отработаны повторами; все источники стали ready до load.
Сборок параллельно этому прогону не было.

| Доставка на активную подписку, Гц |8.242|9.325|
| Pose C2S / S2C, MiB/s |19.288 /62.762|19.289 /71.545|

Прогон завершился успешно, но это **не** обещание стабильных10Гц для512
игроков: receive gap p95 по workers252–317мс; aggregate phantom.rejected
во время load1742 (метрика объединяет причины admission, не равна числу
потерянных UDP пакетов). Небольшое различие CPU одного прогона не доказывает
ускорение вычислений. Трафик вырос вслед за реально доставленной частотой.
Результаты: [JSON](phantom-two-player-2026-10-07-512.json), полные локальные
логи — `build/native-nif/two-player-20261007/steady512`.

Pose-числа включают protobuf envelope, но исключают ENet/IP overhead.
Замеры ENet по **всем** lanes:641232686B C2S,3441869772B S2C за30.001с;
UDP datagrams1284034 /2842288. Оценка с28B IPv4+UDP на datagram:
21.526 /111.939MiB/s, без Ethernet/IP options. Это оценка по ENet counters,
не packet capture. Разницу с pose-потоком нельзя назвать overhead поз:
среди полученных application bytes есть938569914B control и119653626B
movement/actor lane. Этот смешанный benchmark сохранён сопоставимым;
оптимизация control/actor-values находится вне данного исправления.
