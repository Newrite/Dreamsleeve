# Разделение SessionRegistry: локальные измерения 27 сентября 2026

> Замер 27 сентября 2026 года на protocol v1: числа относятся к той версии кода, а не к текущему состоянию.

Новый путь лучше в измерении одного отправителя, но примерно на 12% медленнее старого пути при 16 и 32 отправителях в один общий канал. Разделение владельцев само по себе не устраняет последовательную работу одного канала и одного сетевого выхода. Эти результаты не подтверждают обещание общего ускорения; для следующей оптимизации нужен профиль времени и аллокаций исходящего пути.

## Воспроизведение и граница

- Baseline: `f4eef57f3f28b6a266e53af5fc042757de010bb2`, до разделения registry.
- Новый production-код: `6cf6c0dc5491aafc8be386ae79e18d73d210d0f6`; harness и документация ещё не были закоммичены при измерении.
- Windows 10.0.19045, .NET SDK 10.0.401, 16 доступных логических процессоров, Release. `DOTNET_TieredCompilation=0` только в измеряемых процессах.
- 3 отдельных процесса для каждой версии, 32768 операций на сценарий после 1024 прогревочных операций. Baseline выполнялся перед новой версией. Рандомизации порядка и статистических доверительных интервалов нет.
- [Необработанные результаты всех 33 сценариев](session-routing-2026-09-27.json), [harness и полная методика](../../tests/Dreamsleeve.Server.Benchmarks/README.md).

```powershell
./Scripts/benchmark_server.ps1 -Requests 32768 -Repetitions 3
```

Общая граница: отправка уже декодированной SendChat в существующую сессию → сериализация и обработка публикаций всех N получателей. Тестовый получатель разбирает исходящий ServerPacket для подсчёта и корреляции; этот parse входит в оба результата. Входной decode, поиск сессии и реальная сеть исключены. Новый runtime также опрашивает пустой транспорт; старый вариант не имеет соответствующего runtime. Один pending-запрос на отправителя, одинаковый текст, история 64. Каждое сообщение, включая авторское с request_id, публикуется ровно один раз каждому получателю.

В таблицах указаны **медианы трёх значений**, включая медианы отдельно рассчитанных процентилей каждого прохода; это не процентили объединённой выборки. Throughput заканчивается только после всех публикаций. При увеличении N растёт работа рассылки: соответственно 32768, 524288 и 1048576 исходящих пакетов за сценарий.

Admission заканчивается после awaited PostAsync и включает задержку возобновления вызывающего кода. Он не измеряет обработку сообщения внутри очереди. Предельная нагрузка и отказы admission здесь не исследуются: в harness увеличены конечные ёмкости очередей. В основном сценарии у нового варианта сохраняется последовательная сериализация всех публикаций через runtime; определить долю её стоимости относительно actor-переходов, Fanout и тестового parse по этим данным нельзя.

Allocated — все выделения за 32768 запросов, не удерживаемая память. При большом N они закономерно включают миллион сериализаций и разборов protobuf. Измерение private bytes до/после не является проверкой утечки или пика памяти.

Суммы mailbox покрывают разные известные границы: registry+выходной агент у baseline, runtime+тестовые reader agents у нового варианта. В обычном chat-сценарии reader agents простаивают. Внутренние очереди player/chat/presence не измерены, поэтому приведённые суммы не выражают весь backlog и не дают прямого сравнения одинаковых ресурсов. Выборка mailbox и ThreadPool идёт каждые 10 мс и может пропустить короткие пики; числа в таблице — медианы наблюдавшихся максимумов трёх проходов. [Настроенные ёмкости и точный смысл счётчиков](../../tests/Dreamsleeve.Server.Benchmarks/README.md#память-очереди-и-завершение) сохранены отдельно от этих измерений.

PlayerLeft измеряется один раз после рабочей части до наблюдения события оставшимися игроками, с опросом примерно раз в 1 мс; при N=1 наблюдателей нет. Остановка включает teardown всех владельцев. Это тестовый транспорт без сетевого drain, а первое завершение процесса может включать холодный JIT ещё не вызванных cleanup-методов: значения N=1 нельзя интерпретировать как зависимость времени остановки от числа игроков. Новый runtime ждёт подтверждённого cleanup владельцев; у baseline иной жизненный цикл.

## Дополнительные сценарии новой схемы

| Сценарий | Игроков | Операций/с | p50 / p95 / p99, мс | Allocated, MiB |
| --- | ---: | ---: | ---: | ---: |
| 1 отдельная комната | 4 | 618279 | 0.0049 / 0.0083 / 0.0122 | 171.2 |
| 4 отдельные комнаты | 4 | 620513 | 0.0048 / 0.0074 / 0.0118 | 173.6 |
| Player Update+Read | 1 | 268987 | 0.0033 / 0.0051 / 0.0091 | 108.2 |
| Player Update+Read | 16 | 1781034 | 0.0070 / 0.0085 / 0.0118 | 108.0 |
| Player Update+Read | 32 | 1854264 | 0.0144 / 0.0175 / 0.0215 | 108.0 |

В комнатах одинаковы общее число запросов, четыре отправителя и четыре получателя каждого сообщения. Публикации сериализуются отдельными тестовыми агентами получателей без runtime и PlayerSession. Сравнимы лишь строки «1 комната» и «4 комнаты» друг с другом: здесь видимого выигрыша throughput нет, и эти строки ничего не доказывают о сетевом выходе runtime. Их наблюдаемый пик суммы queues rooms+receivers составил 16 в обоих случаях.

Update+Read обращается к независимым PlayerSession, проверяет видимость изменения в следующем снимке и не создаёт сетевых пакетов. Дополнительный тестовый агент на каждого игрока переносит ReplyChannel; его стоимость включена. С ростом N до 16 увеличивается суммарный throughput этого изолированного сценария, далее рост почти прекращается; это не измерение обработки игровых пакетов. Медианы пиков суммы runtime+тестовых readers: 2/4/13; пиков ThreadPool: 2/4/22. Admission отдельно не замерялся, в JSON стоит null.

## Медленный получатель и границы

Численную производительность при медленном получателе этот benchmark не измеряет. Изоляцию и конечные границы проверяют детерминированные тесты [ChatRoomAgentTests](../../tests/Dreamsleeve.Server.Tests/ChatRoomAgentTests.fs) и [PresenceAgentTests](../../tests/Dreamsleeve.Server.Tests/PresenceAgentTests.fs): gate удерживает получателя, mailbox=1 заполнен, здоровые участники получают следующий результат до освобождения gate. Источник удаляет подписку и сообщает SlowConsumer. Настройки источника: mailbox=4, control reserve=2, max control deliveries=4, история чата=2. Переполнение управляющего пути отдельно проверяется при max control deliveries=1 и host mailbox=1. Тесты не зависят от скоростей ThreadPool или задержек ОС.

Настоящие ограничения исходящих ENet-пакетов проверены loopback-тестами [EnetTransportTests](../../tests/Dreamsleeve.Server.Tests/EnetTransportTests.fs): число и байты пакетов удерживаются до native callback освобождения, включая ACK, reset и уничтожение host. Это отдельная проверка транспортной границы, отсутствующей в throughput-harness.

Результат архитектурного изменения — разные владельцы состояния, локальная изоляция медленных подписчиков, контролируемая очистка и отсутствие общего прикладного registry на пути всех команд. Единственный ENet host остаётся последовательным владельцем транспорта; общий канал остаётся последовательным владельцем порядка сообщений. Измерения дают основание профилировать исходящий путь перед следующей оптимизацией, а не добавлять новые уровни или обещать линейный рост throughput.
