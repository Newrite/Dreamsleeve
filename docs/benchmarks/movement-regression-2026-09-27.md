# Расследование регрессии движения, 27 сентября 2026

Первоначальный вывод «регрессия сервера» смешал два эффекта: накладные расходы
принудительного MTU-разбиения и ограничения единственного UDP-сокета генератора,
обслуживавшего 500/1000 peers. Проверки с изменением одного фактора это разделили.

Исправлено: MTU-разбиение больше не навязано по умолчанию; стенд поддерживает
несколько независимых сокетов и явный выбор режима пачек. Добавлены логи границ
разрыва транспорта/завершения агента и метрики возраста таймаута ENet. Очереди,
сроки таймаутов, reliability/channel и частота публикации сервера не увеличивались.

## Гипотезы и проверки

1. Отключено только MTU-разбиение, остальные оптимизации оставлены. Dense/500
   на одном сокете с 256 KiB всё ещё завершался ошибкой. Значит, MTU не объясняет
   всю наблюдавшуюся проблему.
2. Диагностический повтор зарегистрировал сначала Transport.Disconnected при
   Ready; перед этим не было прикладного close из-за full mailbox или завершения
   PlayerSession. Максимальный возраст earliest timeout достиг 6183 мс,
   отсутствие входящего трафика по peer — 3414 мс. Это согласуется с ENet retry
   timeout (minimum 5000 мс), а не с ошибкой авторизации или падением агента.
   ENet reset стирает состояние до отдачи Disconnect: точную причину конкретной
   потерянной датаграммы эти метрики не доказывают. Системный UDP error counter
   не является счётчиком потерь нашего сокета.
3. Увеличен только клиентский socket buffer до 8 MiB при прежнем размере пачек.
   Dense/500 сошёлся, p95 снизился до 1304 мс, timeout age max — до 1503 мс.
   Затем при том же буфере включено MTU-разбиение: сходимость также успешна,
   но enqueue вырос с 70102 до 406802, сумма runtime tick — с 7728 до 8822 мс,
   p95 практически не изменился. Это подтверждённые дополнительные расходы.
4. Клиенты разнесены по 64 сокетам, каждый снова с 256 KiB. Сервер по-прежнему
   имеет один host/owner, генератор — один service loop. Оба режима пачек сошлись.
   MTU → крупные пачки: отправка 6,66 → 8,07 Гц, репликация 3,11 → 3,66 Гц,
   p95 1608 → 1253 мс, enqueue 416660 → 75071. Каждый режим измерен один раз,
   поэтому проценты не следует считать точной устойчивой характеристикой.

У одного реального клиента свой сокет и свой receive buffer. Один сокет на 500
виртуальных клиентов сохраняет тот же общий буфер и существенно иную нагрузку
на приём. Разрыв в таком тесте нельзя без дополнительных проверок приписывать
пределу числа клиентов сервера. Вместе с тем несколько сокетов в одном потоке
тоже не эквивалентны 500 независимым игровым процессам или WAN.

## Dense/500: контролируемые сравнения

Источник 10 Гц, сервер 100 мс, load 10 с (failed-случаи обрывались раньше).
Target 0 означает прежние крупные пачки; 1200 — MTU-aware splitting.

| Target | Сокеты × буфер | Сошлось | Отправка, Гц | Репликация, Гц/пара | Возраст p95, мс | Enqueue |
| ---: | --- | --- | ---: | ---: | ---: | ---: |
| 0 | 1 × 256 KiB | нет | 5.70 | 2.47 | 3673 | 52928 |
| 0 | 1 × 256 KiB | нет | 5.53 | 2.75 | 3565 | 61168 |
| 0 | 1 × 8192 KiB | да | 7.33 | 3.18 | 1304 | 70102 |
| 1200 | 1 × 8192 KiB | да | 7.05 | 3.05 | 1291 | 406802 |
| 1200 | 64 × 256 KiB | да | 6.66 | 3.11 | 1608 | 416660 |
| 0 | 64 × 256 KiB | да | 8.07 | 3.66 | 1253 | 75071 |

Первые три записи получены с временной однострочной заменой вычисления target
на MaxPacketBytes. Сохранённый конфиг тех экспериментов ещё содержал 1200;
`effectiveMovementTarget` в компактном JSON отмечает фактический режим.
Эта временная правка удалена. Для воспроизведения теперь есть штатное значение 0.
Два failed-случая завершились до полных 10 с; их счётчики не сопоставимы с полным
окном успешного теста. Диагностика добавлена со второго прогона и одинакова внутри
обеих пар A/B (8 MiB и 64 sockets).

## Проверка итоговой версии: 1000 клиентов

256 клиентских сокетов, 256 KiB на сокет, target=0, 10 секунд, источник 10 Гц,
сервер 100 мс. Конечная сходимость проверяет каждый source/observer и отсутствие
лишних/устаревших позиций. Фрагментация остаётся обязанностью ENet.

| Сценарий | Сошлось | Отправка, Гц | Репликация, Гц/пара | Возраст p95, мс | Drain, мс | CPU сервера, ядер | Private peak, MiB |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| spaces | да | 9.47 | 7.37 | 254 | 421 | 1.40 | 139.4 |
| boundaries | да | 6.75 | — | 1690 | 5415 | 1.82 | 303.7 |
| sparse | да | 9.84 | 9.78 | 130 | 265 | 0.68 | 110.0 |

Sparse сохраняет почти 10 Гц и низкую задержку. Dense/500 и boundaries/1000
остаются перегруженными: успешный drain не означает устойчивые 10 Гц. Настоящий
предел плотного fanout этими изменениями не устранён. Dense/1000 после исправления
в этом расследовании не повторялся, обещания исправить его производительность нет.
Результаты на нескольких сокетах не являются прямым сравнением скорости с прежней
односокетной матрицей — это контроль источника искажения стенда.

## Изменения и воспроизведение

- `Server.MovementPacketTargetBytes=0` — default и example: batching до строгого
  MaxPacketBytes. Положительное значение оставляет opt-in эксперимент с MTU.
- В генераторе peer slot адресуется парой (host index, incoming peer ID), чтобы
  одинаковые локальные слоты разных ENet hosts не смешивали игроков. Все host
  выделяются/освобождаются одним владельцем; каждый имеет отдельный socket buffer.
- `--client-hosts` и `--movement-packet-target` runner сохраняет в metadata/config.
  Default hosts=1 оставлен для воспроизводимости прежних результатов. Многосокетный
  режим должен задаваться явно, а суммарный socket budget учитываться в интерпретации.
- `transport.peer.timeout.age.max` и `transport.peer.receive.age.max` семплирует
  transport owner; ни один фоновый поток не обращается к ENet peer.
- Регрессионный тест проверяет, что default не превращает одну допустимую пачку
  в несколько пакетов ради MTU. Проверки opt-in, строгого размера и порядка сохранены.

```powershell
python -u Scripts/benchmark_enet.py --clients 500 --rates 10 --scenarios dense --seconds 10 --timeout 600 --profile movement --client-hosts 64 --movement-packet-target 0 --output build/benchmarks/control-large
python -u Scripts/benchmark_enet.py --clients 500 --rates 10 --scenarios dense --seconds 10 --timeout 600 --profile movement --client-hosts 64 --movement-packet-target 1200 --output build/benchmarks/control-mtu
python -u Scripts/benchmark_enet.py --clients 1000 --rates 10 --scenarios spaces boundaries sparse --seconds 10 --timeout 600 --profile movement --client-hosts 256 --movement-packet-target 0 --output build/benchmarks/control-1000
```

Release build без предупреждений; 278/278 managed tests и 19/19 native ENet smoke
сценариев прошли. Четыре финальных нагрузочных случая сошлись. Проверка выполнялась
на прежней машине/SDK, с production Server GC и прежним конечным movement-профилем
очередей. Конфиги и хэши бинарников сохранены; исходная база — `00b3fe0`, далее
явные локальные изменения, перечисленные в metadata каждого эксперимента.
