# Pacing и проверка измерительного стенда — 08.10.2026

Ветка `codex/phantom-native-nif`, protocol24, native asset2 / pose3.
Это изменение доставки полного asset; NiStream и игровые ABI не менялись.

## Что исправлено

Фиксированный credit 32 KiB заменён пополнением по прошедшему времени. При
интервалах обслуживания 10/16 мс он действительно ограничивал передачу ниже
настроенных 5 MiB/s. Остаток части переносится, накопление ограничено negotiated
flight. Серверный общий credit пополняется один раз на timestamp и совместно
расходуется upload/download; peer имеет дополнительный бюджет. По умолчанию
оба серверных бюджета равны 5 MiB/s: это не обещание 5 MiB/s каждому из многих
одновременных peers при общем серверном лимите 5 MiB/s.

`ModelFlow` принадлежит исходящей передаче. До появления очереди окно быстро
растёт; затем estimated queued bytes из задержки ACK управляют плавным ростом
и уменьшением. Предел — negotiated window, повторные ACK не дают нового кредита
окна. Нет прежнего абсолютного порога задержки, подавлявшего даже минимальный
flight при обычном jitter. `Streaming.WaitMs` сокращает ожидание существующего
transport owner до следующей оплаченной части; заполненный flight ждёт ACK.
Новый сетевой поток клиента не добавлен. Серверный runtime использует Stopwatch
с сохранением согласованной временной шкалы deadlines.

## Почему пересмотрены старые результаты

Python 3.12 на этом Windows возвращал для `time.monotonic()` GetTickCount64 с
resolution 15,625 мс. При 5 MiB/s один такой шаг соответствовал 80 KiB, больше
искусственной очереди 64 KiB. Старый relay создавал ложные переполнения. Ещё
smoke-server имел собственный лимит 4 MiB/s на peer. Исторические результаты
сохранены с предупреждением в [старом отчёте](phantom-delivery-2026-10-08.md).

Python теперь только запускает процессы и собирает файлы. Пакеты обслуживает
отдельный test-only `Dreamsleeve.Network.Relay`: .NET Stopwatch, Socket.Select,
ArrayPool, FIFO сериализация каждого направления. Заголовки IPv4+UDP (28 bytes)
включены в скорость канала, Ethernet framing не учитывается. Tail-drop и заданная
потеря отличаются от переполнения памяти самого стенда: последнее делает прогон
невалидным. Опоздание фактического dispatch измеряется отдельно, с histogram.
Это пользовательский socket relay, не эмулятор ядра/реального интернет-маршрута.
Детерминированные Expecto-тесты проверяют FIFO, drain, overhead и 5 MiB/s без
ложных bursts. Смена языка сама по себе не считается подтверждением точности.

## Реальная модель через сервер и native Streaming

Один asset: 13 287 784 compressed bytes (12,672 MiB). Настройки приложения на
обеих сторонах 5 MiB/s. RTT100 мс, queue64 KiB, отдельный link rate в каждом
направлении; `clean` означает отсутствие shaping. `1loss` — 1 MiB/s, jitter
±10 мс и потеря каждого 200-го UDP datagram. Upload и download последовательны.
Тест выполняет production codec/cache и ENet, но не engine NiStream Load/render.

| Прогон | Upload / download, s | Полный цикл, s | Чат, ms | Overflow datagrams |
|---|---:|---:|---:|---:|
| verified-clean | 3.413 / 2.982 | 6.665 | 116.8 | 0 |
| verified-5 | 3.488 / 3.086 | 6.848 | 117.3 | 0 |
| verified-5-repeat | 3.482 / 3.083 | 6.840 | 115.2 | 0 |
| verified-4 | 6.818 / 5.808 | 12.903 | 121.0 | 618 |
| verified-1loss | 30.668 / 34.126 | 65.096 | 151.7 | 947 |

[Машинные результаты](phantom-pacing-2026-10-08.json) содержат SHA256 исходников,
точность Stopwatch, wire bytes, jitter/loss и lateness. Все resourceDrops=0,
relayErrors пусты. На 5 MiB/s повтор дал практически тот же результат; это два
локальных запуска, не статистика разных сетей. Успешный тест 1 MiB/s подтверждает
сохранение соединения и целого asset, но потери reliable fragments остаются
дорогими. 5 MiB/s application bytes также не равны 5 MiB/s IPv4 bytes.

Независимая калибровка paced UDP source + echo: 7489/7489 пакетов,
**4,990 MiB/s** при заданных 5 MiB/s, без потерь и дубликатов. Максимальный
service gap 3,509 мс; результат проверяется с допуском скорости ±2%. Матрица
снята до добавления финальных критериев признания результата невалидным;
пересылка не менялась, binary SHA каждого запуска сохранён.

## Следующая отдельная оптимизация: дельты

Offline native Zstd prefix + LDM на одной реальной паре дал 190568 bytes вместо
13194472 и точное восстановление raw asset; подготовка около 36 мс вне game thread.
Это не внедрённый wire-контракт. Сервер сможет восстанавливать полный asset в
ограниченном worker без интерпретации геометрии, но ещё нужны pinned base,
проверка target hash, идентичность recompression C++/managed, cancellation и
full fallback. В текущем production по-прежнему передаётся полный native asset.
