# Репликация движения v5 через ENet, 27 сентября 2026

Пространственный индекс и пакетная доставка существенно снизили CPU и повысили
частоту репликации при ограниченной видимости. Из 12 случаев 11 сошлись по
конечному состоянию, однако `dense/500` и `boundaries/1000` сильно деградировали.
`dense/1000` завершился неожиданным отключением клиента. Устойчивые 10 Гц для
1000 игроков этими измерениями не подтверждены.

## Условия и воспроизведение

Измерен коммит `bdb3c38`, чистое рабочее дерево. AMD Ryzen 7 5800X3D,
16 логических процессоров, Windows, .NET SDK 10.0.401, Release, Server GC.
Сервер и генератор работают отдельными процессами на одной машине; генератор
имеет один ENet host/socket/service loop. Без закрепления ядер, WAN и искусственных
потерь. Один прогон каждого случая, 10 секунд нагрузки; это не длительный soak test.

```powershell
dotnet build tests/Dreamsleeve.Server.NetworkBenchmarks -c Release --no-restore
python Scripts/benchmark_enet.py --clients 100 500 1000 --rates 10 --scenarios dense spaces sparse boundaries --seconds 10 --timeout 600 --profile movement --output build/benchmarks/movement-v5
```

Сборка прошла без предупреждений и ошибок. Runner завершился с кодом 1 из-за
`dense/1000`. C++-микробенчмарк интерполяции и регрессионные тесты в этом прогоне
не повторялись; предыдущие результаты остаются в отдельных отчётах.

Подготовка каждого случая: новый сервер и SQLite, регистрация/вход с параллелизмом
4, подключение по четыре клиента с ожиданием сходимости онлайна, BeginCharacter
по 16 с обслуживанием сети по 150 мс, ожидание N² начальных проекций и секунда покоя.
Подготовка отделена от нагрузки. Источник запрашивает 10 Гц, серверный интервал
репликации — 100 мс, радиус — 8192. Максимум восемь ожидающих ACK на игрока:
при перегрузке генератор приостанавливает отправку и считает пропуски из-за лимита.
После нагрузки проверяется последняя позиция каждой пары либо её отсутствие за AOI.

- `dense`: все видят всех в одном пространстве.
- `spaces`: десять пространств с равномерным распределением.
- `sparse`: группы по 25, расстояние между группами 20000.
- `boundaries`: смена пространства и пересечение радиуса каждые две секунды.

Профиль `movement` имеет увеличенные конечные очереди и не является production
конфигом: runtime mailbox 65536, presence mailbox 8192, player mailbox/output
max(256,2*N+128), ENet 4096 пакетов/16 MiB на peer и 262144 пакета/256 MiB глобально.
Полные конфиги, хэши и метаданные сохранены в [JSON](movement-v5-2026-09-27.json).
Runtime и транспортные настройки совпадают с предыдущей матрицей, кроме UDP-порта.
Различие лимита генератора в старых сериях описано в
[исходном отчёте](movement-2026-09-27.md); выбранные серии не имели ошибок admission.

## Результаты

PASS означает сходимость конечного состояния. DEGRADED выделяет успешные случаи
с фактической отправкой ниже 9,5 Гц либо возрастом p95 выше 500 мс — это порог
обозначения в отчёте, не утверждённый SLO. FAIL означает ошибку прогона.

Возраст — время от timestamp источника до обработки получателем, включая очереди,
объединение замеров и обслуживание ENet. Репликация — число полученных замеров,
делённое на длительность нагрузки и число видимых пар, включая самого игрока:
N² для dense, N²/10 для spaces, N*25 для sparse. Для boundaries состав меняется,
поэтому постоянный знаменатель не используется. Это средние по окну нагрузки.
CPU 1,0 соответствует одному логическому ядру; Private peak — private bytes процесса
в период нагрузки, с шагом выборки 100 мс, а не размер живой managed heap.

## Сбои и деградация

- **dense/500:** 10 секунд нагрузки, затем 6,26 секунды drain. Состояние сошлось,
  но источник снизился до 6,13 Гц, возраст p95 — 3,64 с, p99 — 5,26 с.
  Лимит ожидающих ACK остановил 18021 отправку; максимальное ожидание ACK — 13,71 с.
- **boundaries/1000:** 10 секунд нагрузки и 9,53 секунды drain. Источник — 6,13 Гц,
  возраст p95 — 3,75 с, p99 — 5,69 с, 35964 остановки отправки по окну ACK.
  Максимальное ожидание ACK — 14,12 с. Сходимость после drain не означает работу
  в реальном времени во время нагрузки.
- **dense/1000:** 10,01 секунды нагрузки, затем ошибка
  `Client 320 unexpectedly disconnected` и `Graceful client disconnect timed out`.
  Конечное состояние не сошлось, осталось 5175 ожидающих ответов. Источник — 2,11 Гц,
  возраст p95 — 8,47 с, 76281 остановка отправки по окну ACK. В сохранённой диагностике
  нет подтверждённой причины закрытия со стороны сервера; приписывать этот сбой
  конкретному лимиту ENet без дополнительных измерений нельзя.

## Что следует из измерений

Полностью плотная рассылка сохраняет квадратичное число получателей. Даже при
снизившемся CPU она накапливает задержку и тормозит источники через окно ACK.
Индекс полезен для ограниченной видимости, batching уменьшает стоимость рассылки,
но ни один из них не устраняет объём dense-трафика.

Объединение заменяет замеры только до передачи ENet; уже принятые надёжным
транспортом старые позиции остаются в его очередях. Это возможная составляющая
задержек, а не установленная единственная причина. Следующая диагностика — время
ожидания и размер исходящих очередей, размеры/фрагментация пакетов, повторы и ACK,
включая обслуживание генератором. Добавление потоков само по себе из этих данных
не следует как решение.

Гистограммы `presence.flush.duration` и `runtime.tick.duration` в JSON относятся
ко всему запуску, включая подготовку и drain, и не измеряют ожидание в mailbox.
Их нельзя сопоставлять с load-only CPU как один интервал. Процентили задержек —
верхние границы логарифмических корзин с точностью 1% + 0,01 мс; maximum точный.

Сырые результаты находятся в `build/benchmarks/movement-v5/` (игнорируются Git).
Компактный JSON сохраняет метрики, конфиги и релевантную диагностику, убирая
пустую таблицу chat recipients и подробные логи регистрации.
