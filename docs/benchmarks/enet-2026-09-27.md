# Реальный ENet: 100, 500 и 1000 клиентов, 27 сентября 2026

Все 18 прогонов прошли: два независимых запуска для каждой комбинации числа клиентов и нагрузки. При 1000 клиентах и 100 сообщениях чата в секунду каждый запуск доставил все 1 000 000 публикаций. Серверных отказов, неожиданных отключений, пропусков и дублей не обнаружено. Это подтверждает работоспособность выбранной нагрузки на loopback, но не устанавливает максимальную вместимость сервера.

## Условия и воспроизведение

- Измерен обычный Dreamsleeve.Server с настоящим UDP/ENet, отдельно от процесса генератора. Production-код не менялся; базовый коммит `ef5531f`.
- AMD Ryzen 7 5800X3D, 16 логических процессоров, Windows 10, .NET SDK 10.0.401, Release. TieredCompilation не переопределён. Оба процесса работают на одной машине без изоляции ядер.
- Вход окном до 8 сессий, затем точная проверка полного набора PlayerId у каждого клиента, 3 секунды без чата и 10 секунд измеряемой нагрузки. Каждый кейс начинает с нового процесса сервера и пустого profile store.
- Один общий канал, короткие уникальные сообщения (около 16–20 символов). Скорость 0/10/100 — суммарные отправки в секунду, не скорость каждого клиента. Отправители чередуются.
- Генератор использует один ENet host, один UDP socket и один цикл Service для N независимых peers; это не N игровых процессов. Ограничения: 128 незавершённых полных рассылок, один ожидающий собственный ответ на peer.
- Вход, исходящий protobuf encode, ENet, клиентский decode и проверка получателя входят в путь. RTT до авторской публикации и доставка последнему получателю измерены часами генератора, поэтому включают его планирование и обработку.

```powershell
dotnet build src/Dreamsleeve.Server -c Release
dotnet build tests/Dreamsleeve.Server.NetworkBenchmarks -c Release
python Scripts/benchmark_enet.py --repetitions 2
```

Использован отдельный профиль `scaled`: PeerLimit/MaxSessions=1000 во всех кейсах, runtime mailbox=8192, control reserve=3004, ENet ServiceTimeoutMs=0, EventBudget=512, общий исходящий лимит 65536 пакетов/64 MiB, OpenTimeout=30 s, ShutdownTimeout=10 s. Персональные очереди и остальные значения остались как в example config. Обычные настройки сервера в репозитории не изменены. Полный конфиг каждого запуска включён в JSON.

## Результаты

В ячейках — диапазоны двух запусков. Процентили рассчитаны внутри каждого запуска, не по объединённой выборке. CPU выражен в эквивалентах одного логического ядра (1.0 — одно ядро). RAM — наблюдаемый пик private bytes сервера только во время нагрузки; генератор в эти числа не включён.

Каждый кейс отправил заданное число сообщений (0, 100 или 1000) и дождался всех доставок. Всего проверено 3 520 000 публикаций чата.

Для 1000 клиентов и 100 отправок/с:

- Фактическая скорость отправки: 99.94–99.99 сообщений/с.
- Одновременно ожидали полной доставки максимум 2–3 сообщения при лимите 128; генератор не упирался в собственный предел admission, к окончанию нагрузки все публикации уже были получены.
- Полученный protobuf-трафик чата: около 8.04 MB/s. Это полезные protobuf-конверты, без presence/welcome, UDP/IP/ENet заголовков, ACK и повторных передач.
- Пик working set сервера во время нагрузки: 108.8–108.9 MiB. Это другая метрика памяти, не сумма с private bytes.
- CPU генератора: 0.389–0.574 ядра. Его работа и общий socket могут влиять на задержку и достижимую скорость.
- Вход и сходимость присутствия для всех 1000 клиентов: 3.00–4.01 с. Это постепенный вход, не одновременный connect storm.

## Что эти числа позволяют утверждать

На этой машине 1000 соединений и проверенная нагрузка чата помещаются в небольшой объём памяти, без видимого накопления backlog за десятисекундный интервал. Ограниченные очереди выдержали выбранный профиль без изменения production-кода. Само число агентов не стало препятствием.

Это ещё не результат для 1000 игровых клиентов: координат, интерполяции, больших снимков, постоянной БД и аутентификации в сценарии нет. Нельзя переносить эти цифры на рассылку игровых обновлений всем участникам, на WAN или на обычный default config с 4096 исходящими пакетами.

## Ограничения измерения и проверка

Процессы опрашивались каждые 100 мс через GetProcessTimes/GetProcessMemoryInfo. Пики между выборками могут быть выше; private bytes не равны объёму живых managed-объектов. GC/allocations не измерялись и принудительный GC не вызывался. Сохранённые профили, JIT и удержанные страницы heap не обязаны освобождаться после disconnect. Два коротких повтора не заменяют длительный soak и не дают доверительного интервала; порядок кейсов фиксирован. Прогрева чата не было, первая обработка и её JIT включены.

Первичный пилот и разведочная серия не включены в таблицу: затем уточнены проверки presence и добавлен подсчёт байтов. Для итоговых 18 запусков source и binaries зафиксированы хешами. Отдельно проверено, что deadline runner даёт FAIL и завершает свои процессы; malformed CLI отвергается до запуска. Server и harness собраны Release без предупреждений/ошибок; подсчёт доставки и агрегация метрик прошли независимое ревью.
