## Главная находка: частые поколения NIF

Один контейнер модели:27.58–27.69MB raw,13.18–13.28MB послеZstd3
(примерно12.6MiB). По всем записям317847927B сжатых моделей;
238337797B из них —18повторных поколений после первой модели каждого сценария.
Это объём сохранённых assets, **не замер переданных байтов**: очереди и отмена
устаревших передач могут отбросить промежуточные поколения.

В idle новые поколения приходят в0,3.810,5.001,7.004,10.506,11.673,12.814s.
Повторные модели дают75.86MiB за15s — около5.06MiB/s потенциальной публикации
даже без первой модели. Это уже сопоставимо с полным5MiB/s model budget.
Одна модель соответствует примерно140секундам поз одного источника при20Гц.
Её идеальное время передачи при свободных5MiB/s —2.53s, без ACK/очередей/загрузки
сцены. Частые новые поколения могут появляться быстрее завершения загрузки.

Поблочное сравнение привязано к kind/name/ordinal геометрии, отдельно сверены
packed shape buffers, связанный NiSkinPartition и dynamic positions. Это
офлайн сопоставление, не новый runtime способ идентификации каналов.

- Для всех переходов walk/idle/camera состав геометрии, packed buffers и
  NiSkinPartition совпадают. Меняются только dynamic positions пяти объектов:
  `00UBE_CotRFemaleEyesGold`, `00UBE_FemaleEyesHuman_outer`,
  `00UBE_FemaleEyesHuman_shadows`, `00UBE_FemaleHead`, `00UBE_LashiviousLashes21`.

  некоторые пересборки происходят при максимуме меньше0.006.
- В magic49→50 добавляется `BSTriShape:GlowMeshLightSpell:1`, в50→51 удаляется.
  Остальные изменения общей геометрии — те же пять лицевых dynamic buffers.
  На03:18:03.333 лог показывает временно отсутствующее вложение
  `omitted=1, hidden=2`; после нового поколения снова `omitted=0`.
- Все24compressed hashes различны. Content cache не объединит такие assets.
  NIF также сохраняет текущие transforms/ссылки, поэтому одинаковая постоянная
  внешность сама по себе не гарантирует одинаковый hash полного снимка.

Точный триггер пересборки не записан: pointer/partition identity, completed
revision и sparse dynamic signature объединены в текущем решении.
Сильная рабочая гипотеза — probe реагирует на мелкие текущие изменения FaceGen.
Он сравнивает hash координат после `round(f*16)`: сколь угодно малое движение
через границу квантования меняет hash. Ожидание стабильности750ms не задаёт
порог значимости деформации. Лог не доказывает конкретную причину каждой
пересборки; наличие dynamic-различий не позволяет назвать их все сменой
постоянной внешности или все простым морганием.

`partialSamples` не является числом потерянных лиц/брони: текущий Recorder
увеличивает его также при любом hidden channel. Поэтому301partial в walk/idle
с `omittedGeometry=0, hiddenGeometry=1` нельзя трактовать как301ошибку.
При этом summary хранит последнее omitted, а не максимум; краткую потерю
вложения в magic видно только в логе. Диагностику этих состояний стоит уточнить.

## Затраты и точность

Обычный capture без первого кадра каждого поколения: median0.056–0.060ms,
p950.252–0.278ms, максимум0.470ms. Первый кадр поколения:42.35–64.55ms.
Это суммарная подготовка/проверка/сериализация native модели с записью первого
снимка; из этих данных нельзя разнести clone, NiStreamSave, NIF validation,
audit и другие операции по отдельности или приписать задержку GPU.
Load/Apply и фактическая resident память в этих архивах отдельно не измерены.

Максимальная ошибка production pose относительно сохранённых float:
position0.0541266, normalized quaternion angle0.0034329°, scale0.00042969.
Видимость совпадает. Позы сохраняют свой world origin и source timestamp;
movement не используется как неявная база. Разреженность/интерполяционная
ошибка между20Гц кадрами этой проверкой не измеряется.

Байтовые плоскости — обратимая перестановка существующих квантованных bytes:
сначала одинаковые позиции байта всех каналов, отдельно bounds. Дополнительной
потери точности нет. Каждый кадр по-прежнему декодируется самостоятельно.
Это самый простой подтверждённый кандидат. Итоговый полный пакет должен
сохранить новый version/flags/layout contract; несколько служебных байтов
финального формата в эксперимент не добавлялись.

int16 сохраняет шаг1/16 и на всех1806кадрах точно восстанавливает int32 XYZ.
Но диапазон относительно origin ограничен[-2048,2047.9375]: production должен
иметь явный расширенный вариант для выходящих за диапазон объектов/модов,
а не clamp. Это дополнительный контракт и проверка. На этих данных такой
вариант вместе с перестановкой укладывается в3ENet-фрагмента при MTU1392;
простая перестановка в редких кадрах всё ещё требует4.

База словаря — первые pre-Zstd bytes **того же поколения**, поставляемые
отдельно reliable и идентифицируемые вместе с моделью. Каждый последующий кадр
сжимается независимо относительно этой базы; зависимости от предыдущего
unreliable пакета нет. Первые24кадра не участвовали в среднем3395.51B;
базу нужно дополнительно доставить (около6.2KB raw на поколение), поэтому
27% — ориентировочный выигрыш, не точное сравнение одинаковых множеств пакетов.
В разных сценариях итог3092–3552B; в спринте/бою выгода меньше. Короткие поколения
могут завысить эффект: нужна длинная выборка после исправления лишних пересборок.
Без перестановки/сужения сам словарь дал лишь4367.69B в среднем.

Офлайн p95 только вызова Zstd: текущий layout0.039–0.050ms,
плоскости0.035–0.042ms, int16+плоскости0.027–0.033ms. Это native compressor
через ctypes, без production C++ packing/validation, без игрового worker,
без отдельного CPU benchmark; оценкой полного encoder эти времена не являются.

Для первых6моделей повышениеZstd3→9 уменьшило размер примерно на4.1–4.3%,
а измеренное разовое сжатие выросло примерно128–132ms→282–288ms.
Zstd6 в этих запусках дал файл немного большеZstd3. Уровень сжатия модели
не устраняет основной расход от повторной публикации.

## Порядок следующих изменений

1. Разделить постоянную внешность, динамику лица и временные эффекты. Уточнить
   причины rebuild в диагностике; заменить hash-only сравнение dynamic probe
   измеримым порогом/гистерезисом относительно принятой модели, сохранив
   обнаружение настоящих морфов. Не просто убрать все dynamic meshes из аудита.
   Для временного GlowMesh определить политику включения/видимости отдельно:
   не пересылать всё тело на появление и исчезновение короткого эффекта.
2. Внедрить обратимую перестановку pose bytes в общий codec, поднять контракт
   синхронно; проверить production round-trip, packet loss, real ENet и игру.
   Это ожидаемые16% без изменения точности, NIF или native skinning.
3. Рассмотреть int16 с явным расширенным вариантом: ещё около2.3процентного
   пункта поверх перестановки и устойчивый переход4→3фрагмента на этой выборке.
4. Словарь поколения вводить только после сравнения сложности/выгоды на
   длинных поколениях. Правила готовности базы должен владеть существующий
   Exchange/transfer lifecycle, не новая параллельная машина состояний.
5. Для512игроков отдельно выбрать допустимую частоту по дистанции/приоритету,
   число получателей и общий egress budget. Локальные записи дают размеры;
   новый серверный benchmark нужен для фактических очередей/доставки/нагрузки.

Новые игровые записи для этих первых шагов не требуются. Production код и
установленная DLL в ходе анализа не менялись.
