# Первая волна оптимизации: повторные ENet-бенчмарки, 27 сентября 2026

Дрейф публикаций устранён: при ограниченной видимости репликация приблизилась к
10 Гц. Но плотная рассылка и частые смены видимости ухудшились. Матрица дала
9/12 успешных проверок конечного состояния, из них две с сильной деградацией;
три случая завершились ошибкой. Общая готовность к 1000 клиентам не подтверждена.

Позднее выполнено [расследование](movement-regression-2026-09-27.md): ограничения
общего сокета нагрузчика и цена MTU-разбиения рассмотрены отдельно. Ниже сохранены
исходные измерения; ранние failures не являются доказательством ошибки агента сервера.

## Методика

Коммит `00b3fe0`, чистое дерево на старте всех прогонов. Windows, Ryzen 7 5800X3D,
16 logical CPU, .NET SDK 10.0.401, Release, production Server GC. Сборка без
предупреждений. Сервер и генератор — отдельные процессы на одной машине,
один host/socket/service loop у генератора. Нет WAN, искусственных потерь,
профайлера EventPipe, принудительного GC или изменения production-кода.

Матрица: 100/500/1000 peers, 10 Гц от каждого источника, replication 100 мс,
10 секунд нагрузки, по одному случаю каждой комбинации. Дополнительно повторены
плотные 500 клиентов и 20 секунд групп по 25 на 1000 клиентах. Очереди увеличены
конечным benchmark-профилем `movement`, как в прежних прогонах; UDP-буферы 256 KiB.
Новый MovementPacketTargetBytes=1200 ограничивается negotiated peer payload.
Все полные конфиги, хэши сборок и источников сохранены с результатами.

```powershell
dotnet build tests/Dreamsleeve.Server.NetworkBenchmarks -c Release --no-restore
python -u Scripts/benchmark_enet.py --clients 100 500 1000 --rates 10 --scenarios dense spaces sparse boundaries --seconds 10 --timeout 600 --profile movement --output build/benchmarks/movement-opt-wave1
python -u Scripts/benchmark_enet.py --clients 500 --rates 10 --scenarios dense --seconds 10 --timeout 600 --profile movement --output build/benchmarks/movement-opt-wave1-dense-repeat
python -u Scripts/benchmark_enet.py --clients 1000 --rates 10 --scenarios sparse --seconds 20 --timeout 600 --profile movement --output build/benchmarks/movement-opt-wave1-sparse20
```

PASS означает конечную сходимость без ошибок; DEGRADED — та же успешная проверка,
но отправка ниже 9,5 Гц или p95 возраста позиции выше 500 мс. Это обозначение
отчёта, не утверждённый SLO. FAIL нельзя интерпретировать как успешную пропускную
способность. Возраст включает весь путь от timestamp источника до получателя.
CPU измерен в эквивалентах одного ядра; память — пиковые private bytes в load.
Репликация делится на число видимых пар: N², N²/10 или N×25; для меняющейся
видимости boundaries постоянный знаменатель не используется.

## Контрольные повторы и диагностика

Повтор dense/500 снова FAIL: отправка 4,88 Гц, репликация 2,71 Гц/пара,
p95 4264 мс, остановка нагрузки через 8,90 с. Ошибка та же: игрок покинул сессию
до cleanup. Провал воспроизведён, однако первопричина закрытия ещё требует
отдельной проверки. Увеличение лимитов не выполнялось.

Контроль sparse/1000 длительностью 20 секунд прошёл. Сравнение с прежним
непрофилированным 20-секундным `default` из детальной диагностики:

| Метрика | До | После |
| --- | ---: | ---: |
| Отправка, Гц/игрок | 9.91 | 9.90 |
| Репликация, Гц/пара | 8.35 | 9.88 |
| Возраст p95, мс | 135.38 | 134.03 |
| Средний период публикации, мс | 119.05 | 99.92 |
| CPU сервера, ядер | 0.71 | 0.76 |
| Private peak сервера, MiB | 136.60 | 109.23 |
| Аллокации, MiB/с | 170.98 | 133.03 |
| Суммарная GC pause, мс | 207.32 | 422.43 |
| Пакетов enqueue за load | 365744.00 | 594132.00 |
| Сумма transport.poll.duration, мс | 4697.61 | 5658.92 |
| Сумма runtime.tick.duration, мс | 7105.93 | 9931.61 |

- Публикация держится около 100 мс, за load выполнено 200 flush. Средняя работа
  Presence на flush — 7,38 мс; ранее 7,83 мс. Основное улучшение частоты связано
  с устранением дрейфа, а не кратным ускорением самой публикации.
- Аллокации снизились примерно на 22%, но GC pause выросла с 207 до 422 мс.
  Генераций 0/1/2: раньше 76/58/1, теперь 90/72/0. Это один повтор, не доказательство
  устойчивого ухудшения GC. Оснований добавлять принудительный GC отсюда нет.
- За load выполнено 594132 enqueue против 365744 (+62%). Все новые load-пакеты
  не превышали 1194 байт; метрики fragmentation/target-exceeded в load отсутствуют,
  то есть соответствующих событий не было. Фрагментация обычного движения устранена,
  но прикладных пакетов больше; суммарное время poll и runtime tick выросло.
- По сумме entries примерно 2,8% movement flush приходится на settlement, остальные
  на tick. В этом сценарии ACK-барьер не выглядит основным источником дробления.
- Пиковое pending ENet в sparse/1000 — около 0,96 MiB. В основной матрице dense/500
  достигал 78,9 MiB, dense/1000 — 160,0 MiB. Это удерживаемый payload, без служебных
  структур ENet, и не полная память процесса.
- GC/аллокации посчитаны как разность первых/последних load samples; длительность
  этого окна около 19,9 с. Границы фаз имеют погрешность до 100 мс. Histogram
  percentiles приблизительные; сумма длительностей не равна CPU time.

## Следующая проверка

Сначала провести изолированный A/B `b80915d` (до MTU-разбиения) и `00b3fe0`
(после него) с одинаковым измерительным стендом, повторениями dense/500,
spaces/1000 и sparse/1000. Это позволит отделить расходы дополнительных пакетов
от эффекта остальных оптимизаций. Пока нет основания объявлять MTU-разбиение
безусловным улучшением либо переходить к шардированию/настройке GC.

Первопричину досрочного закрытия сессии нужно связать с конкретным лимитом,
таймаутом или транспортным событием. Клиентский `PlayerLeft` сам её не раскрывает.
Production-код и размеры очередей в ходе измерений не менялись.

[Компактные результаты и метрики](movement-opt-wave1-2026-09-27.json).
Полные client/server logs, samples, конфиги и SQLite остались в трёх каталогах
`build/benchmarks/movement-opt-wave1*`. Основная матрица и dense-повтор завершились
с exit code 1 из-за зафиксированных неуспешных случаев; sparse20 — с exit code 0.
