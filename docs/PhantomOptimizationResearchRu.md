## Вывод и порядок работ

Нативный NIF + независимые снимки поз — подходящая основа для визуальных фантомов.
Менять renderer или воспроизводить чужой behavior graph не требуется.
Однако считать текущий путь полностью защищённым от рывков нельзя. До NIF-дельт
нужны изоляция срочных поз от тяжёлой работы, управление временем воспроизведения
и раздельное измерение дорогих игровых этапов. Дельта передачи не устраняет Clone,
NiStream Save, NiStream Load или создание нативной сцены.

| Приоритет | Изменение | Где и почему |
|---|---|---|
| P0 | Убрать блокировку поз моделью для одного получателя | Infrastructure/TransportOwner: сейчас общая bulk FIFO на peer |
| P0 | Развести тяжёлую обработку assets и срочные poses | Client.Core/Worker: сейчас один последовательный worker |
| P1 | Адаптивный буфер и монотонное время воспроизведения | Client.Core; общие чистые правила рядом с Domain.Motion, один владелец timeline |
| P1 | Раздельные timings и бюджет native capture/load/apply | Game/Hooks, без небезопасного переноса игровых объектов на worker |
| P1 | Проверить 10/20 Гц по значимости и реальную ошибку движения | Текущие 10 Гц заметно теряют детали боя даже без сети |
| P2 | Сократить копии, выделения, повторную работу Apply | Только после измерения, сохраняя границы владения |
| P2 | Сохранение недавно скрытой сцены при повороте камеры | Ограниченный grace/cache по памяти; не сохранять через смену контекста |
| P3 | Сжатие поз относительно гарантированно доступной базы; NIF-дельта | После latency/budget тестов, независимо от renderer |

## Похожие подходы и что из них применимо

**Unreal Live Link** разделяет статические данные субъекта, например скелет, и
последовательность кадров с трансформами. Приёмник буферизует кадры и может
интерполировать их с задержкой, затем применяет к штатной анимации движка.
Это близкий аналог нашего разделения asset/pose. Но Live Link не доказывает
безопасность NiStream, переносимость Skyrim-материалов или отсутствие внешних
зависимостей NIF. [Документация Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/live-link-in-unreal-engine).

**Unreal Pose Snapshot** умеет сохранять позу костей и применять её позднее.
Документация отдельно предупреждает о LOD: отсутствующие в снимке кости нельзя
восстановить волшебным образом. Для нас это аргумент фиксировать точную таблицу
каналов поколения, а не искать кости по неоднозначным именам при каждом Apply.
[Pose Snapshot](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-pose-snapshot-in-unreal-engine).

**Skyrim Together Reborn** полезен как сравнение другого решения. Его официальное
описание поддержки модифицированных анимаций обсуждает behavior variables,
зависимость hash от behavior-модов и порядка, одинаковые версии/modlists.
Для нашей цели визуальной реплики фактическая поза снижает зависимость от
совпадения behavior-систем. Это не утверждение о проверенной совместимости
Dreamsleeve со всеми модпаками. Точного опубликованного эквивалента нашего
переносимого NiStream-фантома в изученных источниках не найдено.
[Официальный README STR](https://github.com/tiltedphoques/TiltedEvolution/blob/dev/README-ANIMATION-MODS.md).

**Mirror Snapshot Interpolation** выделяет алгоритм времени из транспорта и
тестирует его симуляциями потерь, перестановки, пауз и разных частот. В исходнике
есть оценка jitter, регулируемая глубина буфера, небольшое ускорение/замедление
локальной шкалы, а также отдельная обработка большого рассогласования.
Применима идея и набор проверок, а не копирование Unity-компонента.
[Объяснение](https://mirror-networking.gitbook.io/docs/manual/components/network-transform/snapshot-interpolation),
[исходник алгоритма](https://github.com/MirrorNetworking/Mirror/blob/master/Assets/Mirror/Core/SnapshotInterpolation/SnapshotInterpolation.cs).

**Animation Budget Allocator Epic** управляет частотой и объёмом работы по
значимости персонажей и бюджету времени игрового потока. Для нас полезен принцип
измеряемого бюджета в миллисекундах; он не даёт API для безопасной остановки
NiStream посередине вызова. [Документация](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-budget-allocator-in-unreal-engine).

## Что сейчас делает интерполяция

В [Playback.ixx](../src/Dreamsleeve.Client.Core/Phantom/Playback.ixx): восемь снимков,
линейная интерполяция мировых позиций, shortest-path NLERP кватернионов, масштаб
между endpoints; видимость берётся слева до правого endpoint. После конца буфера
экстраполируются позиции всех каналов, вращения/масштабы остаются последними.
По умолчанию 10 Гц, delay100ms, extrapolation100ms, timeout1000ms.

В [Domain/Logic.ixx](../src/Dreamsleeve.Client.Core/Domain/Logic.ixx), `SourceTime`,
первый пакет задаёт привязку ко времени получения; последующие следуют source
timestamps. Исправление не двигает всю историю из-за одного более быстрого пакета.
Но адаптации к устойчивому изменению задержки/расхождению часов нет: привязка
сохраняется до сброса. Увеличить одно значение delay недостаточно для всех условий.

Рекомендуемая следующая реализация:

1. Отдельно оценивать доставку и продвигать монотонный playhead по source-time.
   Обновление оценки не должно мгновенно сдвигать уже показываемый кадр назад.
   Небольшая коррекция скорости с мёртвой зоной; явный rebuffer после длинной паузы.
2. Размер буфера задавать интервалом снимков и измеренным jitter/underrun, с min/max.
   Начальная проверяемая настройка для 10 Гц — 200ms; для 20 Гц — 100–150ms.
   Это кандидаты для испытаний, а не новые автоматически применённые defaults.
   RTT сам по себе не определяет нужный запас, а arrival содержит ещё и наши очереди.
3. Раздельно считать interpolation / underrun / extrapolation / hold / reset.
   Телепорт, новая generation/context и длинный gap — дискретные переходы.
   Не сглаживать через несовместимые endpoints.
4. Ограничивать предсказание корня, а не независимо продолжать скорости всех
   кистей, оружия и костей. Удержание артикуляции обычно безопаснее растяжения
   скелета; визуальную коррекцию после возврата данных проверять отдельно.
5. Hermite попробовать для траектории корня с осмысленными velocities и ограничением
   overshoot. Вычисленные соседние tangents — эксперимент, не точная скорость;
   нельзя требовать будущих кадров без учёта дополнительной задержки.
   Не добавлять velocity каждой кости автоматически.

Glenn Fiedler демонстрирует интерполяцию при10Гц, объясняет обмен задержки на
устойчивость к потере пакетов, Hermite для позиции и SLERP для вращения. Его350ms
относятся к конкретному сценарию потерь/jitter, а не являются универсальным
значением. Непредсказуемая динамика ограничивает пользу экстраполяции.
[Snapshot Interpolation](https://gafferongames.com/post/snapshot_interpolation/).

### Мировые трансформы и структура скелета

Линейно смешиваемые мировые позиции дочерних костей проходят по хордам, а не
по дугам вокруг родителя. Это математический риск текущего `Motion::Between`,
не диагноз каждого замеченного игрового артефакта. Например, при повороте жёсткого
отрезка на90° середина хорды сокращает длину до0,707 исходной.

Кандидат: world/root motion + интерполяция локальной артикуляции относительно
стабильных родителей; затем вычислить итоговые трансформы и применить к тому же
нативному скелету. Нельзя слепо считать parent из NIF живым parent оружия:
перепривязки, синтетические кости и flattened tree требуют отдельных инвариантов.
Сначала сравнить offline на соответствующих native bindings; это не новый renderer.

ACL рекомендует оценивать ошибку с учётом иерархии и расстояния от кости до
видимой поверхности. Для наших измерений нужны также точки кистей/ступней,
конец оружия и виртуальные точки на расстоянии от кости. Маленькая ошибка
компоненты quaternion сама по себе не гарантирует малую видимую ошибку.
[Measuring Accuracy](https://nfrechette.github.io/2016/11/01/anim_compression_accuracy/),
[Dominance based error estimation](https://nfrechette.github.io/2023/02/26/dominance_based_error_estimation/).

### Синтетическая проверка запаса буфера

Тот же скрипт отдельно моделирует только нынешнее правило `SourceTime` и наличие
endpoints в буфере:120секунд,60render frames/s, startup2s исключён, seed73021.
Сценарий: начальная задержка20ms, jitter±20ms, независимая потеря datagram2%,
условно3фрагмента на полный снимок. Вероятность потери снимка5,88%.
Это не запуск C++ Playback, не измерение ENet и не запись сети пользователя.

| Частота | Буфер | Кадры без правого endpoint |
|---|---:|---:|
|10Гц|100ms|8,04%|
|10Гц|200ms|0,35%|
|10Гц|300ms|0,014%|
|20Гц|100ms|0,44%|
|20Гц|200ms|0% в этом прогоне|

Дополнительный сценарий устойчиво меняет задержку20→180ms на30-й секунде.
При10Гц/100ms после перехода интерполяция практически прекращается: текущая
привязка не адаптируется, начинаются extrapolation/hold. Это воспроизводимый
контрпример к утверждению «fixed delay и один anchor достаточны»; не доказательство,
что именно такой переход был у двух игроков.

Уменьшение полного пакета улучшает и устойчивость. При независимых потерях p
и k фрагментах вероятность потери полного снимка `1-(1-p)^k`. Реальные burst losses
не независимы. У нас правильный sequenced-fragmented ENet режим уже есть, но он
не устраняет необходимость получить все фрагменты. Не заменять его flags=0.
[Fragmentation and Reassembly](https://gafferongames.com/post/packet_fragmentation_and_reassembly/).

## Снимки без статтеров: аудит текущего пути

### Что уже хорошо

- `Capture::Source` хранит bindings и ObjectRefHandle; не строит NIF для каждой позы.
- Cadence сохраняет сетку времени и пропускает пропущенные слоты без дубликатов.
- Dirty events только запрашивают audit; структура и деформация имеют coalescing.
  Probe ограничивает dynamic samples до32вершин на geometry; нет полного vertex stream.
- PoseDemand останавливает live sample/encode/send без выбранной аудитории.
- Zstd, hash, файловый кеш и detached decode находятся вне игрового потока.
- Старое пригодное поколение может показываться до готовности нового.

### Где остаётся дорогая работа

1. [PhantomCapture.ixx](../src/Dreamsleeve.Client/Game/PhantomCapture.ixx), `Open`,
   синхронно вызывает Prepare/Clone/Save и Parse, создаёт bindings/Source и первую
   позу. В27начальных кадрах записей агрегат capture-stage42,35–64,55ms; обычный
   capture-stage p95 по семи записям0,252–0,290ms. Эти архивы protocol22 сделаны
   до последних исправлений. Таймер начинается с переданного frame time и охватывает
   несколько операций: это НЕ чистое время Clone/Save и НЕ GPU timing.
   Но такой агрегат уже сопоставим с несколькими кадрами по16,67ms.
2. [PhantomScene.ixx](../src/Dreamsleeve.Client/Game/PhantomScene.ixx), `Advance`,
   за один вызов выполняет весь native Load и подготовку связей/материалов.
   `buildSteps=1` в Game ограничивает число загрузок за кадр, не их длительность.
   `remainingChannels=65536` ограничивает объём Apply, но не миллисекунды.
3. [Worker.ixx](../src/Dreamsleeve.Client.Core/Phantom/Worker.ixx), `Run`, сначала
   обрабатывает local asset, затем local pose; далее remote asset и только затем
   batch remote poses. Zstd3 модели, чтение/проверка/сохранение кеша способны
   задерживать позы всех фантомов на этом worker. Это установленный порядок кода;
   длительность такой блокировки в текущей сетевой игре ещё не измерена.
4. `Source::Sample` копирует `last` в выход и затем обратно; `Playback::Between`
   создаёт копию снимка каждый render frame; `Exchange::Read` под mutex копирует
   Remote и его deque/shared_ptr-историю, а не все bytes NIF. Эти выделения и
   reference counts — кандидаты профилирования, не доказанный главный bottleneck.
   `Scene::Apply` также каждый кадр проходит по nodes/bounds/skins/surfaces.

Правильная последовательность оптимизации:

- Сначала раздельные таймеры topology/probe, Clone, normalize, Save, asset Parse,
  Sample, worker wait, compression/hash, read/decode, Load, native preparation,
  interpolation, Apply, Attach и destruction. Отдельно wall time и очередь.
  p50/p95/p99/max и количество пропусков/выделений; не писать тяжёлый log каждый кадр.
- Срочные позы отделить от batch asset work одним ограниченным исполнителем для
  detached model jobs, сохранив Exchange владельцем epoch/generation. Приоритет
  внутри одного worker полезен, но не прервёт уже начатый длительный Zstd/IO.
- Для pose — повторно используемые contiguous buffers/неизменяемые snapshots,
  публикация владения без многократных копий. Pool нельзя переиспользовать, пока
  worker/render ещё читает его. Не создавать независимые lifecycle в каждом слое.
- Снимать всю позу в одном согласованном engine update point. Разносить разные
  кости одного снимка по игровым кадрам нельзя: получится несуществовавшая поза.
  Незавершённые engine jobs/сторонние writers требуют выяснения thread contract.
- Тяжёлую пересборку coalesce, отменять до начала устаревшую работу, сохранять
  прошлую сцену. Ввести временной бюджет допуска работ, но честно учитывать, что
  уже вызванный Clone/Load этим бюджетом не ограничить.
- Разделять подготовку между кадрами можно только после аудита независимых стадий
  и владения detached clone. NiPointer не разрешает фоновые вызовы движка.
  Без подтверждённого engine async API нельзя обещать нулевой hitch полной модели.

Fixed-rate sampling, render interpolation и catch-up — разные вещи. Сохраняем
один актуальный снимок после просадки вместо очереди одинаковых догоняющих кадров;
нужен запас CPU, чтобы работа не порождала дальнейшее отставание.
[Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/).

## Сервер: выявленные очереди и пределы проверки

### Блокировка поз моделью одного peer

[PhantomOptions.fs](../src/Dreamsleeve.Server.Core/PhantomOptions.fs):
`LanePolicy.bulk` включает **Models и Poses**.
[TransportOwner.fs](../src/Dreamsleeve.Server.Infrastructure/TransportOwner.fs):
`enqueueBulk` кладёт их в одну FIFO на peer; `takeCommand` берёт голову; если
Models получает native budget error, `finishBulk` оставляет голову на месте и
peer помечается blocked на текущий pass. Позы за ней ждать обязаны, несмотря
на независимый ENet lane. По достижении головы pose старше200ms отбрасывается.
Тест есть на доступность ДРУГОГО peer, но это не проверка pose того же peer.

Исправление должно разделить семантику reliability/fragmentation и приоритет
handoff. Нужны pose latest slots с ключом получатель/источник/view/generation либо
равноценная информация в transport contract; нельзя заменить все poses одного peer
одним последним пакетом — потеряются другие источники. FIFO reliable model chunks
сохраняется. Существующий ENet owner остаётся один; нужен fairness между traffic classes,
а не отдельный transport или безусловное голодание моделей под постоянным control.
Регрессия: удерживать model budget, обновлять несколько источников тому же peer,
проверять своевременные poses, отсутствие старого backlog, chat/control и cleanup.

порядка интервала позы. Runtime avgCPU~1,40ядра не отменяет длинных хвостов.

границе. Кандидат — распределять due sources по runtime ticks с fair cursor и
ограничениями bytes/operations/time. Не дублировать snapshots и не создавать второй
actor/spatial index. Нынешнее кеширование encoded packet на revision уже полезно.

Нужны повторяемые A/B с фазами constant subscriptions / AOI churn / camera churn /
cold model replacement, separately actor values0/4Гц. Измерять per-lane queue age,
source sample→worker→send→server→receive→render, missed deadlines и GC pauses.
Текущий receive-gap смешивает потерю пакетов и периоды без подписки; новую метрику
считать только внутри непрерывной пары source/view. ДляGC — EventPipe/ETW, allocation
rate, pause events; ни CPU average, ни память123,9MiB не доказывают отсутствиеGC hitch.
[Microsoft dotnet-counters](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-counters),
[.NET runtime metrics](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/built-in-metrics-runtime).

Идея накопления приоритета полезна для будущей значимости: давно не обслуженный
источник повышает шанс отправки, чтобы близкие не вытесняли остальных навсегда.
Для нас это изменение scheduler внутри текущего AOI, а не перенос чужой физической
симуляции. [Priority Accumulator](https://gafferongames.com/post/state_synchronization/).

## Компактность и что не стоит делать первым

Pose3 уже использует quantization, byte planes и Zstd1. Текущий quaternion — все
четыре int16, не smallest-three. Последний можно проверить как отдельный codec
experiment с world-space error; экономию считать после Zstd и полного protobuf.
Методы smallest-three и relative encoding описаны в
[Snapshot Compression](https://gafferongames.com/post/snapshot_compression/).

Предыдущие измерения тех же7архивов: payload planar~3875–3943B;
i16+planar~3785–3838B; i16+planar+фиксированная база поколения~3092–3552B.
Простой base dictionary без изменения представления иногда хуже нынешнего pose3.
Это офлайн кандидаты: диапазон i16, размер/доставка базы, overflow fallback,
переходы generation и итоговый полный пакет ещё требуют production-контракта.
Не делать снимок зависимым от предыдущего unreliable пакета.

ACL — преимущественно компрессия заранее известных animation clips. Анализ
будущих кадров, удаление ключей и сегменты нельзя бесплатно перенести в live:
они требуют lookahead/задержки. Для будущих death clips подход более уместен.
Более сложный кодек не гарантирует выигрыш на коротком потоке.
[Опыт с linear sample reduction](https://nfrechette.github.io/2019/07/23/pitfalls_linear_reduction_part1/).

NIF-дельту следует восстанавливать в detached bytes, проверять точную базу,
результат и тот же native asset contract, затем использовать обычный Load/Apply.
Сортировка произвольного NIF и патчинг живого дерева затрагивают ссылки, skin bindings,
allocators и lifetime — это отдельная, гораздо более рискованная задача.
Сначала измерить, какая доля hitch приходится на Save/Load: маленькая сеть не
обязательно означает дешёвую замену сцены.

Серверный сектор камеры и demand уже внедрены вv24. На возвращении в сектор сейчас
понадобится native Load, даже при file cache hit. Полезна короткая, ограниченная
памятью задержка освобождения только при camera culling; настоящий AOI departure,
context change, disconnect/privacy должны сохранять свои правила удаления.
Геометрия/позы не становятся дешевле лишь от повышения лимита видимых фантомов.
