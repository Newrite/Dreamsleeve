# Пространственная репликация v6

Три согласованных ENet-канала: Control (0, reliable), Chat (1, reliable),
Realtime (2, sequenced unreliable). Контракт движения введён в protocol v6 и с тех
пор не менялся; клиент и сервер обновляются вместе.

## Каналы

Control несёт сессию и приветствие с историей, `UpdatePlayer`, baseline/clear видимости,
остальные события присутствия, метки и модерацию; Chat — чат, объявления, удаление
сообщений и их ответы; Realtime — только позы (`ClientMovementPacket`/`ServerMovementPacket`).
Номера — часть протокола (`DeliveryLane`), надёжность задаёт флаг пакета, отказ идёт по
каналу запроса. ENet упорядочивает reliable внутри канала: потеря пакета чата не задерживает
Control. Позу не подтверждают — следующий период повторяет последнюю. Ранний `ChatPublished`
клиент держит до `SessionOpened` в ограниченном буфере, ранний realtime отбрасывает. ENet
`Service` сам выполняет работу протокола (отправку, ACK, повторы) и не ограничен по
длительности, поэтому у ENet свой поток («Транспорт»); большие UDP-буферы его не заменяют.

## Положение и границы

Клиент отправляет SetLocation по Control перед первым измерением нового
пространства, при телепорте и при очистке позиции. ContextRevision возрастает
в течение соединения, Sequence начинается с 1 в новом контексте. Отдельный
ClientMovementPacket содержит абсолютную позу, context и sequence, без
RequestId и подтверждения. Клиент повторяет последнюю позу по своему периоду.

Сессия принимает только новое измерение текущего контекста. Потерянная последняя
позиция остановившегося игрока восстанавливается следующим повтором. Сервер
не воспроизводит все промежуточные измерения.

Базовый период отправки клиента и репликации сервера — 50 мс (20 Гц).
Это ориентир для расчётов нагрузки; тики независимы и не синхронизированы.

Presence на каждом ReplicationIntervalMs берёт последнее состояние каждого
источника и отправляет каждому получателю все видимые актуальные позы.
Неизменившиеся samples сохраняют sequence и исходный timestamp. Потери и
пропуски периода допустимы; отсутствие записи в пакете не означает удаление.

Новый наблюдатель, вход в AOI, смена пространства или поколения создают новый
ViewRevision. Reliable PlayerVisibilityChanged несёт baseline либо clear.
Realtime PlayerMoved содержит PlayerId, ViewRevision, Sequence и MovementPose,
но не может сам установить пространство или видимость. Клиент принимает его
только для известного revision с более новым sequence. Sequence 0 допустим
в повторе baseline; повтор не добавляет точку интерполяции.

Между каналами нет общего FIFO: ранний realtime до baseline отбрасывается,
последующий период восстанавливает актуальную позу. Старый realtime после
clear/reentry не возвращает игрока. Смена revision сбрасывает интерполяцию.
PlayerUpdated без location — metadata; она сохраняет позу только при том же
CharacterGeneration. Смена поколения инвалидирует старое движение.

## Состояние игрока

`PlayerInfo`: профиль, имя персонажа или `character_name_withheld`, положение, actor values,
поколение, `PlayerDetails`, `view_revision`, `movement_sequence`. `SetDetails` заменяет
`PlayerDetails` целиком: раса (`NamedForm`: FormKey и подпись), необязательный уровень
(отсутствие не равно 0), занятие (`ActivityKind`; цель — только у занятий с целью, сложность
замка — у Lockpicking, ключ меню — ровно у Menu), место (подписи мира, локации и маркера,
ASCII-ключ вида маркера, интерьер; в расстояниях не участвует), `game_started_at_unix_ms` —
начало игры со слов клиента. Без персонажа `SetDetails` допустим только без расы и уровня. Actor values
заменяются картой целиком (пустая — очистка, Scalar 0 — присутствующее значение).
`PlayerSession` владеет `Player`: `BeginCharacter`/`LeaveGame` повышают поколение и очищают
положение, details и actor values, `RenameCharacter` их сохраняет. `PresenceAgent` сравнивает
`Latest`/`Published`: смена личности — `PlayerUpdated`, изменившиеся actor values и details —
`PlayerMetadataChanged`. Модель клиента, и автора тоже, меняется только по этим событиям; в БД
эти данные не пишутся.

## Область видимости

Один Latest-индекс разделён по полному WRLD/CELL FormKey и трёхмерной сетке.
Размер ячейки равен VisibilityDistance (при нуле — 1 unit). После отбора
кандидатов проверяется точное расстояние в double с включённой границей.
Движение наблюдателя пересчитывает и неподвижных соседей; self включён всегда.
Без своей позиции чужие координаты не видны. Метаданные и онлайн глобальны.

View-таблицы содержат только текущие видимые пары, поэтому память O(N + V),
где V — число таких пар. Плотный случай остаётся O(N²). Скрытые позы не передаются.

## Транспорт

Presence → PlayerSession → runtime передаёт готовую immutable-пачку получателя.
Runtime сразу кодирует её; второго словаря движения и ожидания transport tick
нет. Полный конверт ServerMovementPacket делится по границам записей до
согласованного ENet payload MTU. MovementPacketTargetBytes=0 использует MTU;
положительное значение может только уменьшить предел. Неделимая запись выше
предела — ошибка; fallback в reliable-фрагментацию отсутствует.

TransportOwner владеет ENet на отдельном потоке. Runtime передаёт готовые пакеты
по ограниченной очереди; worker чередует admission и protocol pump, не ожидая
конца прикладного тика. Получение events через CheckEvents отделено от работы
Service(0, null). Это не обещает ограниченную длительность самого ENet Service.

Realtime при насыщении может быть пропущен. Reliable admission/native failure
наблюдаемы и закрывают затронутое соединение, а не молча теряют команды.
Внутренние ENet packet budgets и handoff count/bytes ограничиваются отдельно.
