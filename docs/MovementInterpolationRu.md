# Измерения движения и интерполяция

Реализован клиентский слой без зависимости от Skyrim. Сетевой поток обновляет
ClientModel и публикует принятые измерения через существующий ClientExchange.
Игровой поток владеет MovementView: после Drain вызывает Apply, каждый кадр —
Sample(playerId, frameTime). Sample не меняет модель и не отправляет команды.
SKSE-хук и создание светлячков пока не реализованы.

## Время и порядок

PlayerLocation.sampled_at_us — монотонное время замера отправителя в микросекундах.
ClientExchange.Post заполняет нулевую метку до помещения LocalMovement в очередь;
адаптер может передать ненулевую метку более раннего замера. Все замеры одного
персонажа должны использовать одну шкалу. Время не является UTC и не используется
для авторизации, игровой валидации или сравнения разных игроков.

Сервер хранит метку вместе с последней позицией и переносит её в PlayerMoved,
PlayerInfo и начальный снимок. Промежуточные входящие позиции по-прежнему заменяются
до серверного тика. Новая метка в той же позиции тоже является измерением: это
сохраняет остановку перед возобновлением движения. Метаданные отдельных пакетов
не создают измерений.

Метка появилась в v4; ноль по-прежнему означает источник без метки, для которого
история строится по времени приёма. В действующем [контракте v6](SpatialReplicationRu.md)
движение идёт по Realtime (ENet channel 2, unreliable sequenced), независимо от
reliable Control и Chat. ContextRevision/Sequence упорядочивают входящие измерения
на сервере, ViewRevision/Sequence — измерения для конкретного наблюдателя.
Reliable baseline задаёт пространство и видимость; ранний realtime отбрасывается,
последующий период восстанавливает актуальную позу. Повтор принятого измерения
не добавляет точку истории. Смена revision сбрасывает интерполяцию.

На границе сетевого и игрового потоков дополнительно остаются generation/revision
ClientStateUpdate: это порядок локальной публикации, а не замена wire-поколений.

MovementView привязывает первый замер каждого игрока к локальному steady_clock.
Следующие времена вычисляются по разнице меток отправителя. Неравномерная доставка
не меняет расстояние по времени между точками. Первая сетевая задержка остаётся
частью этой привязки: синхронизации часов, оценки RTT и адаптивной задержки нет.
При скачке часов/длинном перерыве шкала привязывается заново. Если старый замер
из снимка или входа в видимость сдвинул следующую точку в будущее больше чем на delay,
история также начинается заново; она не растягивает движение по устаревшей базе.

## Обмен между потоками

ChangeBatch.movement и ClientStateDelta.movement содержат упорядоченные
MovementObservation: playerId, characterGeneration, viewRevision, receivedAt и optional location.
Их нельзя заменять списком затронутых playerId: тот хранит только итоговое состояние.
Несколько перемещений, потеря видимости и возврат между публикациями сохраняют порядок.
PlayerStore копирует для измерения только координаты и поколение, без actor values.

Лимит maxPendingMovementSamples ограничивает накопление в модели. При переполнении
история заменяется полным снимком. Переполнение StateUpdateQueue восстанавливается
тем же существующим путём. Снимок и playersReplaced сбрасывают историю, задают новую
базу по времени публикации. Задержка игрового Drain не становится временем приёма.
Обычные изменения метаданных историю не сбрасывают.

## Вычисление положения

Целевое время — frameTime минус delay. Между двумя точками используется линейная
интерполяция XYZ и кратчайшая дуга каждой Euler-компоненты rotation в радианах.
До первой точки показывается первая, после последней — последняя: экстраполяции нет.
При одинаковых временах последняя точка заменяет предыдущую без деления на ноль.

История разрывается при смене characterGeneration, полного FormKey пространства,
потере видимости/позиции, отключении, новом снимке, длинном перерыве, сбросе часов
или перемещении дальше teleportDistance. Порог расстояния — дополнительная эвристика. Игровой адаптер сообщает явный
телепорт через LocalLocation: новый ViewRevision сбрасывает историю даже при
небольшом перемещении внутри того же пространства.
При разрыве новая позиция показывается сразу, без пролёта через старое пространство.

## Настройки клиента

В Configuration.movement:

| Поле | По умолчанию | Назначение |
|---|---:|---|
| delay | 150 ms | Отставание отображения для накопления соседних точек |
| maxGap | 1000 ms | Разрыв истории по источнику, приёму или расхождению шкал |
| historyCapacity | 32 | Максимум точек на видимого игрока |
| teleportDistance | 2048 world units | Порог скачка позиции |

Configuration.maxPendingMovementSamples — 4096 наблюдений до публикации.
Задержка неотрицательна, maxGap больше delay и не больше часа (безопасное преобразование
в длительности), historyCapacity не меньше двух, teleportDistance положителен и конечен.
Runtime и MovementView.TryCreate возвращают ошибку для неверной конфигурации.
Внешний загрузчик C++ конфигурации по-прежнему не реализован.

Серверный ReplicationInterval и клиентский playerSampleIntervalMs — независимые
периоды передачи. Клиент повторяет последнюю позу, сервер повторяет все актуальные
видимые позы, включая неподвижных игроков; потеря последнего пакета исправляется
следующим периодом. ACK каждого измерения и ожидания pending для движения нет.
visibilityDistance/showFireflies остаются настройками будущего адаптера отображения;
выключение светлячков не меняет сетевой поток и историю.

## Проверка без Skyrim

```powershell
xmake run Dreamsleeve.Client.Dev --movement-demo
```

Детерминированная трасса: замеры каждые 100 ms, неодинаковая задержка доставки,
кадры каждые 16 ms, остановка, затем телепорт. Выводит frame_ms,rendered_x,history_size.
В режиме --connect доступны pose <playerId> и watch <playerId> <durationMs> (до 60000 ms).
Watch дрейнит состояние и вычисляет координаты каждые 16 ms. Вне watch консоль
по-прежнему дрейнит по команде; переполнение восстанавливается снимком.

Tests.Movement.cpp проверяет интервалы источника при джиттере, несколько точек за
одну публикацию, кратчайший поворот, остановку, сбросы, лимиты, устаревшие поколения
и восстановление снимком. Тесты кодеков проверяют сохранение меток C++/F#.
Scripts/smoke_chat.py проверяет метки и MovementView на реальном ENet-соединении.
Нагрузочный стенд движения добавлен: [методика ENet и native-прогонов](../tests/Dreamsleeve.Server.NetworkBenchmarks/README.md#movement-benchmark).
Он отдельно измеряет серверную рассылку и одного C++-потребителя с историей.

Историческая проверка первоначальной интерполяции (до v6): 200 native-тестов, 259 managed-тестов, 19 сценариев ENet smoke,
131 кадр детерминированного демо. Саморевью: метки не меняют авторизацию и критерий видимости,
нет новой очереди/потока/блокировки, наблюдения ограничены и не копируют actor values;
проверена устаревшая база при входе в видимость и отсутствие деления на ноль.
