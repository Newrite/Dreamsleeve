# Принятые решения и состояние проекта

Сверено 28 сентября 2026 года с решениями обсуждения «Языки для ENet» и
реализацией разделённых серверных владельцев, ENet runtime и сетевой отправки чата. Это описание проекта, а не поручение агенту.
Поздние явные решения пользователя и актуальные контракты кода заменяют ранние
примеры. Предложенный формат сообщения сам по себе ещё не утверждённый протокол.

## MVP и границы

Первый результат: глобальный чат, таблица онлайна со статами/именем персонажа/
локацией и светлячки других игроков. Гильдии, партии, друзья, PM, роли, модерация
и админка остаются последующими этапами. Сервер получает состояние Skyrim и
ретранслирует его; он не проверяет скорость, телепорты или игровые диапазоны HP.
История сообщений ограничена памятью; долговременного архива в БД сейчас нет.

Ближайшая разработка сосредоточена на `Client.Dev` и сервере без самой игры.
Реализован браузерный UI: TypeScript/React/Vite/Zustand, раздельные логика/разметка/CSS,
темы и заменяемые layouts, общий интерфейс для браузера и PrismaUI через адаптер.
[План UI](ClientUiPlanRu.md) фиксирует чат, fade, настройки, drag/resize и отдельный
канал системных объявлений только для чтения. Объявления закладываются в UI сразу,
их серверная доставка — отдельный близкий к MVP шаг; она ещё не реализована.
Вопрос имени персонажа в истории отложен до завершения UI-задачи.
Рабочий проект и инструкции: [Client.UI](../src/Dreamsleeve.Client.UI/README.ru.md).
C++ host, запись TOML через UI и PrismaUI-интеграция реализованы в SKSE DLL
([SkseClientRu.md](SkseClientRu.md)); браузерный стенд по-прежнему не заменяет проверку в Skyrim.

## Стек и границы модулей

- Сервер: F# / .NET 10+, yENet (выбран вместо zENet), Channels/Task-агенты.
- Клиент: C++23, модули, native ENet 1.3.18, xmake/MSVC, protobuf, spdlog, Glaze.
- `Client.Core` содержит DreamNet, домен, модель, AuthHttp и ClientApplication без зависимостей от Skyrim.
  ClientApplication владеет сетевым потоком и входом; TOML читает LoadClientSettings
  по пути, который передаёт конечный клиент. Client.Dev использует этот общий запуск.
  `Client` — SKSE DLL на CommonLibSSE-NG: преобразование игровых типов, PrismaUI-host,
  SKSE Menu Framework, светлячки. Host-модули без CommonLib (bridge, ui.toml, корреляция)
  тестируются в native-наборе.
- `DreamNetClient` — автомат одного транспортного соединения. `Poll` обрабатывает
  события в пределах бюджета; внешний владелец управляет циклом выполнения.
  ENet Connected не означает готовую прикладную сессию.
- Codec переводит байты в прикладные данные. `ClientRuntime` связывает транспорт,
  вход в сессию, отправку чата, модель и выдачу результатов через Exchange.
  Передача игровых показаний и PlayerDetails реализована в Protocol v6.
  Кодек создаётся один раз с проверенным config. C++ Encode пишет непосредственно
  в DreamNetPacket через TryAllocateWith; отправка использует передачу владения.
  Начальные данные представлены непосредственно в SessionOpened. Модель получает
  обычные операции; владелец публикует состояние после обработки события целиком.
  Отдельной транзакции и копии хранилищ для входа нет. C++ обработчик входа реализован;
  Client.Dev --connect использует его на отдельном потоке, синтетическое демо сохранено.
- Размер пакета задаётся конфигурацией и применяется и в codec, и в ENet host;
  также настраиваются буфер ожидающих данных, начальные списки и серверные лимиты строк.
  Сервер загружает TOML до старта владельца. Автоматическое согласование лимитов
  между сторонами и hot reload пока не реализованы; настройки фиксируются при старте. См. [контракт](../Protocol/README.ru.md).
- Коды отказа команд определяет общий RequestRejectionCode в protocol.proto. F# и C++
  используют сгенерированные типы. Сервер выдаёт определённые ненулевые коды;
  клиент сохраняет неизвестные ненулевые значения и пояснение для будущих расширений.
- Mutable-состояние серверных агентов доступно только владельцу. Агенты
  сериализуют обработчики, но не создают отдельный поток на каждого агента.

## Идентичность и имена

`PlayerId`, `ChatMessageId`, `ChatChannelId` — выдаваемые сервером `uint64`, не UUID.
Ноль не является корректным серверным ID. Верхняя граница `Int64.MaxValue` ранее
предлагалась для SQL, но не принята как ограничение домена: фабрики сейчас
принимают весь ненулевой `uint64`. SQLite выделяет положительные INTEGER до
`Int64.MaxValue`; преобразование проверяется на границе хранения, домен не сужается.

| Значение | Контракт |
|---|---|
| `Username` | Уникальное серверное имя; Trim, ASCII `A-Z a-z 0-9 _ .`, нижний регистр |
| `DisplayName` | Отображаемое имя; Trim + NFC, совпадения разрешены |
| `CharacterName` | Необязательное имя игрового персонажа; сохраняется как пришло из игры |

В чате показывается DisplayName; карточка по PlayerId позволяет показать Username.
Уникальность Username обеспечивает хранилище профилей, включая офлайн-профили;
фабрика профиля проверяет только значение. Резервирование профилей и реестр активных/открывающихся сессий реализованы.
`ChatMessage.Author` хранит профиль на момент отправки, а актуальный каталог
профилей может использоваться UI отдельно. ID и время сообщения назначает сервер.
Время: .NET `DateTimeOffset` ↔ Unix milliseconds `int64` ↔ C++ `sys_time<milliseconds>`.
Порядок сообщений задаёт ID, а не время.

## Пространство и показания

- `FormKey = PluginName + LocalFormId`: плагин происхождения и локальная часть ID,
  без индекса load order. Отображаемое имя и числовой хеш не заменяют полный ключ.
- `LocationId = FormKey` обозначает WRLD в экстерьере или CELL в интерьере.
  Отдельный PositionSpace не нужен. BGSLocation может дать подпись места,
  но не определяет пространство сравнения координат.
- `PlayerLocation` содержит весь `Location`, XYZ `float` в единицах Skyrim и
  три угла `float` в радианах. Отсутствующее положение не равно `(0, 0, 0)`.
  Расстояния вычисляются только внутри одинакового пространства, с промежуточным
  `double`; для отбора по радиусу достаточно квадрата расстояния.
- Actor Value имеет строковый ключ `namespace:name`, например `skyrim:health`
  или `avg:...`; подпись отделена от ключа. `Scalar(value)` и
  `Resource(current, maximum)` представлены F# DU / C++ `std::variant`.
  Отрицательные и превышающие максимум показания сохраняются, clamping нет.
- `PluginName` и `ActorValueKey` используют только ASCII case folding. Их не
  обрезают, не NFC-нормализуют и не проверяют как пути файлов Windows.
- Начало нового персонажа очищает позицию и показания даже при том же имени;
  простое переименование их сохраняет. Выход из игры сохраняет серверный профиль.

## Проверки и владение клиентским состоянием

Серверные фабрики проверяют входные строки, размеры и конечность чисел один раз.
Клиент хранит полученные от сервера значения без повторной UTF-8/текстовой
валидации и нормализации. Для игровых ключей есть явно вызываемые boundary helpers.
Клиентские пространственные функции предполагают конечные входные числа;
`IsWithinRadius` сейчас отклоняет отрицательный радиус. Проверку параметров следует
делать на границе их ввода, а не на каждом кадре.

В C++ остаются проверки операций: неизвестный игрок/канал, несовпадение identity,
конфликт сообщения, неоднозначная дельта, курсор истории, поколение сессии.
F# использует UMX и закрытые представления; C++ — алиасы и открытые структуры.

Все методы `ClientModel`, включая чтение, выполняет один последовательный владелец
в сетевом потоке. UI и игровой поток получают самостоятельные значения.
Для доставки снимков и дельт используется одна `StateUpdateQueue`.
Прежний `SnapshotMailbox` удалён: реальных потребителей у него не было,
а для текущего пути доставки отдельный механизм последних снимков не нужен.

## Подтверждение собственных действий сервером

Собственные подтверждаемые действия клиента проходят тот же путь применения,
что и события других игроков. Отправка команды сама по себе не меняет принятое
состояние: optimistic update для этих данных не делаем.

Для чата: клиент отправляет текст и канал, сервер принимает или отклоняет команду.
При успехе сервер рассылает сообщение в том числе автору; клиент добавляет его
через обычный `ChatMessagesReceived`, с серверными ID, временем и профилем автора.
Отдельного локального добавления своего сообщения и последующего слияния с echo
нет. При отказе показывается ServerRejection, сообщения в истории не появляется.

Этот принцип распространяется и на другие подтверждаемые сервером изменения.
SelfPlayerId нужен для идентификации себя в UI/сессии, а не для отдельного пути
применения собственных сообщений. Локальный сбор игровых показаний выполняется независимо, но реплицируемая
модель онлайна и присутствия получает их через серверные уведомления. Отправка чата и серверная рассылка подключены;
ClientModel применяет подтверждение автора через тот же путь, что и чужое сообщение.

## Изменения UI и чат

В модели уже есть `TakeChanges(ChangeBatch&)`: игроки и метаданные каналов
передаются как уникальные затронутые ID, содержимое чата — как упорядоченные
`ChatMessagesRemoved` / `ChatMessagesAdded`. Обычное сообщение не требует копии
всей истории. `FindChatState()` возвращает метаданные без сообщений.
Полный контракт — в [State/README](../src/Dreamsleeve.Client.Core/State/README.ru.md).

Добавлен следующий локальный шаг: `TakeStateUpdate(model, scratch)` вычитывает
накопитель и возвращает самостоятельный `ClientSnapshot` либо `ClientStateDelta`.
Игроки и метаданные каналов разрешаются на владельце; обычные сообщения остаются
content-deltas без копирования всей истории. `SnapshotPlayers()` копирует только
онлайн. Регистрация канала выставляет `resetChats`, преобразуемый в `resetContent`
для получателя: remove → register одного ID очищает прежнюю историю. Готовые
пакеты передаются между потоками через `ClientExchange`, использующий внутреннюю `StateUpdateQueue`; сам вызов
TakeStateUpdate такой очередью или подпиской не является.

`StateUpdateQueue` ограничивает число ожидающих пакетов и вычитывается пачкой.
Собственного mutex у неё нет: доступ сериализует единственный mutex ClientExchange.
Публичный ClientApplication вызывается только главным потоком приложения; статус
и команды управления также проходят через Exchange, без callbacks с сетевого потока.
Один владелец модели публикует данные, один потребитель последовательно применяет
пачки. Начало доставки требует снимка. Переполнение удаляет ожидающую цепочку
дельт и требует нового снимка; до него дельты не принимаются. Свежий снимок
заменяет все ожидающие пакеты. Ограничение относится к числу пакетов, не байтам.

Реестр подписок убран: один сетевой владелец и один игровой поток, который
вычитывает данные также для UI. Вместо Subscribe/Unsubscribe используется
`ClientExchange`: Post → TakeCommands и Publish → Drain. Обычные сообщения
чата идут Added/Removed без копии всей истории. Снимок появляется при первой
публикации, запросе восстановления, смене сессии или переполнении очереди состояния.

Игровой адаптер снимает значения из игровых объектов и передаёт самостоятельные
доменные данные. Кодеки, сборка пакетов и ENet принадлежат сетевому владельцу.
Команды помечены локальной generation; runtime должен отклонять устаревшие команды.
RequestSnapshot может обслуживаться для текущей модели независимо от старого курсора.
Соседние полные LocalMovement одного поколения заменяют друг друга до вычитки;
команды смены персонажа, выхода из игры и чата сохраняют порядок.

В обратной выдаче отказы отделены от заменяемого снимком состояния и сохраняют
исходную generation. Очередь команд ограничена и возвращает Full/Closed. Очередь
состояния ограничена числом пакетов; отказы и ожидаемые ответы учитываются в общем бюджете команд.
CloseInput запрещает новые команды, владелец обрабатывает принятые, публикует
результаты, вызывает Finish; вызывающая сторона завершает поток через join.

В Client.Dev основная консоль заменяет игровой/UI-поток. Реальное соединение
обслуживается сетевым потоком ClientApplication. Синтетическое state-demo выполняется
целиком на главном потоке: `send` не добавляет сообщение, `accept` имитирует
подтверждение сервера, `reject` — отказ. Демо проверяет также переполнение, снимок,
сброс сессии и остановку. В игровом адаптере Post/Drain не ожидают обработки команд.

Существующая revision модели растёт и при успешных no-op. Это не непрерывный номер
пакета UI. Прикладной codec чата реализован; сетевой runtime обслуживает вход, чат, телеметрию и отключение; JS-адаптер ещё отсутствует.

Локальный `MarkId` не содержит catch/rethrow. Предложенная граница аварийных
исключений — внешний runtime: остановить повреждённую сессию и сообщить ошибку,
а не продолжать применять изменения к частично обновлённой модели. Обработка ошибок выделения памяти
на границе владельца пока не реализована; runtime не обещает восстановления после них.

## Присутствие и интерполяция

Реализован MovementView, которым владеет игровой поток. ClientModel сохраняет
упорядоченные наблюдения отдельно от coalesced player invalidations; ClientExchange
доставляет их внутри ClientStateDelta. Время замера отправителя проходит через
PlayerLocation.sampled_at_us, время приёма фиксируется при применении к модели.
История ограничена и сбрасывается на границах персонажа/пространства/видимости,
при телепорте, перерыве, новом поколении и восстановлении снимком.

Интерполяция XYZ и rotation работает без экстраполяции. Есть конфигурация задержки,
ёмкости и порогов, детерминированное --movement-demo и pose/watch для реального ENet.
SKSE-адаптер вызывает Apply/Sample из хука `Main::Update`; светлячки берут позы из Sample.
[Контракт, ограничения и проверки](MovementInterpolationRu.md).

| Область | Состояние |
|---|---|
| DreamNet | Обёртки ресурсов, автомат соединения, ограниченный Poll, отправка/приём и тесты loopback |
| F# Domain / Agent | Реализованы и имеют регрессионные тесты |
| C++ Domain / State | Игроки, ограниченный ChatCache, модель, StateUpdate, очереди и ClientExchange для одного потребителя |
| Client.Dev | Общий ClientApplication, --config/--connect, консольный ввод пароля и отдельное синтетическое демо |
| Server | ENet runtime, HTTP auth, TOML-конфигурация, Serilog, PlayerSession, ChatRoomAgent, PresenceAgent и жизненный цикл |
| Protobuf / codec | Protocol/*.proto v6: вход, полные PlayerInfo/история, чат, онлайн, телеметрия и отказы; C++ encode/decode и F# decode/encode реализованы |
| UI / Skyrim | Будущие адаптеры; в Core игровых зависимостей нет |
| Persistence | SQLite accounts/profiles, Migrondi, SqlHydra; MemoryProfileStore только для изолированных тестов |

Первый прикладной контракт описан в [Protocol/README](../Protocol/README.ru.md).
Сессия привязана к ENet-соединению, повторное подключение получает новый bootstrap.
RequestId возвращается инициатору в wire-оболочке ответа. В прикладных DU/variant
ответы несут обязательный ID, уведомления — без поля ID; общего optional в ответах нет. Обычный ChatPublished несёт
одно сообщение; история передаётся только при входе. OpenSession v2 несёт одноразовый билет
из HTTP(S) login; пароль и имена в ENet-запрос не передаются. Codec не владеет сессиями и не проверяет
уникальность Username: это ответственность хранилища профилей. SessionTable
у сетевого владельца резервирует PlayerId до завершения старой сессии, cleanup и освобождения транспорта.

Wire contract игровых показаний реализован в v6; пагинация истории ещё не определена.
`generation` модели и `round` истории остаются локальными маркерами, а не серверными
sequence/epoch. Resume и history epoch пока не введены; ticket не является токеном возобновления.
Учётные записи, хеши паролей и профили сохраняются в SQLite и восстанавливаются при входе после перезапуска.
Старые SQL UUID/ULID, уникальный nickname, отдельный PositionSpace и фиксированный
набор level/health из `ProtoExamples` не являются актуальным контрактом MVP.

## Серверные владельцы и жизненный цикл

ServerRuntime владеет ENet и таблицами ConnectionId/PlayerId. SessionTable — обычный
модуль с закрытыми Dictionary; отдельного агента-каталога или кеша нет.
Прикладной путь: runtime → PlayerSession → ChatRoomAgent. Другие игроки и каналы
имеют собственные последовательные владельцы и могут работать параллельно.

PlayerSession погашает билет в AuthService, резервирует подтверждённый профиль и собирает начальные
снимки чата/онлайна. Он хранит только свой Domain.Player, pending RequestId,
ограниченный bootstrap и исходящий порядок. ChatRoomAgent задаёт автора,
MessageId и UTC-время, принимает историю и напрямую рассылает подписчикам.
PresenceAgent отдельно публикует онлайн и периодические изменения PlayerInfo. У каждого источника snapshot и подписка
атомарны; глобального порядка между чатом и присутствием нет. Идентичность сообщения
— (ChannelId, MessageId), счётчик принадлежит каналу.

Mailbox со служебным резервом сохраняет один FIFO. Данные не занимают резерв
Stop/Detach/ответов входа, но служебные сообщения не обгоняют принятые команды.
Full подписчика закрывает только его; канал не ждёт его mailbox и не создаёт
неограниченный набор фоновых рассылок. Отказ управляющего пути виден через Completion.
Ограниченные outbox применяются к командам сессии и управляющему выходу.

Disconnect немедленно закрывает маршрут для новых команд. Резерв PlayerId сохраняется
до фактического Completion старого PlayerSession, подтверждений Detach от чата/онлайна
и освобождения ENet-соединения. Штатный Close допускает отправку принятых пакетов;
по deadline транспорт сбрасывается лишь после готовой domain cleanup.
Очистка после Completion не может оказаться раньше ещё отправляемого старого Join.
Own отменяет и дожидается детей; Watch наблюдает общую зависимость без владения.
OpenTimeoutMs ограничивает вход, ShutdownTimeoutMs — остановку. Потеря общей
зависимости останавливает область runtime; автоматического восстановления нет.

AuthService владеет одноразовыми билетами и допуском операций. SQLite и хеширование
исполняются ограниченными отслеживаемыми workers через AgentReplyDispatcher;
результат возвращается сообщением. Регистрация атомарно сохраняет account и profile.
Билеты теряются при перезапуске, профиль и PlayerId сохраняются.
[Подробности авторизации и текущий NuGet-стек](AuthenticationRu.md).

Подробные контракты, команды запуска и политика перегрузки:
[Server.Core](../src/Dreamsleeve.Server.Core/README.ru.md).
История решения и изменения относительно плана:
[SessionArchitecturePlanRu.md](SessionArchitecturePlanRu.md).

## Реализованная телеметрия v6

PlayerSession владеет персонажем, поколением, положением, actor values и PlayerDetails.
BeginCharacter/LeaveGame сбрасывают игровые данные; RenameCharacter сохраняет показания.
SetLocation надёжно устанавливает или очищает координатный контекст. Измерения позы
поступают отдельно, без RequestId, pending и ACK: только более новый Sequence текущего
ContextRevision заменяет актуальную позицию. Игровые данные не сохраняются в SQLite.

Три канала ENet разделяют Control (0, reliable), Chat (1, reliable) и Realtime
(2, unreliable sequenced). Клиент повторяет последнюю позу по своему периоду;
Presence на каждом периоде отправляет все видимые актуальные позы, включая неподвижных
игроков. Сервер не воспроизводит промежуточные измерения. Метаданные и lifecycle
остаются reliable; автор применяет ту же серверную репликацию, что остальные.

Reliable PlayerVisibilityChanged устанавливает baseline/clear с ViewRevision.
Realtime не может сам создать видимость; неизвестные revision и устаревшие sequence
отбрасываются. MTU ограничивает каждую realtime-пачку без reliable fragmentation.
Принудительного movement-flush перед ответами и чатом больше нет.

TransportOwner обслуживает ENet на отдельном потоке через ограниченные очереди.
Runtime получает уведомление о готовых событиях независимо от периода репликации;
его обработчики и другие агенты не ожидают завершения репликационного тика.
Подробности: [пространственная репликация v6](SpatialReplicationRu.md),
[клиентская интерполяция](MovementInterpolationRu.md).

## Область видимости позиций

PresenceAgent сравнивает WRLD/CELL FormKey и трёхмерное расстояние в Skyrim units.
`Runtime.Presence.VisibilityDistance` задаёт серверный радиус (8192 по умолчанию).
Граница включена, 0 допускает только совпадающие координаты; NaN, infinity и
отрицательный радиус — ошибки настройки. Self получает свои данные независимо от радиуса.
Без собственного положения чужие позиции недоступны. Выход из радиуса/пространства
или потеря позиции посылает reliable PlayerVisibilityChanged без location, сохраняя игрока онлайн.
Вход в область возвращает текущее положение, даже если другой игрок не двигался.
Bootstrap и Joined содержат отфильтрованный baseline. Последующие PlayerUpdated несут метаданные; границы видимости передаются отдельно.

Клиентские `visibilityDistance` и `showFireflies` предназначены для будущего
SKSE-адаптера отображения; сейчас они не отключают сетевой трафик. Клиентский
радиус может ограничить отрисовку, но не расширяет область серверной доставки.
Пространственный индекс по FormKey и трёхмерной сетке реализован; гистерезиса пока нет.
Проверки ограничены соседними ячейками. Полностью плотная группа остаётся O(N²).

Схемы разделены на common/chat/player/session/protocol; network содержит транспортные
причины отключения. Общий package сохранён; пакетное движение использует wire-версию v6.

Публичный ProtocolCodec обрабатывает оболочку и вызывает внутренние преобразования
ChatCodec/PlayerCodec/SessionCodec. Файлы находятся в каталоге Protocol соответствующего
Core-проекта; отдельные экземпляры для частей протокола не создаются.


## Проверка транспорта v6

[Отчёт 27–28 сентября](benchmarks/movement-v6-owner-2026-09-27.md) сравнивает
одинаковый новый протокол с inline ENet и production owner. На 1000 клиентах,
20 Гц источника и группах по 25 owner доставляет около 19,57 свежих поз в секунду
на видимую пару, p95 возраста 51–63 мс. При группах по 100 холодный вход в AOI
сходится с owner (18,66 Гц, 58–95 мс), а inline отключает клиентов. Отдельный
прогрев позиций отделяет установившееся движение от reliable baseline-всплеска:
owner даёт 19,42 Гц и 53–86 мс, inline снова отключает клиентов.
Это короткие локальные измерения, не гарантия ёмкости на другом окружении.

Пройдены 300 managed-тестов, 207 native-тестов, 19 ENet smoke-сценариев и
7 дополнительных тестов владельца транспорта. Protocol v6 требует совместного
обновления клиента и сервера; параллельной поддержки v5 нет.

текущие каналы, повторяемые позы или TransportOwner. Указанные настройки, проверки

### Ход предыдущих измерений

[Первый бенчмарк](benchmarks/movement-2026-09-27.md) и
[повтор после индекса и batching v5](benchmarks/movement-v5-2026-09-27.md)
охватывают 100/500/1000 игроков. На 1000 sparse репликация выросла с 2,50 до
8,43 Гц, p95 снизился с 347 до 130 мс, CPU — с 2,28 до 0,70 ядра.
На 1000 spaces получено 6,83 Гц и p95 419 мс. Dense/500 и boundaries/1000
сходятся после drain, но задержки достигают секунд; dense/1000 всё ещё падает.
Это короткие прогоны с увеличенными лимитами, не гарантия production capacity.
На момент этих измерений production config не менялся; актуальный контракт уже v6.

[Детальная диагностика](benchmarks/movement-diagnostics-2026-09-27.md) отделила
дрейф таймера от сетевой нагрузки: при 100 мс sparse публикуется примерно раз
в 119 мс. При входе 30 Гц и таймере 20 мс получено около 19,3 Гц, но с перегрузкой
ACK и p95 около 0,5 с. Буферы 8 MiB проблему не устранили. Следующие приоритеты:
целевой срок публикации, MTU-бюджет пачек, семантика заменяемого движения и аллокации.
Добавлены Server.ReceiveBufferBytes/SendBufferBytes (default 256 KiB), метрики
транспорта/GC и офлайн TraceReport; принудительный GC и шардирование не добавлялись.

[План оптимизации по результатам диагностики](MovementOptimizationPlanRu.md)
зафиксировал дополнительные пробелы: пересборку actor values на каждом snapshot,
временные коллекции fanout и накладные расходы доставки агентов. Добавлены
изолированные allocation probes. Первая волна реализована: независимые owned tickers,
кеш immutable actor values, detached struct arrays и повторное использование scratch,
ленивые admission notifications и синхронная отправка готовых сообщений outbox,
буфер обхода routes и MTU-aware batching движения. Агенты обрабатывают команды
независимо от transport tick; Presence обновляет состояние сразу, по периоду публикует
накопленные изменения. Wire v5 и reliable/FIFO-семантика сохранены.
[Повторные бенчмарки](benchmarks/movement-opt-wave1-2026-09-27.md) выполнены:
основная матрица — 9/12 проверок сходимости, из них две с сильной деградацией.
Контрольные 20 с при 1000 клиентах в группах по 25 дали 9,88 Гц репликации,
p95 134 мс и 109 MiB private peak. Dense/500 повторно провалился; dense/1000
и boundaries/1000 также не сошлись. До дальнейших оптимизаций нужно отделить
влияние MTU-разбиения контролируемым A/B и установить причину закрытия сессий.
Wire cache, дополнительные route indexes и изменение ACK-барьеров пока не внесены.


[Расследование регрессии](benchmarks/movement-regression-2026-09-27.md) показало,
что ранние разрывы dense/500 существенно зависели от одного общего UDP-сокета
генератора. При нескольких сокетах с прежними per-socket буферами оба режима
пачек сходятся. Отдельный A/B подтвердил накладные расходы принудительного MTU
batching: в прежней версии настройка MovementPacketTargetBytes = 0 отключала разбиение,
положительное значение оставлено для явного эксперимента. Строгий MaxPacketBytes
и reliable delivery сохранены. Добавлены --client-hosts / --movement-packet-target
в стенд и диагностика транспортного разрыва/возраста retry timeout.

Итоговые проверки: 278 managed tests, 19 native smoke, четыре нагрузочных случая
сошлись. На 1000 клиентах с группами по 25 получено 9,78 Гц и p95 130 мс.
Плотные 500 и boundaries/1000 остаются перегруженными: сходимость после drain
не означает устойчивые 10 Гц. Ни шардирование, ни настройки GC не добавлялись.

## Сохранённая аутентификация

Client.Core использует Windows Credential Manager для токена входа на выбранный
сервер: ConnectSaved не требует повторного пароля/env. UI имеет Connect с remember,
SignOut, ForgetSavedLogin и ResetPassword, читает типизированный результат через
Exchange. SQLite schema v2 разделяет аккаунты, password credentials и provider
identities; токены и reset-коды хранятся только как хеши. Серверная консоль поддерживает
reset-password/revoke-access, отзыв закрывает игровое соединение. Будущая админка
вызывает тот же доверенный API. Steam-проверка пока не реализована; общий grant и
игровая сессия от способа входа не зависят. См. AuthenticationRu.md.

### Имя сервера и статусы отправки UI

`Server.ServerName` в серверном TOML (по умолчанию Dreamsleeve, 1–128 символов без
управляющих символов) отправляется в welcome. Клиент публикует имя в ClientStatus,
Client.Dev печатает его. Веб-UI использует snapshot.serverName в обоих заголовках.
Pending-строки существуют только в UI; Core отдаёт bounded chatConfirmations с
корреляцией requestId/messageId, а история остаётся авторитетной. Явный отказ даёт
ручной повтор, обрыв или 15 секунд ожидания — неопределённую доставку без автоповтора.
PrismaUI host реализован в SKSE-адаптере: [SkseClientRu.md](SkseClientRu.md).

### Диагностика остановки ENet (2026-09-29)

В игровом прогоне после disconnect получен `ENet protocol pump failed`.
Это остановка runtime по отрицательному результату ENet, затем отмена Completion,
а не подтверждённое повреждение памяти. Исходный лог не содержит код сокетной
ошибки, поэтому причина прогона пока не установлена.

Адаптер теперь сразу на owner-потоке сохраняет последнюю SocketError и включает
название/код, результат service и число отслеживаемых соединений в причину отказа.
Последняя сокетная ошибка не доказывает, что любой отказ протокола вызван ОС.
Отмена уже аварийно остановленного runtime логируется без вторичного стека.
Никакие неизвестные ошибки ENet не подавляются; автоматический restart не добавлен.

Проверена фактическая xENet 1.3.1 DLL: receive ConnectionReset уже обрабатывается
библиотекой. Регрессионный тест вызывает локальный отказ send (broadcast запрещён),
проверяет AccessDenied и отсутствие устаревшей ошибки при следующем успешном poll.
17 транспортных и 18 ServerRuntime тестов прошли. Обновлена публикация dist/Server;
исправление причины исходного сбоя не заявляется до получения точной диагностики.
