# План: каналы ENet, движение без подтверждений и владелец транспорта

Статус: **план, реализация не начата**. 2026-09-27.
Основание: [исследование с источниками](benchmarks/enet-service-architecture-research-2026-09-27.md),
[эксперимент owner](benchmarks/enet-worker-2026-09-27.md) и проверка текущего кода.
Последнее согласованное решение пользователя — **три канала**; оно уточняет
двухканальную схему раздела E4 исследовательского отчёта.

## Цель и порядок

Сначала исправить семантику движения и убрать обслуживание каждого измерения
как команды. Проверить корректность потерь/перестановок. Затем выделить владельца
ENet и измерить его пользу на новом протоколе. Не смешивать смену протокола,
расписания Service и внутренностей библиотеки в один эксперимент.

Каждый шаг заканчивается сверкой с этим планом, саморевью, целевыми проверками
и отдельным коммитом при реализации. До завершения сквозной миграции новый
протокол не считать готовым к использованию. Не поддерживать старую и новую
семантику параллельно в production; старую ревизию оставить для сравнения.
В этом задании меняются только план и указатель в документации, без бенчмарков.

## Простые решения, которые принимаем заранее

| Канал | Назначение | Пакеты в обоих направлениях |
| --- | --- | --- |
| 0 Control | Сессия, персонаж, локация, вход/выход из видимости, метаданные, обязательные команды | Reliable |
| 1 Chat | Запросы чата, публикации и их ответы | Reliable |
| 2 Realtime | Периодические абсолютные позиции/повороты | Unreliable sequenced |

Идентификаторы — часть версии протокола, не произвольные настройки. Количество
каналов в конфиге не меньше трёх; при создании соединения согласовать нужные три.
Надёжность задаётся флагом пакета. В первый этап Realtime содержит **только движение**.
Actor values/details, приходящие только при изменении, сохраняют reliable.

**Восстановление без нового repair-протокола:** клиент повторяет последнюю валидную
позицию с заданным периодом, даже после остановки. Сервер на каждом периоде
репликации отправляет последние позиции всех видимых игроков, включая неподвижных.
Не только Dirty. Это полный набор позиций в нескольких независимо применимых
пакетах, а не полная PlayerInfo со всем чатом/actor values и не атомарный снимок.
Пропущенная запись восстанавливается на следующем успешно доставленном повторе;
жёсткой гарантии времени при произвольных потерях нет. Отсутствие игрока в одной
пачке не означает удаление. Снятие видимости — отдельное reliable-событие.
Цена простоты — повторение неподвижных позиций; измерить bytes/s, прежде чем
добавлять dirty+редкие repair snapshots. Не внедрять оба варианта одновременно.

**Порядок:** realtime не создаёт игрока, не меняет локацию и не включает видимость.
Это устанавливает reliable-событие с начальной позицией. Измерение для неизвестного
или несовпадающего контекста отбрасывается: не нужны очереди будущих позиций,
asks для восстановления или ожидание всех частей снимка.

## 1. Зафиксировать wire-контракт и инварианты

- [ ] Разделить обязательные PlayerUpdate-команды и MovementSample в proto и типах
  F#/C++. У sample нет RequestId; ClientRequest остаётся с обязательным ID.
  Предпочесть отдельный небольшой realtime envelope выбранного канала, чтобы
  optional RequestId не растекался в домен. Использовать существующее разбиение
  кодеков, без универсального реестра обработчиков.
- [ ] Ввести reliable смену/очистку локации. Сейчас SampleMovement включает
  WRLD/CELL и отсутствие location означает clear — это нужно разделить.
  LeaveGame/BeginCharacter и разрыв непрерывности при телепорте сбрасывают поток.
- [ ] Описать минимальные версии, с назначенным владельцем и сроком жизни:
  **вверх** — контекст движения, установленный reliable-переходом внутри connection;
  **вниз** — revision видимого контекста пары observer/player, выдаваемая Presence.
  Она меняется при новом персонаже/подключении источника, смене пространства,
  повторном входе в AOI и сбросе интерполяции. Не заводить отдельные epoch для
  каждого из этих поводов: один токен downstream-контекста покрывает их все.
- [ ] Для upstream можно использовать монотонный номер перехода, который назначает
  ClientRuntime и передаёт в reliable-команде; сервер устанавливает его только при
  принятом переходе. Обогнавший переход sample отбрасывается, периодический повтор
  исправляет потерю. Refused-переход не должен оставлять клиента бесконечно
  отправляющим в непринятый контекст: завершение reliable-команды явно это разрешает.
- [ ] Downstream revision выдавать из монотонного счётчика наблюдателя в пределах
  его сессии. Не переиспользовать после clear/reentry/reconnect источника; это
  позволяет обходиться без неограниченных tombstones удалённых игроков.
  Поколение подключения наблюдателя уже обеспечивает локальный ClientModel.
- [ ] Номер измерения внутри upstream-контекста задаёт порядок относительно
  reliable baseline и подавляет повторы; source timestamp нужен интерполяции,
  он не заменяет порядок (сейчас допустим 0). Повторное распространение сервером
  того же измерения сохраняет его номер/время. Baseline содержит соответствующий
  номер, чтобы поздний старый sample его не откатывал. Повторное измерение клиента
  получает новый номер; это не request и не требует ответа.
- [ ] Поднять версию протокола, зарезервировать удалённые protobuf поля/номера,
  регенерировать обе стороны тем же protoc. Сохранить существующие MSVC обходы.
  В docs отличить сетевые revision от локальных ClientModel generation/revision.

Проверки: codec round trips в C++ и F#, смена версии, нулевые координаты/уровень,
контекст и номер измерения, запрет movement в command envelope. Exhaustive DU/
variant обработчики без общего catch-all для известных вариантов.

## 2. Провести три канала через транспорт и кодеки

- [ ] Общая классификация Control/Chat/Realtime на границе протокола. Encoder
  возвращает готовый payload с назначением доставки; низкоуровневый ENet adapter
  переводит его в channel/flags и не разбирает protobuf/игровую логику.
- [ ] Расширить ServerTransport.Send/Received и C++ transport boundary метаданными
  канала/доставки. OutgoingPackets.TrySend больше не хардкодит Reliable/channel 0.
  Приём проверяет допустимость payload для выбранного канала, а не просто любой
  channel != 0. Не разрешать произвольные комбинации flags из домена.
- [ ] Ответ/отказ на chat-команду идёт Chat; control-команду — Control. Bootstrap
  SessionOpened с историей остаётся Control. Анонимный malformed realtime не
  порождает reliable-ответ на каждый пакет; действующие пределы/валидация сохраняются.
- [ ] Realtime-пакет всегда укладывается в min(согласованный ENet payload budget,
  прикладной MaxPacketBytes, положительный target если задан). Target=0 означает
  автоматический MTU-лимит для realtime, а не разрешение больших фрагментов.
  Учитывать реальный сериализованный envelope и varint-размеры после новых полей.
  Крупные позиции разбивать на независимые пачки; не использовать unreliable
  fragmentation как замену этому правилу. Reliable snapshot может фрагментироваться.
- [ ] Учесть в документации библиотечный fallback при переполнении unreliable
  sequence: flags=0 не обещает буквально ноль reliable-команд на вечном соединении.

Проверки: фактические channel/flags на обоих концах, неверная классификация,
точная граница MTU, меньший negotiated MTU, недостаточное число каналов.
Файлы: Config, network.proto, SessionContracts, ProtocolCodec, OutgoingPackets,
EnetTransport, DreamNet и managed-нагрузчик. Пакеты и buffers не увеличивать скрыто.

## 3. Упростить серверное движение и сделать надёжными его границы

- [ ] PlayerSession принимает sample отдельным обработчиком без command pending,
  RequestId, PlayerUpdateAccepted и outbox-ответа на каждую позицию. Проверяет
  готовность, установленный контекст и последовательность; сохраняет последнее.
  Ограничения finite/контракта остаются на границе, не дублируются по всем агентам.
- [ ] Presence остаётся владельцем AOI/проекции и периода репликации. Reliable
  события устанавливают/убирают видимый контекст; realtime содержит только pose
  уже видимых игроков. Локация, view revision и начальная поза идут в baseline.
  Выход observer из пространства должен убрать все прежние видимые позиции.
- [ ] Сохранить пространственный индекс. Хранить только необходимые текущие
  видимые пары и их токены, с очисткой при detach; не вводить глобальную матрицу
  всех пар или ещё один cache-agent. Метаданные по-прежнему реплицируются по Dirty.
- [ ] Периодическая отправка позиций работает и при пустом Dirty. Согласованный
  набор текущих состояний в пределах прохода Presence сохраняется. Сам автор
  получает своё серверное состояние тем же путём, отдельного optimistic apply нет.
- [ ] Удалить flushMovement перед chat/settlement/metadata. Переходы теперь защищены
  reliable baseline + revision, поэтому старые movement-boundary flush не нужны.
  Не удалить вместе с ними надежную очистку AOI, Leave/Join и bootstrap.
- [ ] Свести хранение latest к одному месту (Player/Presence). Runtime может иметь
  одну ограниченную пачку на отправку, но не второй цикл накопления/барьеров поверх
  готового периода Presence. Удалить SessionTable.Movement, если после переноса
  пакетирования он больше не решает самостоятельную задачу. Новый movement-agent
  или перенос игровой логики в transport не нужны.

Проверки: clear/повторный вход, движение observer, смена CELL/WRLD, смена персонажа,
reconnect с прежним PlayerId, неавторизованный/устаревший sample, независимость чата.
Промежуточные samples не обязаны все попасть в репликацию; команды не теряются.

## 4. Упростить C++ runtime и сохранить интерполяцию

- [ ] LocalMovement больше не вызывает SendPlayerUpdate: убрать движение из
  pendingUpdates, busy/rejection/timeout-пути подтверждений. Команды смены имени,
  локации, actor values и остальные обязательные операции сохраняют корреляцию.
- [ ] ClientRuntime хранит последнюю локальную позу и периодически отправляет её
  в установленном контексте, пока игрок в игре и поза валидна. Clear/Leave прекращают
  отправку. Вход SKSE/Main::Update остаётся через ClientExchange; при накоплении
  samples до сети достаточно последнего, но lifecycle-команды не заменяются им.
- [ ] ClientModel применяет realtime только к существующему видимому контексту
  и не откатывает его номер измерения. Несовпадение/старый sample — нормальный drop,
  не SessionFault. Reliable clear сразу удаляет pose и историю интерполяции.
- [ ] PlayerUpdated/metadata не должны поздним reliable-снимком откатывать более
  новую realtime-позицию. Изменение имени/actor values не переустанавливает baseline.
  Проверить и сузить существующие полные PlayerInfo update до их реальной роли.
- [ ] MovementView продолжает хранить измерения; снять предположение общего
  reliable FIFO, учитывать сброс контекста и повторы baseline. Не переписывать
  алгоритм интерполяции или добавлять предсказание в этой работе.
- [ ] Учесть ChatPublished до SessionOpened между каналами: небольшой ограниченный
  bootstrap-буфер чата до готовности, затем обычное применение с существующей
  дедупликацией message_id. Не буферизовать ранние realtime-позиции. Автор уже
  вложен в ChatMessage, запрашивать PlayerInfo ради показа сообщения не нужно.

Проверки: до baseline/после clear, повтор/старое измерение, metadata после realtime,
остановка, смена контекста, собственный echo, chat до welcome и история с повторами.

## 5. Проверить потери и обновить нагрузчик до смены owner

- [ ] Детерминированный тестовый transport с заданным drop/reorder schedule,
  используя существующие тестовые границы; не отдельный фреймворк симуляции сети.
- [ ] Потерять последнее движение A, продолжать движение B. После остановки A
  периодическая репликация обязана восстановить его pose при доставленном повторе.
- [ ] Потерять часть MTU-пачек; доставить последующую пачку раньше предыдущей.
  Независимые записи применяются, следующий цикл восстанавливает пропущенные;
  отсутствие записи не скрывает игрока и не требует сборки целого snapshot.
- [ ] Переставить realtime относительно location/visibility/Join/Leave; после
  reliable clear старая позиция не воскресает, после reentry старый token не подходит.
- [ ] Нагрузчик использует те же 3 канала, MTU и периодические samples; убрать
  pending ACK cap для движения. Считать реальные produced/admitted/received,
  пропуски периода/очереди, source age, per-player stale duration и сходимость.
  Для финальной проверки остановить изменение координат, но продолжать повторять
  последнюю позу до ограниченного срока проверки; завершение процесса не «repair».
- [ ] На этом этапе сквозной smoke и все затронутые тесты F#/C++ должны проходить.
  Обновить Client.Dev команды перехода/движения и демонстрацию интерполяции.

Это обязательная контрольная точка перед выделением owner: более низкая задержка
из-за невосстановимой потери части состояния не считается улучшением.

## 6. Ввести небольшой production owner без нового уровня доменных агентов

- [ ] Один OS thread в Infrastructure создаёт/обслуживает/уничтожает Host, Peer,
  packet leases. Runtime получает detached events, отправляет готовые payloads;
  транспорт не кодирует домен и не занимается AOI. Текущий эксперимент — источник
  проверок, не готовая production-реализация для копирования.
- [ ] Две ограниченные очереди направлений; count/byte limits и резерв lifecycle.
  Переиспользовать библиотечные примитивы, если подходят, без универсального
  scheduler/новой акторной библиотеки. Пачки небольшие, передаются по готовности
  с владением неизменяемым buffer; нет барьера окончания всего игрового тика.
- [ ] Чередовать bounded исходящий admission и обслуживание/выдачу ENet событий.
  Не вычитывать одно направление до пустоты. Пределы count/bytes/time относятся
  к нашему проходу; Service(0) не становится от этого ограниченным по длительности.
  Не вводить адаптивный алгоритм до необходимости; начальные пределы — config.
- [ ] Не полагаться на выдачу уже готовых events как на факт чтения UDP. Проверить
  доступный путь protocol pump без раннего dispatch (Service с null event) и
  bounded CheckEvents; если обёртка не предоставляет его, узкий interop helper,
  с отдельными lifecycle-тестами. Не менять внутренний scheduler ENet на этом шаге.
- [ ] При исходящей работе — wakeup; idle wait короткий и прерываемый. Сеть не ждёт
  ReplicationIntervalMs. Runtime также своевременно получает ready-notification:
  одна объединяемая нотификация + bounded drain/повтор, без сообщений на каждый
  пакет и без потери wakeup. Existing timer остаётся для deadlines, не для всей
  логики агентов. Проверить stop/дедлайны независимо от нагрузки.
- [ ] Отделить accepted-to-queue от доставки. Не выдавать per-sample Task/TCS или
  ACK для handoff. Нативный отказ reliable направляется runtime с connection и
  причиной; fault/completion owner наблюдаемы вне заполненной data queue.
- [ ] Перегрузка realtime допускает пропуск до admission, следующий период повторит
  состояние. Не превращать её в массовые disconnect. Reliable/control не теряются
  молча: bounded admission, резерв Close/Reset и явное закрытие медленного peer при
  невозможности сохранить контракт. Размеры per-peer не дают одному клиенту занять
  весь буфер. Не плодить новый надёжный retry-протокол поверх ENet.
- [ ] DisconnectLater продолжает pump до disconnect/deadline, затем Reset; Dispose
  на owner, однократное освобождение всех буферов/leases. Проверить повторный запуск
  сервера и сообщения со старым ConnectionId. Минимальные локи на границе допустимы;
  доменные агенты остаются со своим последовательным владением состоянием.

Проверки: владение, порядок reliable, saturation обоих направлений, отсутствие
starvation Close/receive, ошибки startup/native send/loop, stop при полном буфере,
устаревшее соединение и все пути освобождения. Существующие 6 experiment-тестов
не покрывают production shutdown/перегрузку — расширить проверки именно поведения.

## 7. Измерить результат и закрыть чистку

- [ ] Сначала новый протокол без owner, затем тот же протокол с owner. Одинаковые
  payload schedule/частоты/буферы/MTU, чередующиеся повторы. Старый reliable baseline
  сравнивать отдельно как смену протокола, не как чистый выигрыш scheduler.
- [ ] После этого отдельно сравнить готовые небольшие handoff-пачки; глобальный
  tick buffer и per-packet wakeup не внедрять оба как постоянные режимы продукта.
- [ ] Наблюдать оба конца: реальные receive gaps, service gaps, retries, UDP drops,
  очереди/их возраст, sourceHz, состояние неподвижных игроков, CPU/аллокации и
  стоимость telemetry. Свести влияние общего lock benchmark MeterListener к
  известной величине; тяжёлый probe запускать отдельно от основных цифр.
- [ ] Проверить 1000 клиентов/20 Гц и разные AOI, затем отдельные машины/RTT, если
  доступны. Нагрузочные измерения запускать отдельно от сборок/тяжёлых приложений.
  Порог приемлемого возраста определить до теста; не выдавать convergence за 20 Гц.
- [ ] Обновить protocol/README.ru.md, README обоих Core, State README, серверный и
  клиентский конфиги, корневую документацию и инструкции тестов. Удалить старые
  assertions channel0/reliable-only, movement settlement метрики, мёртвые варианты
  и comments про общий reliable FIFO. Не переименовывать всё остальное заодно.
- [ ] Зафиксировать оставшиеся ограничения. Fork ENet с продолжимым send-pass,
  zENet, IOCP, шардинг, ручной GC, новые пулы и repair/ACK-менеджеры **не входят** в
  этот рефактор. Вернуться к ним только если новый профиль показывает необходимость.

## Что должно стать меньше

RequestId/pending/settlement для движения; принудительные flush перед любым ответом;
сохранение каждого устаревшего измерения; runtime-словарь границ движения; скрытая
зависимость доменной логики от транспортного тика. Добавления ограничены реальными
новыми границами: контекст движения/видимости, три канала и владелец транспорта.

Критерий завершения: корректные потери/перестановки и lifecycle, единый новый
контракт на C++/F#/нагрузчике, bounded наблюдаемые очереди, нет молчаливой потери
reliable-команд, воспроизводимый отчёт и отсутствие двух параллельных production
реализаций. Нагрузочная цель и архитектурная корректность оцениваются отдельно.
