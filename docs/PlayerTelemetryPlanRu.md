# Передача состояния игрока: план и границы

Исходный план первой реализации v3; изменение контракта v4 описано ниже.
Продолжение после авторизации и SQLite. Работа идёт через Server и Client.Dev,
без SKSE и PrismaUI. Используются существующие Domain.Player и ClientModel.

## Контракт

- Protocol v3: начальный список и PlayerJoined содержат полный PlayerInfo.
- PlayerInfo включает серверный профиль, имя персонажа, необязательное положение,
  actor values, поколение персонажа и PlayerDetails. Профиль/PlayerId клиент не задаёт.
- Команды: BeginCharacter, RenameCharacter, Sample (полное показание location +
  actor values), SetDetails, LeaveGame. Начало персонажа и выход сбрасывают прошлую телеметрию;
  поколение меняется даже при одинаковом имени. Rename сохраняет показания.
- У Sample отсутствующая location означает неизвестное положение, пустые actor values
  очищают карту. Scalar(0) отличается от отсутствующего варианта. Resource допускает
  отрицательное значение и current > maximum. NaN/Infinity отклоняются.
- Все команды имеют RequestId. ACK подтверждает принятие, но клиентская модель
  изменяется только серверными уведомлениями; автор получает ту же репликацию.
- Начальная версия использует существующий reliable ENet-канал. Переход на
  unreliable/sequenced потребует отдельного контракта порядка и подтверждений.

## Владельцы

PlayerSession принимает валидированные команды своего соединения и владеет Player.
PresenceAgent хранит неизменяемые проекции для онлайна/репликации, объединяет частые
изменения и периодически рассылает последнее состояние каждого изменённого игрока.
Если изменилось только положение, отправляется PlayerMoved без профиля/actor values.
Иные изменения отправляются PlayerUpdated. Неизменившиеся данные не рассылаются.
ServerRuntime остаётся владельцем транспорта и короткой диспетчеризации.

Очереди, число actor values, строки и пакеты ограничены. Период репликации задаётся
конфигом; следующий tick планируется после обработки предыдущего, без очереди тиков.
Старое соединение не обновляет нового владельца PlayerId; detach удаляет dirty state.
Поздний подписчик получает актуальный полный снимок, затем упорядоченные изменения.

Игровые данные не пишутся в БД. RenameCharacter не меняет Username/DisplayName
учётной записи. Позиция сохраняет FormKey пространства (WRLD/CELL), координаты Skyrim
и Euler rotation в радианах; ограничений скорости/HP сервер не вводит.

## Этапы и проверка

1. Общий proto, генерация, доменные операции и кодеки; проверки presence/oneof,
   конечности чисел, нормализации и лимитов. Сверка F#/C++.
2. Session/Presence/runtime: coalescing, bootstrap, авторская репликация, lifetime,
   сброс/смена персонажа, отсутствие устаревшего dirty state после detach.
3. ClientRuntime/Exchange/Dev: действующая отправка игровых команд, bounded pending,
   изменения модели через сервер, вывод состояния и команды без самой игры.
4. Общие managed/native тесты, реальный сквозной smoke двух клиентов и позднего входа,
   регрессия чата/авторизации, документация и review перед коммитом.

Метаданные остаются глобальными; последующим шагом добавлена фильтрация позиций
по пространству/радиусу (см. CurrentStateRu.md). Интерполяция и игровой hook
остаются будущими шагами; текущий сетевой тест
не является доказательством пропускной способности для тысячи движущихся игроков.

## Уточнение PlayerDetails по Skyrim Rich Presence

Пользователь уточнил состав PlayerInfo по
[skyrim-rich-presence](https://github.com/doodlum/skyrim-rich-presence/blob/7209d0e1c9e1e4fdfd6fbb790cf38623cbac31b2/src/RichPresence.cpp).
Исходник просмотрен на commit `7209d0e1c9e1e4fdfd6fbb790cf38623cbac31b2`;
реализация плагина не копируется, Discord RPC не добавляется в зависимости.

PlayerDetails хранит отдельные наблюдения:

- Race: FormKey записи расы и её подпись; Level: необязательный uint32, включая ноль; отсутствие отличается от нулевого уровня.
- Activity: вид занятия, необязательная подпись цели, сложность замка для Lockpicking,
  ключ меню для Menu. Поддерживаются бой, диалог, торговля, обучение, чтение,
  крафт, использование объекта, езда, скрытность, плавание, полёт, смерть,
  ragdoll, меню, новая игра и загрузка. Unknown отличается от Exploring.
- Place: подписи мира, локации и ближайшего маркера, расширяемый ключ типа маркера,
  признак интерьера. Они не участвуют в сравнении координат.
- GameStartedAt: сообщённое клиентом время начала игрового процесса; UI сам
  вычисляет elapsed, сервер не выдаёт его за время входа в сетевую сессию.

SetDetails передаёт блок целиком отдельно от Sample; движение не пересылает его
каждый раз. Main menu/New game допустимы без активного персонажа. Race/Level
при отсутствии персонажа отклоняются. Begin/Leave очищают details вместе с
прежней телеметрией. Локализованные подписи целей сохраняются без нормализации,
ключи меню/маркеров нормализуются ASCII folding и имеют отдельный лимит.

Discord application title, картинки и кнопки — настройки представления.
Опциональные HUD-уведомления, MiscStats и survival-индикаторы плагина не являются
автоматической рассылкой в этом шаге; actor values уже имеют расширяемые ключи.

Для проверки контрактов достаточно Client.Dev; интеграция с SKSE должна позже
читать данные на допустимом игровом/UI-потоке и передавать самостоятельные значения.
Код плагина использует Main update, game tasks и UI tasks; переносить его обращения
к RE-объектам в сетевой поток нельзя.

## Сверка реализации

Этапы 1–3 реализованы. Саморевью и перекрёстная сверка выявили и исправили:
различение отсутствующего Place в C++/F#, настраиваемый лимит actor values,
потерю возврата к старому значению после поздней подписки и повторное включение
медленного подписчика, удалённого во время публикации перед Join.
Снимки Presence хранят только нужные Latest/Published, без удержания начального Snapshot.

Managed Release: 250 тестов, без предупреждений сборки. Текущий microbenchmark
прошёл 8 сценариев по 1024 запроса; отдельный сетевой smoke benchmark v3 доставил
4/4 сообщений без ошибок. Эти короткие прогоны проверяют работоспособность harness,
а не производительность массовой телеметрии. Исторические benchmark-отчёты не изменены.

Реальный Server + C++ Client.Dev smoke прошёл 13 проверок: автор/наблюдатель/поздний вход,
полный PlayerInfo и details, движение без потери остальных данных, rename, сброс
при одинаковом имени/выходе, чат, reconnect и восстановление SQLite после restart.
Локальный журнал: `build/smoke-chat.log` (генерируется повторным запуском, не хранится в Git).

Финальные native: 179/179 тестов; Client.Dev собран. Все четыре этапа выполнены,
документация и экспорт server.example.json обновлены, git diff --check чист.

Последующий шаг видимости: серверный радиус и клиентские настройки отображения
добавлены; метаданные глобальны, позиции проецируются по WRLD/CELL и расстоянию.
Проверено 256 managed / 180 native тестами и 17 сценариями реального ENet smoke.
Саморевью: предыдущая база фиксирована до завершения всей пачки, движение наблюдателя
пересчитывает неподвижные источники, удалённые при доставке участники не воскресают.
Настройки отображения предназначены для будущего SKSE, сетевые подписки от них не зависят.

## Разделение компонентов — Protocol v4

Объединённая Sample-команда заменена независимыми Move, SetActorValues и SetDetails.
WRLD/CELL остаётся внутри положения. Движение не трогает показания, они не трогают
местоположение. Пустая карта actor values означает явную очистку.
Сервер сравнивает Latest/Published на своём интервале: позиция уходит PlayerMoved,
изменившиеся actor values/Details — PlayerMetadataChanged (только присутствующие
компоненты заменяются). Профиль, имя, поколение и bootstrap остаются полными.
Несколько измерений объединяются до последнего; возврат к опубликованной версии
и неизменившиеся компоненты не отправляются. Неизменившаяся позиция не heartbeat.
Клиентский и серверный интервалы по умолчанию 100 мс, но не синхронизируются.
Actor values сейчас заменяются картой целиком, без отдельного протокола удаления ключей.

Старая ветка oneof зарезервирована, v3 отклоняется проверкой версии. Кодеки и
модель клиента обновлены, Dev принимает move/values/details. Проверки: 258 managed,
182 native, 18 сценариев ENet smoke. Оба benchmark-проекта собираются.
Саморевью проверило presence/empty, отсутствие локального эха, сохранение AOI и
порядка при удалении медленного подписчика между metadata и movement.

## История движения и интерполяция — реализовано

В v4 совместимо добавлено время замера PlayerLocation.sampled_at_us. C++ сохраняет
упорядоченные наблюдения внутри существующего exchange; игровой потребитель
MovementView держит ограниченную историю и интерполирует XYZ/rotation без экстраполяции.
При переполнении восстанавливается снимком. Добавлены настройки и Client.Dev demo/watch.
[Поведение, проверка и ограничения](MovementInterpolationRu.md).

Следующим шагом остаётся сетевой бенчмарк движущихся клиентов, затем решение о
пространственном индексе по измерениям. SKSE-интеграция остаётся отдельной задачей.
