# Серверные владельцы: профили, каналы и сессии

Реализованы контракт профилей, агент хранения в памяти, агент канала и реестр сессий.
Запускаемый Dreamsleeve.Server пока остаётся заглушкой; ENet и вход не подключены.

## Владение и зависимости

- Domain: валидированные идентификаторы, имена и неизменяемый PlayerData.
- Agent: локальные mailbox, адресаты AgentRef и фоновые операции PipeToSelf.
- Core: протокол профилей, ChatAgent и SessionRegistry — автомат входа/выхода и реестр онлайна.
- Infrastructure: модуль MemoryProfileStore с состоянием, обработчиком и start.
- Server: будущая точка сборки зависимостей и жизненного цикла.

`MemoryProfileStore.start capacity` возвращает обычный `Agent<ProfileRequest>`.
Частичное применение `handle state` передаёт состояние именованному обработчику.
Словарь и выдача ID принадлежат этому агенту; наружу не возвращается состояние или
функции прямого доступа к нему. Собственных lock, Interlocked, очереди заданий,
интерфейса IProfileStore или класса-обёртки ProfileAgent нет.

## Контракт и выполнение

FindByUsername возвращает Found с профилем либо отсутствием, Create — Created
либо UsernameTaken/IdExhausted. Создание резервирует канонический Username и
ненулевой uint64 PlayerId в одном обработчике. Обращения нескольких отправителей
сериализуются mailbox; поиск не создаёт профиль и не авторизует игрока.

Запрос содержит OperationId: Guid и ReplyTo: ReliableAgentRef<ProfileReply>. Это внутренняя
корреляция, а не клиентский wire RequestId. Получатель использует Ref.Map для
включения ответа в собственный DU и проверяет актуальность своей операции.
При сборке адреса `Ref.TryReliable()` возвращает Some только для unbounded или
bounded-wait mailbox; Map сохраняет это ограничение. Dropping-mailbox нельзя
передать в ProfileRequest. Обработчик видит только Posted/Closed/Canceled,
не проверяет политику очереди и не бросает исключение при её несовпадении.

Операции над памятью выполняются непосредственно в обработчике. Выносить доступ
к принадлежащему агенту словарю в PipeToSelf нельзя: фоновая работа не становится
владельцем состояния. Настоящий агент БД сможет использовать те же команды/ответы,
запускать внешнее асинхронное I/O и получать результаты сообщениями через PipeToSelf.
Реализация агента БД и управление его параллелизмом пока не добавлены.

## Очередь и остановка

Capacity ограничивает ожидающие запросы в стандартном bounded-wait mailbox;
ещё один запрос может находиться в обработчике. TryPost возвращает обычный
AgentPostResult, PostAsync асинхронно ожидает свободное место.

После операции обработчик асинхронно отправляет ответ. Если mailbox получателя
заполнен, агент памяти ждёт приёма ответа перед следующим запросом. Поток при этом
не блокируется. Это явное обратное давление; фоновые отправки не накапливаются.
Закрытый получатель не откатывает уже выполненную запись. Posted означает только
помещение сообщения в очередь, а не его обработку получателем.

Complete запрещает новые запросы и дренирует уже принятые, включая отправку ответов.
Abort отменяет ожидание отправки и прекращает обработку. Всё это обеспечивает
сама библиотека Agent. Если живой получатель не читает mailbox, graceful shutdown
может ждать: будущий супервайзер должен ограничить время остановки и вызвать Abort.

Офлайн-профили сохраняются до завершения агента. При перезапуске сетевой части
нужно оставлять агент хранения живым. Новый агент или новый процесс начинают
с пустого хранилища; перенос состояния между владельцами и сохранение на диск
не реализованы. Нет отдельного разделяемого объекта хранения вне агента.

## Наблюдение за аварией

Необработанное исключение при стандартной политике останавливает агент:
Completion завершается с исходной ошибкой, StopReason содержит Faulted.
Владелец должен наблюдать Completion. Он может ожидать его через PipeToSelf
и получить результат сообщением в собственный mailbox, продолжая обрабатывать
остальные команды. Даже если дочерний агент уже завершился, уведомление не теряется.
Completion завершается после очистки и фоновой работы; только затем можно
создать замену и выдать потребителям её новый Ref. Старый адрес остаётся Closed.

Подписка на событие Stopped после Start может пропустить ранний сбой. Для callback
нужно задавать OnStopped в options до запуска; callback вызывается перед Completion
и не должен ждать эту задачу. Автоматического перезапуска пока нет: будущий
супервайзер определит политику повторов и судьбу незавершённых запросов.
Перезапуск MemoryProfileStore теряет профили и сбрасывает выдачу ID — это нельзя
считать прозрачным восстановлением работающих сессий. Принятые команды сами
повторно не исполняются; до сбоя запись могла уже выполниться без доставки ответа.

## Агент канала чата

`ChatAgent.start config channelId output` создаёт `Agent<ChannelRequest>` в Core.
ChatAgentConfig задаёт MailboxCapacity и HistoryCapacity; обе ёмкости положительные,
передаются при старте. Изменяемый Domain.Chat создаётся внутри start и остаётся
у одного обработчика. Дополнительных коллекций участников, lock и обёрток нет.

Команды и результаты:

| Команда | Результат |
|---|---|
| Join PlayerId | Joined с независимым снимком участников и сохранённой истории после входа |
| Leave PlayerId | Left с признаком удаления; повторный выход возвращает false |
| Publish ChatMessage | Published с принятым сообщением и снимком получателей на момент приёма, включая автора |
| ReadHistory(cursor, maxCount) | History с ограниченной страницей, курсором, HasGap и HasMore |

OperationId — внутренняя корреляция. Все ChannelReply содержат ChannelId и идут
в один ReliableAgentRef, заданный при старте. Это сохраняет порядок между снимком
входа и последующими публикациями. SessionRegistry уже обрабатывает вход/выход
в этом порядке. Публикации пока не подключены: при добавлении SendChat реестр
будет сопоставлять OperationId с RequestId, возвращать автору ChatAccepted,
остальным — ChatPublished.
Отдельного локального сообщения для автора нет. Сам ChatAgent пакеты не рассылает.

Publish принимает уже составленный сервером ChatMessage. Привязка автора к живой
сессии, назначение ID/времени и проверка права входа в канал принадлежат вызывающему
серверному компоненту и ещё не подключены. При общей выдаче ID владелец должен
сохранять их порядок при отправке команд в каждый канал. ChatAgent использует
проверки Domain.Chat: другой канал, отсутствие участника или невозрастающий ID
дают DomainError без изменения истории. Текст и профиль повторно не валидируются.
OperationId не обеспечивает дедупликацию команд. Профиль автора хранится в сообщении
и сохраняется в истории после его выхода.

При заполненном output обработчик асинхронно ждёт место; следующие команды
ограничены MailboxCapacity. Фоновые отправки не накапливаются. Complete дренирует
принятые команды и ответы; Abort отменяет ожидание и отбрасывает остаток.
Если отправка обнаружила закрытый output, канал вызывает Abort: продолжать работу
без единственного получателя результатов нельзя. Владелец наблюдает Completion.
Само помещение ответа в очередь ещё не подтверждает его обработку или доставку
клиентам. Остановка не откатывает уже выполненную команду.

Владелец output должен продолжать читать свой mailbox при отправке команд каналу:
циклическое ожидание двух заполненных очередей приведёт к зависанию. Он должен
обрабатывать Full либо использовать ограниченные фоновые отправки с результатами
в mailbox, а не ждать ответ внутри собственного обработчика.

Повторный Join идемпотентен по участникам и возвращает свежий снимок. SessionRegistry
отсекает устаревшие ответы через OperationId и удерживает имя до завершения Leave;
старое соединение не может удалить участника после повторного входа.
Перезапуск канала создаёт пустую историю и состав участников; автоматического
восстановления и wire-пагинации пока нет.

## Реестр сессий

`SessionRegistry.start config globalId profiles output` возвращает обычный Agent.
Config задаёт MailboxCapacity и MaxSessions; лимит сессий включает незавершённые
входы и выходы. При сборке сервера MaxSessions должен укладываться в
ServerConfig.MaxInitialPlayers, а история канала — в MaxRecentMessages и бюджет
пакета. Преобразование OpenSession в SessionOpenRequest выполняется после codec:
доменные строки и ненулевой RequestId повторно здесь не проверяются.

Владелец запускает профильное хранилище, реестр, затем ChatAgent с выходом
`registry.Ref.Map(SessionRegistryMessage.ChannelReplied).TryReliable()`.
После этого отправляет реестру BindChannel с адресом канала и только затем
начинает передавать Open/Disconnect. Привязка выполняется один раз; до неё вход
закрывается. Это сборка взаимных адресов через сообщения, без разделяемой
изменяемой ссылки. Повторная привязка работающего канала считается ошибкой сборки.

ConnectionId — новый Guid для каждого транспортного соединения. Индекс ENet peer
может переиспользоваться и не подходит. Сетевой владелец прекращает отправку команд
закрытого соединения; повторное подключение получает другой ID.

Вход проходит Finding → Creating (если профиля нет) → Joining → Online.
Ответы хранилища и канала возвращаются сообщениями. Пока имя занято входом,
онлайном или выходом, второй вход под тем же каноническим Username отклоняется.
Повторный Open на том же соединении получает SessionAlreadyOpen.
Существующий офлайн-профиль используется повторно; переданный DisplayName не
перезаписывает сохранённый. При гонке с внешним создателем профиля Create может
вернуть UsernameTaken: реестр отклоняет этот вход, не запускает бесконечные retry.
Всё это Dev-идентификация, без проверки владения именем и без настоящей авторизации.

После подтверждения Join реестр отправляет SessionOpened с собственным ID,
упорядоченным списком онлайна и историей канала. Остальным живым сессиям —
PlayerJoined. Disconnect ставит Leave; PlayerLeft публикуется после его ответа.
Если Disconnect пришёл во время поиска/создания профиля, запоздавший результат
освобождает резервирование, но не открывает сессию. Во время Join реестр дожидается
Joined и отправляет компенсирующий Leave. Имя удерживается до ответа на Leave.
Дубли старых ответов игнорируются по OperationId. История может содержать профили
уже ушедших авторов. Начальный онлайн и последующие PlayerLeft согласованы
с порядком ответов канала, включая выход во время входа другого игрока.

Отправки в зависимости выполняются через один последовательный outbox:
PipeToSelf ждёт допуска в mailbox вне обработчика. Реестр продолжает читать
команды и отключения. На сессию приходится не больше одной ожидающей операции,
поэтому число операций и отложенных отправок ограничено MaxSessions;
одновременно ждёт допуска только одна отправка. Отправки подтверждают лишь приём,
их результат не подменяет ответ хранилища или канала.

SessionOutput.Send содержит ConnectionId и готовый ChatResponse; Close требует
закрыть транспортное соединение. Failed передаёт причину ошибки владельцу.
Выход имеет bounded-wait/unbounded политику; ожидание его допуска асинхронное,
но приостанавливает обработчик реестра. Поэтому транспортный владелец должен
продолжать читать выход и не создавать циклическое ожидание очередей.

Для корректной остановки отправляется Stop, затем ожидается Completion.
Реестр закрывает соединения, дожидается начатых операций и Leave, после чего сам
вызывает Complete. Прямой Complete закрывает приём ответов и для этого сценария
не подходит. При превышении времени остановки владелец вызывает Abort; отмена
прерывает ожидание допуска, но не откатывает уже принятые команды зависимостей.

Профили и канал принадлежат внешнему владельцу жизненного цикла. Он обязан
наблюдать их Completion и передавать DependencyStopped, в том числе при сбое после
успешного допуска запроса. Закрытая очередь обнаруживается при отправке и без
этого сообщения. При ошибке реестр публикует Failed, закрывает живые соединения
и прекращает работу. После такого сбоя требуется остановить и пересоздать связку
реестр/канал: частично выполненные Join/Leave не восстанавливаются автоматически.
Автоматический супервайзер, мониторинг зависимостей и дедлайн входа в запущенном
сервере пока не подключены; без ответа зависимости или сообщения её владельца
ожидающая операция остаётся ожидающей. Профильное хранилище можно сохранить
между штатными перезапусками этой связки.

## Следующие компоненты

Нужно подключить SendChat к реестру: назначение ID/времени, подтверждение автору
и рассылка остальным. Затем — сетевой владелец ENet и сборка жизненного цикла с
наблюдением Completion и остановкой по дедлайну. Агент активного игрока также
ещё предстоит; реестр пока хранит только профили и этапы входа/выхода.
Запускаемый сервер всё ещё заглушка; сквозной вход из Client.Dev пока не доступен.
