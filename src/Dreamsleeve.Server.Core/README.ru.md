# Серверные владельцы: профили, игроки, каналы и реестр

Реализованы хранилище профилей, персональные PlayerAgent, ChatAgent и SessionRegistry.
Запускаемый Dreamsleeve.Server пока остаётся заглушкой; сетевой runtime не подключён.

## Владение и зависимости

- Domain: валидированные идентификаторы, имена и неизменяемый PlayerData.
- Agent: mailbox, AgentRef, PipeToSelf и ограниченные последовательные отправки AgentOutbox.
- Core: PlayerAgent владеет входом и Player; ChatAgent — каналом; SessionRegistry — резервами PlayerId, маршрутами и общим онлайном.
- Infrastructure: модуль MemoryProfileStore с состоянием, обработчиком и start.
- Server: будущая точка сборки зависимостей и жизненного цикла.

`MemoryProfileStore.start capacity` возвращает обычный `Agent<ProfileRequest>`.
Частичное применение `handle state` передаёт состояние именованному обработчику.
Словарь и выдача ID принадлежат этому агенту; наружу не возвращается состояние или
функции прямого доступа к нему. Собственных lock, Interlocked, очереди заданий,
интерфейса IProfileStore или класса-обёртки ProfileAgent нет.

## Контракт и выполнение

FindByUsername возвращает Found с профилем либо отсутствием, Create — Created
либо UsernameTaken/IdExhausted. Создание резервирует канонический Username и
ненулевой uint64 PlayerId в одном обработчике. Обращения нескольких отправителей
сериализуются mailbox; поиск не создаёт профиль и не авторизует игрока.
Для входа используется GetOrCreate → Resolved: одна атомарная операция возвращает
существующий профиль или создаёт новый. Повторное получение сохраняет PlayerId
и DisplayName. Реестр больше не согласует отдельные Find/Create и их гонку.

Запрос содержит OperationId: Guid и ReplyTo: ReliableAgentRef<ProfileReply>. Это внутренняя
корреляция, а не клиентский wire RequestId. Получатель использует Ref.Map для
включения ответа в собственный DU и проверяет актуальность своей операции.
При сборке адреса `Ref.TryReliable()` возвращает Some только для unbounded или
bounded-wait mailbox; Map сохраняет это ограничение. Dropping-mailbox нельзя
передать в ProfileRequest. Обработчик видит только Posted/Closed/Canceled,
не проверяет политику очереди и не бросает исключение при её несовпадении.

Операции над памятью выполняются непосредственно в обработчике. Выносить доступ
к принадлежащему агенту словарю в PipeToSelf нельзя: фоновая работа не становится
владельцем состояния. Настоящий агент БД сможет использовать те же команды/ответы,
запускать внешнее асинхронное I/O и получать результаты сообщениями через PipeToSelf.
Реализация агента БД и управление его параллелизмом пока не добавлены.

## Очередь и остановка

Capacity ограничивает ожидающие запросы в стандартном bounded-wait mailbox;
ещё один запрос может находиться в обработчике. TryPost возвращает обычный
AgentPostResult, PostAsync асинхронно ожидает свободное место.

После операции обработчик асинхронно отправляет ответ. Если mailbox получателя
заполнен, агент памяти ждёт приёма ответа перед следующим запросом. Поток при этом
не блокируется. Это явное обратное давление; фоновые отправки не накапливаются.
Закрытый получатель не откатывает уже выполненную запись. Posted означает только
помещение сообщения в очередь, а не его обработку получателем.

Complete запрещает новые запросы и дренирует уже принятые, включая отправку ответов.
Abort отменяет ожидание отправки и прекращает обработку. Всё это обеспечивает
сама библиотека Agent. Если живой получатель не читает mailbox, graceful shutdown
может ждать: будущий супервайзер должен ограничить время остановки и вызвать Abort.

Офлайн-профили сохраняются до завершения агента. При перезапуске сетевой части
нужно оставлять агент хранения живым. Новый агент или новый процесс начинают
с пустого хранилища; перенос состояния между владельцами и сохранение на диск
не реализованы. Нет отдельного разделяемого объекта хранения вне агента.

## Наблюдение за аварией

Необработанное исключение при стандартной политике останавливает агент:
Completion завершается с исходной ошибкой, StopReason содержит Faulted.
Владелец должен наблюдать Completion. Он может ожидать его через PipeToSelf
и получить результат сообщением в собственный mailbox, продолжая обрабатывать
остальные команды. Даже если дочерний агент уже завершился, уведомление не теряется.
Completion завершается после очистки и фоновой работы; только затем можно
создать замену и выдать потребителям её новый Ref. Старый адрес остаётся Closed.

Подписка на событие Stopped после Start может пропустить ранний сбой. Для callback
нужно задавать OnStopped в options до запуска; callback вызывается перед Completion
и не должен ждать эту задачу. Автоматического перезапуска пока нет: будущий
супервайзер определит политику повторов и судьбу незавершённых запросов.
Перезапуск MemoryProfileStore теряет профили и сбрасывает выдачу ID — это нельзя
считать прозрачным восстановлением работающих сессий. Принятые команды сами
повторно не исполняются; до сбоя запись могла уже выполниться без доставки ответа.

## Агент канала чата

`ChatAgent.start config channelId output` создаёт `Agent<ChannelRequest>` в Core.
ChatAgentConfig задаёт MailboxCapacity и HistoryCapacity; обе ёмкости положительные,
передаются при старте. Изменяемый Domain.Chat создаётся внутри start и остаётся
у одного обработчика. Дополнительных коллекций участников, lock и обёрток нет.

Команды и результаты:

| Команда | Результат |
|---|---|
| Join PlayerId | Joined с независимым снимком участников и сохранённой истории после входа |
| Leave PlayerId | Left с признаком удаления; повторный выход возвращает false |
| Publish ChatMessage | Published с принятым сообщением и снимком получателей на момент приёма, включая автора |
| ReadHistory(cursor, maxCount) | History с ограниченной страницей, курсором, HasGap и HasMore |

OperationId — внутренняя корреляция. Все ChannelReply содержат ChannelId и идут
в один ReliableAgentRef, заданный при старте. Это сохраняет порядок между снимком
входа и последующими публикациями. SessionRegistry уже обрабатывает вход/выход
в этом порядке. Публикации пока не подключены: при добавлении SendChat реестр
будет сопоставлять OperationId с RequestId, возвращать автору ChatAccepted,
остальным — ChatPublished.
Отдельного локального сообщения для автора нет. Сам ChatAgent пакеты не рассылает.

Publish принимает уже составленный сервером ChatMessage. Привязка автора к живой
сессии, назначение ID/времени и проверка права входа в канал принадлежат вызывающему
серверному компоненту и ещё не подключены. При общей выдаче ID владелец должен
сохранять их порядок при отправке команд в каждый канал. ChatAgent использует
проверки Domain.Chat: другой канал, отсутствие участника или невозрастающий ID
дают DomainError без изменения истории. Текст и профиль повторно не валидируются.
OperationId не обеспечивает дедупликацию команд. Профиль автора хранится в сообщении
и сохраняется в истории после его выхода.

При заполненном output обработчик асинхронно ждёт место; следующие команды
ограничены MailboxCapacity. Фоновые отправки не накапливаются. Complete дренирует
принятые команды и ответы; Abort отменяет ожидание и отбрасывает остаток.
Если отправка обнаружила закрытый output, канал вызывает Abort: продолжать работу
без единственного получателя результатов нельзя. Владелец наблюдает Completion.
Само помещение ответа в очередь ещё не подтверждает его обработку или доставку
клиентам. Остановка не откатывает уже выполненную команду.

Владелец output должен продолжать читать свой mailbox при отправке команд каналу:
циклическое ожидание двух заполненных очередей приведёт к зависанию. Он должен
обрабатывать Full либо использовать ограниченные фоновые отправки с результатами
в mailbox, а не ждать ответ внутри собственного обработчика.

Повторный Join идемпотентен по участникам и возвращает свежий снимок. SessionRegistry
отсекает устаревшие ответы через OperationId и удерживает имя до завершения Leave;
старое соединение не может удалить участника после повторного входа.
Перезапуск канала создаёт пустую историю и состав участников; автоматического
восстановления и wire-пагинации пока нет.

## Агент игрока

`PlayerAgent.start mailboxCapacity maxPendingEvents request profiles output`
возвращает обычный `Agent<PlayerMessage>`. Реестр создаёт его для каждого входящего
соединения, до разрешения профиля. Вход проходит Resolving → Joining → Active.
Игрок сам обращается к GetOrCreate, сопоставляет OperationId и создаёт Domain.Player.
Позиция, локация, персонаж и Actor Values принадлежат только этому агенту.
Реестр получает неизменяемый профиль для общего онлайна, но не копию Player.

PlayerEvent.Join просит реестр добавить игрока в канал. PlayerMessage.Joined
подтверждает членство; при начавшемся отключении игрок запрашивает Leave.
После Left персональный агент завершает работу. Реестр обрабатывает ответы канала
в исходном порядке: сам фиксирует онлайн и SessionOpened, затем уведомляет игрока.
Дополнительный ответ Ready от игрока не нужен и не может переставить bootstrap
относительно событий других сессий.

PlayerUpdate уже позволяет передать валидированные доменные изменения:
BeginCharacter, RenameCharacter, SetLocation/ClearLocation, SetActorValues,
LeaveGame. PlayerMessage.Read возвращает самостоятельный PlayerSnapshot.
Смена персонажа и выход из игры очищают положение и Actor Values через Domain.Player.
До готовности обновления не применяются, чтение возвращает NotReady; при закрытии —
Closed. Это внутренний API для будущего адаптера; wire-контракт показаний не добавлен.

Одна операция профиля ожидается через PipeToSelf, поэтому заполненное хранилище
не останавливает обработчик игрока. Его выход в реестр также имеет ограниченную
очередь и одну выполняющуюся отправку. При Stop во время Resolving агент отменяется:
уже принятый GetOrCreate может сохранить профиль, но больше не создаст членство.
Во время Joining/Active выполняется согласованный выход из канала.

## Реестр сессий

`SessionRegistry.start config globalId profiles output` возвращает обычный Agent.
Реестр хранит резервирование PlayerId, адреса/жизненный цикл игроков, неизменяемые
профили участников и ожидаемые операции членства. Персонального автомата поиска
профиля, общего профильного outbox и изменяемого Player в нём нет.

| Настройка | Что ограничивает |
|---|---|
| MailboxCapacity | Входную очередь реестра |
| MaxSessions | Игроков, включая входящие и завершающиеся сессии |
| PlayerMailboxCapacity | Входную очередь каждого PlayerAgent |
| MaxPendingPerPlayer | Каждую очередь реестр → игрок и игрок → реестр, а также незавершённые чтения состояния |
| MaxPendingChannelRequests | Отправки в канал и число операций, ожидающих его ответа |
| MaxPendingOutput | Очередь адресованных результатов для сетевого владельца |

Все лимиты положительные. MaxPendingOutput должен быть больше MaxSessions:
один обработчик может сформировать Failed и закрытие каждого соединения. Лимит
учитывает и отправку, ожидающую допуска. При сборке сервера MaxSessions также
должен укладываться в MaxInitialPlayers, а история — в MaxRecentMessages и бюджет
пакета. Эти настройки поступают от внешней сборки; загрузчика конфигурации ещё нет.

Владелец запускает хранилище, реестр, затем ChatAgent с выходом
`registry.Ref.Map(SessionRegistryMessage.ChannelReplied).TryReliable()` и отправляет
BindChannel. После привязки передаёт Open/Disconnect. ConnectionId — новый Guid
на соединение, независимо от индекса peer. Данные Open уже проверены codec.
До привязки вход закрывается; повторная привязка работающего канала — ошибка сборки.

После ответа GetOrCreate реестр резервирует PlayerId перед отправкой Join.
Резерв удерживается до завершения PlayerAgent и очистки его членства. Повторный Open
того же соединения или другое соединение с занятым PlayerId получает
SessionAlreadyOpen. Во втором случае соединение закрывается, агент отменяется без
Join/Leave: он не владеет членством уже вошедшего игрока. До разрешения профиля
имена не резервируются; уникальность Username принадлежит хранилищу. Существующий офлайн-профиль используется повторно без
смены DisplayName. Это Dev-идентификация, без подтверждения владения именем.

Ожидания разделены: каждый игрок отправляет запрос профиля независимо, канал имеет
свою FIFO, каждый игрок — отдельную очередь входящих команд, сетевой выход — свою.
AgentOutbox запускает отправку через PipeToSelf и ждёт её завершения сообщением.
Ни один обработчик реестра не ждёт допуска в чужой mailbox. Заполненное хранилище
не задерживает Leave другого игрока, заполненный сетевой выход не мешает читать
Disconnect/Stop, пока хватает явно ограниченной очереди результатов.

Переполнение персональной очереди закрывает только игрока. Чтения, которые ещё
не закончились, завершаются Closed при его отключении/падении; превышение лимита
чтений даёт Busy. Переполнение общего канала — ошибка сервиса. Переполнение либо
закрытие общего выхода вызывает Abort реестра; сетевой владелец обязан закрывать
соединения и при завершении Completion, не полагаясь только на сообщения Close.

UpdatePlayer маршрутизирует доменное обновление персональному агенту, ReadPlayer —
запрос снимка. Порядок команд одного игрока сохраняется. SessionOutput.Send содержит
ConnectionId и ChatResponse, Close требует закрыть соединение. PlayerFailed несёт
ошибку конкретного игрока, Failed — отказ общей зависимости или инфраструктуры.
Ошибка GetOrCreate не закрывает остальных игроков; падение ребёнка наблюдается
реестром через Completion и также изолируется с очисткой членства.

Онлайн меняется при обработке Joined/Left из единого выхода канала. SessionOpened
и последующие PlayerJoined/PlayerLeft проходят одну FIFO результатов. Отключённый
до завершения Join игрок не объявляется онлайн. Поздний Joined приводит к Leave;
неожиданное завершение ребёнка также запускает очистку. Старый ConnectionId не может
удалить участника нового соединения. OperationId отсеивает старые ответы, но не
реализует дедупликацию пользовательских команд по RequestId.

## Границы дальнейшего расширения

Реестр пока совмещает жизненный цикл сессий с упорядочиванием глобального онлайна.
Выделение PlayerAgent добавило наблюдение за детьми, ограниченные доставки и
завершение чтений при отказе; само по себе оно не сокращает объём координатора.
Эти механизмы не должны дублироваться для каждой новой игровой возможности.

Группы и гильдии должны иметь отдельных владельцев членства и своих правил,
адресуемых по GroupId/GuildId и работающих с PlayerId. Их команды и ожидаемые
операции не добавляются в SessionRegistry.Pending: эта таблица обслуживает только
вход/выход из глобального канала. Маршрутизацию таких команд выполняет входной
обработчик сервера к нужному владельцу. Согласование группового членства с выходом
игрока потребует отдельного протокола жизненного цикла, а не новых веток здесь.

При появлении нескольких каналов сборку общего онлайна и bootstrap нужно отделить
от каталога сессий, сохранив единый порядок снимка и последующих событий. Сейчас
новый агент ради переноса этих функций не вводится.

## Остановка и общие зависимости

Для штатной остановки используется Stop, затем Completion. Реестр останавливает
игроков, ждёт выхода из канала и завершения детей, дренирует результаты и только
тогда вызывает Complete. Вызывать Complete напрямую при живых детях нельзя:
он закрывает ответы, но не отменяет фоновые наблюдатели Completion.

Наблюдатель каждого ребёнка связывает Abort реестра с child.Abort() и продолжает
ждать очистку ребёнка. Поэтому Completion реестра включает завершение всех его
игроков. Отмена не откатывает уже принятые команды канала или хранилища.
После аварийного Abort внешний владелец должен остановить/пересоздать канал,
чтобы не сохранить оставшееся членство; это отличается от штатного Stop.

Профили и канал принадлежат внешнему владельцу. Он наблюдает их Completion и
передаёт DependencyStopped при завершении зависимости, включая сбой после допуска
запроса. Такой сигнал закрывает весь реестр. Штатная ошибка операции профиля
передаётся игроку и закрывает только его сессию. При неисправности общего выхода
диагностика может не дойти сообщением; Completion остаётся обязательным сигналом.

Автоматический супервайзер, мониторинг общих зависимостей и дедлайн входа в
запущенном сервере пока не подключены. Stop может ожидать ответа зависимостей;
внешний владелец ограничивает время и вызывает Abort. Хранилище профилей можно
сохранить между штатными перезапусками связки реестр/канал.

## Следующие компоненты

Нужно подключить SendChat: серверные ID/время, подтверждение автору и рассылку.
Предел ожидаемых запросов теперь явный; будущие публикации должны соблюдать его,
а обработчик перегрузки — выдавать отказ конкретной команды до изменения истории.
Затем — ENet и сборка жизненного цикла с наблюдением Completion и дедлайнами.
Запускаемый сервер пока заглушка; сквозной вход из Client.Dev ещё не доступен.
