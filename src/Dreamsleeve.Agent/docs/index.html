01

Start here

#

Dreamsleeve.Agent is a small, in-process execution and state-ownership module for F#. Every agent reads one mailbox and awaits one handler at a time. It uses Task and System.Threading.Channels, targets .NET 10+, and uses the standard F#/.NET dependencies without additional libraries.

Use it when several producers need to coordinate work or state without directly sharing mutable objects. It supplies admission, request/reply, lifecycle and error policy; your commands define the domain protocol.

Build the module and run its examples

Run these commands from the bundle/repository root containing src, examples and tests. Install a .NET 10 SDK first. The test project is an executable regression harness.

Shell
dotnet build src/Dreamsleeve.Agent/Dreamsleeve.Agent.fsproj -c Release
dotnet run --project src/Dreamsleeve.Agent/examples/Dreamsleeve.Agent.Examples.fsproj -c Release
dotnet run --project tests/Dreamsleeve.Server.Tests -c Release -- --filter-test-list Dreamsleeve.Agent

The examples terminate after printing:

Output
outbound: global <- hello
outbound: global <- ready
party: Joined; members=1; leader=Nerevar
presence: snapshot=1; removed=true; current=0

A complete first agent

The caller constructs a command with a one-shot reply channel. The handler replies after doing its work. The default deadline below prevents an unanswered request from waiting forever.

F#
open System
open Dreamsleeve.Agent

type Command = Echo of string * ReplyChannel<string>

let example () = task {
    let options =
        { AgentOptions.create "echo" with
            Mailbox = AgentMailbox.boundedWait 64
            DefaultAskTimeout = Some (TimeSpan.FromSeconds 2.) }

    use agent =
        Agent<Command>.Start(options, fun _ (Echo (text, reply)) -> task {
            reply.Reply text
        })

    let! text = agent.AskAsync(fun reply -> Echo ("hello", reply))
    printfn "%s" text
    agent.Complete() |> ignore
    do! agent.Completion
}
Acceptance and completion are different

PostAsync returning Posted acknowledges mailbox admission. Use Ask with an application-defined acknowledgement when the caller needs to observe processing. An acknowledgement can mean “local processing finished”; remote delivery needs its own protocol.

02

Choose an agent

#

Start with the state and consistency boundary. A party is a useful boundary because membership and leadership must change together. A single presence registry is a practical first implementation; split it only when measured throughput or independent ownership calls for it.

TypeHandler returnsUse it forMain responsibility
Agent<'Message>Task<unit>Outbound operations, save requests, sequential dependency access.Define commands and effect ordering.
StatefulAgent<'State,'Command>Task<StatefulTransition<'State>>Party/guild membership, session FSM, small domain aggregates.Return a new immutable state or keep the old one.
MutableStatefulAgent<'State,'Command>Task<MutableStatefulTransition>Presence dictionaries, indexes and frequently updated counters.Exclusively own the mutable graph and return snapshots.
EffectsOutbound worker →Immutable stateParty commands →Mutable statePresence registry →

StatefulAgent does not make an arbitrary F# type immutable. An immutable record containing a mutable dictionary still contains shared mutable state. Choose immutable collections throughout the reachable graph when you want immutable-state reasoning.

03

Example: sequential effects

#

Agent<OutboundCommand> orders work for an asynchronous dependency. The demonstration dependency only prints a line. Replace it with your own cancellable send/save operation; keep the acknowledgement’s meaning explicit.

The second command has a reply, so the caller can observe its completion without a separate state query. Both commands use the same queue. In this single-producer example, the second handler runs after the first.

Outbound.fs · F#
module Dreamsleeve.Agent.Examples.Outbound

open System
open System.Threading.Tasks
open Dreamsleeve.Agent

type OutboundCommand =
    | Send of recipient: string * text: string
    | SendAndConfirm of recipient: string * text: string * ReplyChannel<unit>

let run () = task {
    let options =
        { AgentOptions.create "outbound" with
            Mailbox = AgentMailbox.boundedWait 32
            DefaultAskTimeout = Some (TimeSpan.FromSeconds 2.) }

    // Replace with an asynchronous dependency that accepts ctx.CancellationToken.
    // This example confirms local processing, not delivery to a remote player.
    let send recipient text =
        printfn "outbound: %s <- %s" recipient text
        Task.CompletedTask

    use agent =
        Agent<OutboundCommand>.Start(options, fun ctx command -> task {
            ctx.CancellationToken.ThrowIfCancellationRequested()
            match command with
            | Send (recipient, text) ->
                do! send recipient text
            | SendAndConfirm (recipient, text, reply) ->
                do! send recipient text
                reply.Reply ()
        })

    let! posted = agent.PostAsync(Send ("global", "hello"))
    match posted with
    | AgentPostResult.Posted -> ()
    | other -> failwithf "Unexpected post result: %A" other

    do! agent.AskAsync(fun reply ->
        SendAndConfirm ("global", "ready", reply))

    agent.Complete() |> ignore
    do! agent.Completion
}

Open runnable source. The agent waits for every handler; starting detached tasks inside a handler would move that work outside its sequencing and lifetime.

04

Example: immutable party

#

Membership checks and updates belong in one command. “Read the roster, then post Join” would permit another command to change the roster between the two operations. A command carrying ReplyChannel<JoinResult> decides and replies inside one serialized handler.

Expected domain rejections are normal results such as PartyFull. Reserve unhandled exceptions for unexpected failures. The immutable record uses a Set for membership and a list for joining order; if the leader leaves, the longest-standing remaining member takes over. Its immutable graph is safe to return through ReadAsync id.

Party.fs · F#
module Dreamsleeve.Agent.Examples.Party

open System
open Dreamsleeve.Agent

type PartyState =
    { Leader: string option
      Members: Set<string>
      JoinedOrder: string list }

type JoinResult = Joined | AlreadyMember | PartyFull

type PartyCommand =
    | Join of player: string * ReplyChannel<JoinResult>
    | Leave of player: string

let run () = task {
    let options =
        { StatefulAgentOptions.create "party-42" with
            AgentOptions =
                { AgentOptions.create "party-42" with
                    Mailbox = AgentMailbox.boundedWait 32
                    DefaultAskTimeout = Some (TimeSpan.FromSeconds 2.) } }

    let initial = { Leader = None; Members = Set.empty; JoinedOrder = [] }
    use party =
        StatefulAgent<PartyState, PartyCommand>.Start(
            options, initial, fun _ state command -> task {
                match command with
                | Join (player, reply) when Set.contains player state.Members ->
                    reply.Reply AlreadyMember
                    return StatefulTransition.Stay
                | Join (_, reply) when state.Members.Count >= 4 ->
                    reply.Reply PartyFull
                    return StatefulTransition.Stay
                | Join (player, reply) ->
                    let next =
                        { Leader = state.Leader |> Option.orElse (Some player)
                          Members = Set.add player state.Members
                          JoinedOrder = state.JoinedOrder @ [ player ] }
                    reply.Reply Joined
                    return StatefulTransition.SetState next
                | Leave player ->
                    let members = Set.remove player state.Members
                    let joinedOrder = state.JoinedOrder |> List.filter ((<>) player)
                    let leader =
                        match state.Leader with
                        | Some current when Set.contains current members -> Some current
                        | _ -> List.tryHead joinedOrder
                    return StatefulTransition.SetState
                        { Leader = leader; Members = members; JoinedOrder = joinedOrder }
            })

    let! result = party.AskAsync(fun reply -> Join ("Nerevar", reply))
    // The queued query executes after the command and its state transition.
    let! snapshot = party.ReadAsync id
    printfn "party: %A; members=%d; leader=%s"
        result snapshot.Members.Count (defaultArg snapshot.Leader "none")

    party.Complete() |> ignore
    do! party.Completion
}
A reply is not a transaction commit

Reply is immediately observable. Put it at the end of the handler’s effects. In this example, a subsequent queued Read runs after the returned SetState is applied. There is no automatic rollback, distributed transaction or implicit “reply after every remaining effect” guarantee.

Open runnable source. Extend the command union with leader transfer or invitations when those rules are needed; keep validation and the related state change together.

05

Example: presence snapshots

#

A private dictionary can efficiently serve frequent presence updates. The agent owns the dictionary and all access to it. Commands write in place; queries construct independent snapshots for an online table, broadcast batch or the game’s wisp presentation.

The example intentionally uses a bounded Wait mailbox. Lossy channel modes can also drop reads or remove commands. They do not implement “keep the latest state for each player.” Add explicit keyed coalescing at the domain boundary if that is later required.

Presence.fs · F#
module Dreamsleeve.Agent.Examples.Presence

open System
open System.Collections.Generic
open Dreamsleeve.Agent

type PlayerPresence =
    { PlayerId: uint64
      Location: string
      X: float32
      Y: float32
      Z: float32
      Health: int }

type PresenceCommand =
    | Upsert of PlayerPresence
    | Remove of playerId: uint64 * ReplyChannel<bool>

let run () = task {
    let options =
        { MutableStatefulAgentOptions.create "presence" with
            AgentOptions =
                { AgentOptions.create "presence" with
                    Mailbox = AgentMailbox.boundedWait 128
                    DefaultAskTimeout = Some (TimeSpan.FromSeconds 2.) } }

    // The dictionary belongs exclusively to the agent from this point onward.
    use presence =
        MutableStatefulAgent<Dictionary<uint64, PlayerPresence>, PresenceCommand>.Start(
            options, Dictionary<uint64, PlayerPresence>(),
            fun _ players command -> task {
                match command with
                | Upsert player -> players[player.PlayerId] <- player
                | Remove (playerId, reply) -> reply.Reply(players.Remove playerId)
                return MutableStatefulTransition.Stay
            })

    let! posted =
        presence.PostAsync(Upsert
            { PlayerId = 7UL; Location = "Balmora"
              X = 10.f; Y = 2.f; Z = 0.f; Health = 100 })
    match posted with
    | AgentPostResult.Posted -> ()
    | other -> failwithf "Unexpected post result: %A" other

    // Materialize INSIDE the agent: no live Dictionary/Values/seq escapes.
    // Each element is immutable, and the returned array is an independent copy.
    let! snapshot =
        presence.ReadAsync(fun players ->
            players.Values
            |> Seq.sortBy (fun player -> player.PlayerId)
            |> Seq.toArray)

    let! removed = presence.AskAsync(fun reply -> Remove (7UL, reply))
    let! count = presence.ReadAsync(fun players -> players.Count)
    printfn "presence: snapshot=%d; removed=%b; current=%d"
        snapshot.Length removed count

    presence.Complete() |> ignore
    do! presence.Completion
}
Materialize before crossing the boundary

Returning players.Values, a lazy seq, or the dictionary itself leaks a live view. Seq.toArray runs inside the projection here. Its elements are immutable records; if they contained mutable arrays or objects, those would also need copying.

Open runnable source. A failed mutable command may leave partial mutations. Validate before mutation where practical; choose Continue only when state invariants remain intact.

06

Mailboxes and backpressure

#

AgentOptions.create name defaults to an unbounded mailbox, no Ask deadline, SingleWriter = false, disabled synchronous continuations and no callbacks. Production callers should choose capacity and deadlines deliberately.

ConfigurationWhen the queue is fullSuitable use
AgentMailbox.unboundedAdmission does not wait for capacity. Memory can grow with backlog.Known bounded upstream load or short controlled workloads.
AgentMailbox.boundedWait nTryPost → Full; PostAsync waits asynchronously.Commands where loss is unacceptable; the default choice for these examples.
bounded n DropWriteDiscards the incoming item. Its post result is Dropped.Explicitly disposable incoming work.
bounded n DropOldestEvicts the oldest queued item to admit the new one.A global stream where old buffered work is dispensable.
bounded n DropNewestEvicts the newest already-queued item to admit the new one.Specialized policies; this does not mean dropping the incoming item.

Use open System.Threading.Channels for BoundedChannelFullMode. Capacity must be positive. Drop policies affect queued items; they do not cancel the handler already running.

Observe admission honestly

Post resultMeaning
PostedAccepted at this write. It may still be evicted later on a lossy mailbox, or discarded by abort/fault.
FullImmediate post could not obtain capacity in a bounded Wait mailbox.
DroppedThis incoming write was discarded by the mailbox’s drop policy.
ClosedNo longer accepting messages.
CanceledThe caller canceled asynchronous admission.

QueueLength is an observational snapshot of queued envelopes, including queries; it excludes the active handler and waiting producers. DroppedCount counts loss from mailbox drop policies. Never use either as a check-then-post synchronization mechanism. Shutdown-discarded work is not a channel-drop event.

Capacity alone does not bound all memory

Launching unlimited unawaited PostAsync calls merely moves the backlog into waiting producers and tasks. Await posts, bound producer concurrency, or define an explicit overflow policy. SingleWriter = true promises no concurrent writers; self-posts count too, and one logical writer does not require one fixed OS thread.

07

Requests, replies and timeouts

#

All three agents support TryAskAsync / AskAsync. Both stateful variants additionally expose TryReadAsync / ReadAsync; a read is a projection queued among commands, so it observes state at its position in the mailbox. It is not a direct read of a public state field.

APIBehavior
TryPost messageImmediate admission attempt returning AgentPostResult.
PostAsync(message, cancellationToken = token)Asynchronous admission, returning AgentPostResult.
TryAskAsync(buildMessage, timeout = span, cancellationToken = token)Admit a request and await a typed operational result. “Try” does not mean a nonwaiting capacity check.
AskAsync(...)Return the reply value; throw for unsuccessful outcomes.
TryReadAsync(projection, ...) / ReadAsync(...)Project state in queue order; same timeout/result rules as Ask.

One deadline covers the complete request

The effective timeout starts before admission and covers capacity waiting plus reply waiting. An explicit timeout overrides DefaultAskTimeout. None means no default deadline; Timeout.InfiniteTimeSpan explicitly chooses an unlimited wait. Zero returns TimedOut without constructing or enqueueing a message. Unsupported negative or out-of-range timeouts are rejected before request side effects.

buildMessage is synchronous caller-side code. Keep it fast and side-effect free: no timeout can preempt a blocked synchronous builder. If timeout cancellation has been observed before admission, its command is not admitted.

F#
let! result = agent.TryAskAsync(
    (fun reply -> Echo ("hello", reply)),
    timeout = TimeSpan.FromSeconds 1.)

match result with
| AgentAskResult.Replied text -> printfn "%s" text
| AgentAskResult.TimedOut -> printfn "Request deadline expired"
| AgentAskResult.Canceled -> printfn "Caller stopped waiting"
| AgentAskResult.Dropped -> printfn "Mailbox discarded this request"
| AgentAskResult.Closed -> printfn "Agent is closed"
| AgentAskResult.Full -> printfn "No capacity"
| AgentAskResult.Faulted error -> printfn "Request failed: %s" error.Message
Ask resultMeaning / throwing API
Replied valueThe one-shot reply supplied a value.
Faulted errorValidation, builder, projection, reply, handler or terminal agent failure; throwing API propagates the error.
TimedOutEnd-to-end request deadline expired; TimeoutException.
CanceledCaller stopped waiting or reply was canceled; OperationCanceledException.
DroppedThe request was discarded by a lossy mailbox; InvalidOperationException.
ClosedRequest could not be accepted/completed because the agent closed; InvalidOperationException.
FullCapacity refusal result retained in the contract; ordinary asynchronous Wait admission waits instead. InvalidOperationException.
Timeout is not command rollback

A command already accepted can execute after the caller receives TimedOut or Canceled. Caller cancellation does not cancel the agent’s lifetime token. Use command IDs and idempotent domain operations where retries could duplicate effects; define explicit cancellation commands if the domain needs them.

The reply channel is one-shot

TryReply, TryReplyError and TryCancel return whether they won completion; the corresponding methods without “Try” ignore a losing attempt. The runtime also settles requests on timeout, loss and shutdown. IsCompleted can help avoid optional stale work, but it is an observation, not a lock or cancellation proof.

The first request settlement wins. A reply racing with timeout/abort notification can still produce Replied; there is no wall-clock ordering guarantee across threads. After Ask has returned an unsuccessful result, later replies are rejected.

A reply may be deferred beyond the handler’s return; therefore a handler that simply forgets to reply can still wait indefinitely without a deadline. If the handler replies and then throws, the first reply wins while normal error reporting/policy still runs.

08

Lifecycle and shutdown

#

Start immediately schedules the processing loop. Complete and Abort request a lifecycle change; Completion observes when the loop and terminal cleanup have actually finished.

OperationNew messagesBuffered messagesCompletion
Complete()RejectedDrained normallySuccessful: Completed, unless processing later aborts/faults.
Normal Stop / StopWithState transitionRejectedDrained normallySame graceful path as Complete.
Error policy StopRejectedDiscardedFaulted: Faulted error.
Abort()RejectedDiscardedCanceled: Aborted.
IDisposable.Dispose()RejectedAbort semanticsRequests abort; does not await termination.
IAsyncDisposable.DisposeAsync()RejectedComplete semanticsAwaits termination; can propagate cancellation/failure.
Graceful Stop does not make a final state immutable

StatefulTransition.StopWithState next applies next and closes admission, then processes previously accepted commands. Those commands can change the state again. Choose Abort for a cooperative stop without draining; define a separate domain “closed” state if later accepted commands must become no-ops.

Abort cannot forcibly terminate arbitrary user code. Pass ctx.CancellationToken to cancellable I/O and delays. The current handler must return before termination completes. A noncooperative handler can keep Completion pending; a graceful drain can also wait on long-running work.

F#
agent.Complete() |> ignore
try
    do! agent.Completion
with
| :? OperationCanceledException -> printfn "Aborted"
| error -> printfn "Faulted: %s" error.Message

After termination, StopReason, the stopped notifications and Completion describe the same outcome. Queue references are cleared before completion is published. Discarding a message does not automatically dispose arbitrary resources inside it; define payload ownership and release behavior in the application protocol.

Keep OnStopped and event handlers short. Completion is published after terminal cleanup and stopped callbacks, so a callback must not wait on its own agent’s Completion. The use examples explicitly complete and await on their successful path; scope disposal requests abort if an earlier operation fails.

09

Errors and observability

#

The default policy stops an agent on an unhandled handler exception. It reports Errored, fails the current request if it is still pending, discards queued work and publishes a faulted completion. Selecting Continue changes the lifecycle decision; it does not turn the failed Ask into success.

Agent kindPolicy hookChoices
BaseAgentOptions.OnError(name, error)Continue or Stop.
Immutable stateOnUnhandled(state, error)KeepStateAndContinue, ReplaceStateAndContinue s, Stop, StopWithState s.
Mutable stateOnUnhandled(state, error)Continue or Stop. No automatic rollback.

A state wrapper’s explicit OnUnhandled takes precedence over AgentOptions.OnError. When absent, the base policy is used; when both are absent, the agent stops. A policy callback that throws also causes stopping. Query-projection exceptions fault that query rather than being command failures that stop the agent.

F#
let options =
    { StatefulAgentOptions.create "party" with
        AgentOptions =
            { AgentOptions.create "party" with
                Mailbox = AgentMailbox.boundedWait 64
                OnStarted = Some (fun name -> printfn "Started %s" name)
                OnStopped = Some (fun (name, reason) ->
                    printfn "Stopped %s: %A" name reason) }
        OnUnhandled = Some (fun (_state, error) ->
            eprintfn "Party failure: %s" error.Message
            StatefulErrorAction.Stop) }

Events are observations

Started, Errored and Stopped are live notifications. Since the agent starts before Start returns, a subsequent Started.Add subscription may miss startup. Configure OnStarted before Start when it matters. The same no-replay principle applies to late subscriptions to terminal events; inspect Completion / StopReason for current terminal status.

OnTransition runs after state replacement and receives the previous/new state. It is an observation hook, not a transactional validation stage. Do not mutate those state objects or launch untracked work that later mutates them. Lifecycle/transition observation callbacks should not throw or block; their exceptions are isolated from agent processing.

Observe Completion from the owning service so failures reach logs and shutdown logic. No supervisor or automatic restart is supplied: a restart policy must decide what happens to state, pending work, native resources and duplicated side effects.

10

Ownership and server integration

#

Sequential handlers do not mean a dedicated thread

The loop awaits each handler before reading the next message. Its continuations can run on different pool threads. allowSynchronousContinuations = true may also cause continuation work to run on a completing producer’s thread. It is an advanced scheduling choice, not a thread-affinity guarantee.

For Dreamsleeve, keep ENet host/service/send ownership explicit. An agent can serialize access if every operation goes through that ownership boundary; it does not by itself guarantee a dedicated native pump thread. If your native integration requires a fixed OS thread, create and own that pump separately, exchanging commands and owned data with the domain agents.

A practical first split

ResponsibilitySuggested boundaryCross-boundary data
Network transportExplicit host/pump owner; bounded inbound/outbound queues.Owned packet bytes or decoded messages; never a borrowed span past its owner’s lifetime.
Global chatOne sequential domain owner at first.Validated chat commands and immutable accepted-message events.
PresenceMutable dictionary agent.Player-state updates and independent snapshot batches.
Party/guild rulesImmutable stateful agent per chosen aggregate.Join/leave/invite commands with explicit results.
UI / game presentationIts own update/render owner.Snapshots for the online table and wisps; no live actor dictionaries.

Keep waits acyclic

  • Do not await Ask/Read to the same agent from its current handler: the query needs the consumer already occupied by that handler.
  • Do not await self-PostAsync if a bounded mailbox can be full. ctx.TryPost with explicit Full handling is one option for a base agent; an explicit next-iteration command design is another.
  • A asks B while B asks A can also deadlock. Prefer a directed request flow, asynchronous replies, or a coordinating owner.
  • Do not synchronously block on asynchronous work with .Result / .Wait() inside handlers or callbacks.

The module does not add periodic timers, priority scheduling, durable mailboxes, automatic coalescing or distributed delivery. A timer producer can post ticks, but should also define what happens to accumulated ticks when the consumer falls behind.

01

Начало работы

#

Dreamsleeve.Agent — небольшой модуль F# для выполнения работы и владения состоянием внутри процесса. Каждый агент читает одну очередь и ожидает завершения одного обработчика за раз. Основа — Task и System.Threading.Channels; целевая платформа .NET 10+, используются стандартные зависимости F#/.NET без дополнительных библиотек.

Он полезен, когда несколько отправителей должны согласованно выполнять работу или изменять состояние без прямого доступа к общим изменяемым объектам. Модуль предоставляет очередь, запросы с ответом, жизненный цикл и политику ошибок; доменный протокол задают твои команды.

Первый агент целиком

Вызывающий код создаёт команду с одноразовым каналом ответа. Обработчик отвечает после выполнения работы. Дедлайн по умолчанию в примере ограничивает ожидание запроса, на который не пришёл ответ.

F#
open System
open Dreamsleeve.Agent

type Command = Echo of string * ReplyChannel<string>

let example () = task {
    let options =
        { AgentOptions.create "echo" with
            Mailbox = AgentMailbox.boundedWait 64
            DefaultAskTimeout = Some (TimeSpan.FromSeconds 2.) }

    use agent =
        Agent<Command>.Start(options, fun _ (Echo (text, reply)) -> task {
            reply.Reply text
        })

    let! text = agent.AskAsync(fun reply -> Echo ("hello", reply))
    printfn "%s" text
    agent.Complete() |> ignore
    do! agent.Completion
}
Приём сообщения и завершение обработки различаются

Результат Posted у PostAsync подтверждает приём в очередь. Если нужно дождаться обработки, используй Ask с явно определённым подтверждением. Оно может означать «локальная обработка закончена»; доставка удалённому участнику требует отдельного протокола.

02

Какого агента выбрать

#

Начни с границы состояния и согласованности. Партия — удобная граница: членство и лидерство должны изменяться вместе. Один реестр присутствия подходит для первой реализации; разделять его стоит при измеренной нагрузке или появлении независимых владельцев данных.

03

Пример: последовательные действия

#

Agent<OutboundCommand> упорядочивает работу с асинхронной зависимостью. В демонстрации зависимость только печатает строку. Замени её своим отменяемым действием отправки/сохранения и явно определи смысл подтверждения.

Вторая команда содержит канал ответа: вызывающий код наблюдает её завершение без отдельного чтения состояния. Обе команды используют одну очередь. В этом примере с одним отправителем второй обработчик выполняется после первого.

Outbound.fs · F#
module Dreamsleeve.Agent.Examples.Outbound

open System
open System.Threading.Tasks
open Dreamsleeve.Agent

type OutboundCommand =
    | Send of recipient: string * text: string
    | SendAndConfirm of recipient: string * text: string * ReplyChannel<unit>

let run () = task {
    let options =
        { AgentOptions.create "outbound" with
            Mailbox = AgentMailbox.boundedWait 32
            DefaultAskTimeout = Some (TimeSpan.FromSeconds 2.) }

    // Replace with an asynchronous dependency that accepts ctx.CancellationToken.
    // This example confirms local processing, not delivery to a remote player.
    let send recipient text =
        printfn "outbound: %s <- %s" recipient text
        Task.CompletedTask

    use agent =
        Agent<OutboundCommand>.Start(options, fun ctx command -> task {
            ctx.CancellationToken.ThrowIfCancellationRequested()
            match command with
            | Send (recipient, text) ->
                do! send recipient text
            | SendAndConfirm (recipient, text, reply) ->
                do! send recipient text
                reply.Reply ()
        })

    let! posted = agent.PostAsync(Send ("global", "hello"))
    match posted with
    | AgentPostResult.Posted -> ()
    | other -> failwithf "Unexpected post result: %A" other

    do! agent.AskAsync(fun reply ->
        SendAndConfirm ("global", "ready", reply))

    agent.Complete() |> ignore
    do! agent.Completion
}

Открыть запускаемый исходник. Агент ожидает каждый обработчик; отделённые задачи, запущенные внутри него, выходят за пределы этой последовательности и жизненного цикла.

04

Пример: неизменяемая партия

#

Проверка членства и изменение состава должны находиться в одной команде. Схема «прочитать состав, затем отправить Join» допускает изменение состава другой командой между этими действиями. Команда с ReplyChannel<JoinResult> принимает решение и отвечает внутри одного последовательного обработчика.

Ожидаемые доменные отказы — обычные результаты, например PartyFull. Необработанные исключения оставь неожиданным сбоям. Неизменяемая запись использует Set для членства и список для порядка вступления; при уходе лидера его место занимает самый давний из оставшихся участников. Такой неизменяемый граф безопасно возвращать через ReadAsync id.

Party.fs · F#
module Dreamsleeve.Agent.Examples.Party

open System
open Dreamsleeve.Agent

type PartyState =
    { Leader: string option
      Members: Set<string>
      JoinedOrder: string list }

type JoinResult = Joined | AlreadyMember | PartyFull

type PartyCommand =
    | Join of player: string * ReplyChannel<JoinResult>
    | Leave of player: string

let run () = task {
    let options =
        { StatefulAgentOptions.create "party-42" with
            AgentOptions =
                { AgentOptions.create "party-42" with
                    Mailbox = AgentMailbox.boundedWait 32
                    DefaultAskTimeout = Some (TimeSpan.FromSeconds 2.) } }

    let initial = { Leader = None; Members = Set.empty; JoinedOrder = [] }
    use party =
        StatefulAgent<PartyState, PartyCommand>.Start(
            options, initial, fun _ state command -> task {
                match command with
                | Join (player, reply) when Set.contains player state.Members ->
                    reply.Reply AlreadyMember
                    return StatefulTransition.Stay
                | Join (_, reply) when state.Members.Count >= 4 ->
                    reply.Reply PartyFull
                    return StatefulTransition.Stay
                | Join (player, reply) ->
                    let next =
                        { Leader = state.Leader |> Option.orElse (Some player)
                          Members = Set.add player state.Members
                          JoinedOrder = state.JoinedOrder @ [ player ] }
                    reply.Reply Joined
                    return StatefulTransition.SetState next
                | Leave player ->
                    let members = Set.remove player state.Members
                    let joinedOrder = state.JoinedOrder |> List.filter ((<>) player)
                    let leader =
                        match state.Leader with
                        | Some current when Set.contains current members -> Some current
                        | _ -> List.tryHead joinedOrder
                    return StatefulTransition.SetState
                        { Leader = leader; Members = members; JoinedOrder = joinedOrder }
            })

    let! result = party.AskAsync(fun reply -> Join ("Nerevar", reply))
    // The queued query executes after the command and its state transition.
    let! snapshot = party.ReadAsync id
    printfn "party: %A; members=%d; leader=%s"
        result snapshot.Members.Count (defaultArg snapshot.Leader "none")

    party.Complete() |> ignore
    do! party.Completion
}
Ответ не означает коммит транзакции

Reply становится доступен вызывающему коду сразу. Помещай его в конец эффектов обработчика. В примере следующий запрос Read выполняется после применения возвращённого SetState. Автоматического отката, распределённой транзакции и обещания «ответ только после всех оставшихся действий» здесь нет.

Открыть запускаемый исходник. Добавляй команды передачи лидерства и приглашений по мере появления правил; проверка и связанное изменение состояния должны оставаться вместе.

05

Пример: снимки присутствия

#

Закрытый словарь удобен для частых обновлений присутствия. Агент владеет словарём и всем доступом к нему. Команды меняют данные на месте; запросы создают независимые снимки для таблицы онлайна, пакета рассылки или отображения светлячков в игре.

В примере намеренно выбрана ограниченная очередь Wait. Режимы с потерями могут удалить запрос чтения или команду удаления игрока. Они не реализуют правило «хранить последнее состояние каждого игрока». Если это понадобится, добавь явное объединение обновлений по ключу на доменной границе.

Presence.fs · F#
module Dreamsleeve.Agent.Examples.Presence

open System
open System.Collections.Generic
open Dreamsleeve.Agent

type PlayerPresence =
    { PlayerId: uint64
      Location: string
      X: float32
      Y: float32
      Z: float32
      Health: int }

type PresenceCommand =
    | Upsert of PlayerPresence
    | Remove of playerId: uint64 * ReplyChannel<bool>

let run () = task {
    let options =
        { MutableStatefulAgentOptions.create "presence" with
            AgentOptions =
                { AgentOptions.create "presence" with
                    Mailbox = AgentMailbox.boundedWait 128
                    DefaultAskTimeout = Some (TimeSpan.FromSeconds 2.) } }

    // The dictionary belongs exclusively to the agent from this point onward.
    use presence =
        MutableStatefulAgent<Dictionary<uint64, PlayerPresence>, PresenceCommand>.Start(
            options, Dictionary<uint64, PlayerPresence>(),
            fun _ players command -> task {
                match command with
                | Upsert player -> players[player.PlayerId] <- player
                | Remove (playerId, reply) -> reply.Reply(players.Remove playerId)
                return MutableStatefulTransition.Stay
            })

    let! posted =
        presence.PostAsync(Upsert
            { PlayerId = 7UL; Location = "Balmora"
              X = 10.f; Y = 2.f; Z = 0.f; Health = 100 })
    match posted with
    | AgentPostResult.Posted -> ()
    | other -> failwithf "Unexpected post result: %A" other

    // Materialize INSIDE the agent: no live Dictionary/Values/seq escapes.
    // Each element is immutable, and the returned array is an independent copy.
    let! snapshot =
        presence.ReadAsync(fun players ->
            players.Values
            |> Seq.sortBy (fun player -> player.PlayerId)
            |> Seq.toArray)

    let! removed = presence.AskAsync(fun reply -> Remove (7UL, reply))
    let! count = presence.ReadAsync(fun players -> players.Count)
    printfn "presence: snapshot=%d; removed=%b; current=%d"
        snapshot.Length removed count

    presence.Complete() |> ignore
    do! presence.Completion
}
Материализуй данные до выхода из агента

Возврат players.Values, ленивого seq или самого словаря раскрывает живое представление. Здесь Seq.toArray выполняется внутри проекции. Элементы — неизменяемые записи; если бы они содержали изменяемые массивы или объекты, их тоже пришлось бы копировать.

Открыть запускаемый исходник. Неуспешная команда может оставить частичные изменения. По возможности проверяй данные до изменения состояния; выбирай Continue, только если инварианты состояния сохраняются.

06

Очереди и обратное давление

#

AgentOptions.create name по умолчанию создаёт неограниченную очередь, не задаёт дедлайн Ask, использует SingleWriter = false, отключает синхронные продолжения и не устанавливает callbacks. Для рабочего сервера ёмкость и дедлайны нужно выбирать явно.

КонфигурацияЕсли очередь заполненаПрименение
AgentMailbox.unboundedПриём не ждёт свободного места. Память растёт вместе с накопленной работой.Заведомо ограниченный входной поток или короткие контролируемые задачи.
AgentMailbox.boundedWait nTryPost → Full; PostAsync асинхронно ожидает место.Команды, которые нельзя терять; основной выбор в примерах.
bounded n DropWriteУдаляется поступающее сообщение. Результат его публикации — Dropped.Входящая работа, потеря которой явно допустима.
bounded n DropOldestУдаляется самое старое сообщение из очереди, новое принимается.Общий поток, где старые ожидающие элементы можно потерять.
bounded n DropNewestУдаляется самое новое из уже ожидающих сообщений, новое принимается.Специальные политики; это не удаление поступающего сообщения.

Для BoundedChannelFullMode нужен open System.Threading.Channels. Ёмкость должна быть положительной. Drop-политики затрагивают очередь и не отменяют уже работающий обработчик.

Точный смысл результата публикации

Результат PostЗначение
PostedПринято при этой записи. Позже сообщение может быть вытеснено из очереди с потерями или отброшено при abort/сбое.

DroppedИменно это поступающее сообщение удалено политикой очереди.

QueueLength — наблюдаемый снимок числа конвертов в очереди, включая запросы; активный обработчик и ожидающие отправители в него не входят. DroppedCount считает потери от drop-политик очереди. Ни одно из этих значений нельзя использовать для синхронизации по схеме «проверить, затем опубликовать». Отбрасывание при завершении не является событием channel-drop.

Ёмкость очереди не ограничивает всю память

Бесконечный запуск PostAsync без ожидания лишь переносит накопленную работу в ожидающих отправителей и задачи. Ожидай публикации, ограничивай число отправителей или задавай политику переполнения. SingleWriter = true обещает отсутствие одновременных записей; самопубликации тоже учитываются, а один логический отправитель не требует одного фиксированного потока ОС.

07

Запросы, ответы и таймауты

#

Все три агента поддерживают TryAskAsync / AskAsync. Оба варианта с состоянием также имеют TryReadAsync / ReadAsync: проекция ставится в очередь среди команд и видит состояние в своей позиции. Это не прямое чтение публичного поля состояния.

APIПоведение
TryPost messageНемедленная попытка приёма с результатом AgentPostResult.
PostAsync(message, cancellationToken = token)Асинхронный приём с результатом AgentPostResult.
TryAskAsync(buildMessage, timeout = span, cancellationToken = token)Приём запроса и ожидание типизированного результата. “Try” не означает проверку свободного места без ожидания.
AskAsync(...)Возвращает ответ; неуспешные исходы превращает в исключения.
TryReadAsync(projection, ...) / ReadAsync(...)Читает проекцию состояния в порядке очереди; таймауты и результаты как у Ask.

Один дедлайн на весь запрос

Таймаут начинается до приёма и охватывает ожидание места и ответа. Явный параметр перекрывает DefaultAskTimeout. None означает отсутствие стандартного дедлайна; Timeout.InfiniteTimeSpan явно выбирает неограниченное ожидание. Ноль возвращает TimedOut, не создавая и не ставя сообщение в очередь. Недопустимые отрицательные или слишком большие значения отклоняются до побочных эффектов запроса.

buildMessage — синхронный код на стороне вызывающего. Он должен быть быстрым и не иметь побочных эффектов: таймаут не прерывает заблокированный синхронный конструктор. Если отмена по таймауту уже наблюдается до приёма, команда не будет принята.

F#
let! result = agent.TryAskAsync(
    (fun reply -> Echo ("hello", reply)),
    timeout = TimeSpan.FromSeconds 1.)

match result with
| AgentAskResult.Replied text -> printfn "%s" text
| AgentAskResult.TimedOut -> printfn "Request deadline expired"
| AgentAskResult.Canceled -> printfn "Caller stopped waiting"
| AgentAskResult.Dropped -> printfn "Mailbox discarded this request"
| AgentAskResult.Closed -> printfn "Agent is closed"
| AgentAskResult.Full -> printfn "No capacity"
| AgentAskResult.Faulted error -> printfn "Request failed: %s" error.Message
Результат AskЗначение / API с исключениями
Replied valueОдноразовый канал предоставил ответ.
Faulted errorОшибка валидации, конструктора, проекции, ответа, обработчика или завершения агента; API с исключениями передаёт её вызывающему.
TimedOutИстёк общий дедлайн запроса; TimeoutException.
CanceledВызывающий перестал ждать либо ответ отменён; OperationCanceledException.
DroppedЗапрос удалён очередью с потерями; InvalidOperationException.
ClosedЗапрос нельзя принять/завершить из-за закрытия агента; InvalidOperationException.
FullРезультат отказа по ёмкости сохранён в контракте; обычный асинхронный приём в Wait ожидает место. InvalidOperationException.
Таймаут не откатывает команду

Принятая команда может выполниться после получения вызывающим кодом TimedOut или Canceled. Отмена ожидания не отменяет токен жизненного цикла агента. Если повтор может дублировать эффект, используй идентификаторы команд и идемпотентные доменные операции; при необходимости вводи отдельную команду отмены.

Канал ответа одноразовый

TryReply, TryReplyError и TryCancel возвращают, удалось ли первыми завершить запрос; варианты без “Try” игнорируют проигравшую попытку. Среда также завершает запросы по таймауту, потере и остановке. IsCompleted помогает избежать необязательной устаревшей работы, но остаётся наблюдением, а не блокировкой или доказательством отмены.

Побеждает первое завершение запроса. Ответ, конкурирующий с уведомлением таймаута/abort, всё ещё может дать Replied; хронологический порядок между потоками не гарантируется. После возврата неуспешного результата Ask поздние ответы отклоняются.

Ответ допускается отложить за пределы возврата обработчика; поэтому забытый ответ без дедлайна всё ещё может ожидаться бесконечно. Если обработчик сначала ответил, а затем выбросил исключение, первый ответ сохраняется, а сообщение об ошибке и политика продолжают действовать.

08

Жизненный цикл и завершение

#

Start сразу планирует цикл обработки. Complete и Abort запрашивают изменение жизненного цикла; Completion сообщает, когда цикл и завершающая очистка действительно закончились.

ОперацияНовые сообщенияНакопленные сообщенияCompletion
Complete()ОтклоняютсяОбрабатываютсяУспех: Completed, если дальнейшая обработка не прервётся или не завершится ошибкой.
Обычный переход Stop / StopWithStateОтклоняютсяОбрабатываютсяТот же корректный путь, что у Complete.
Stop в политике ошибокОтклоняютсяОтбрасываютсяС исключением: Faulted error.
Abort()ОтклоняютсяОтбрасываютсяОтменена: Aborted.
IDisposable.Dispose()ОтклоняютсяСемантика AbortЗапрашивает abort, не ожидает остановки.
IAsyncDisposable.DisposeAsync()ОтклоняютсяСемантика CompleteОжидает остановки; может передать отмену/исключение.
Корректный Stop не фиксирует окончательное состояние

StatefulTransition.StopWithState next применяет next и закрывает приём, затем обрабатывает ранее принятые команды. Они могут снова изменить состояние. Для кооперативной остановки без обработки остатка используй Abort; если принятые команды должны стать пустыми действиями, введи отдельное доменное состояние «закрыто».

Abort не способен принудительно прервать произвольный пользовательский код. Передавай ctx.CancellationToken в отменяемый ввод-вывод и задержки. До завершения агента текущий обработчик должен вернуть управление. Неотменяемый обработчик может удерживать Completion; корректная обработка остатка очереди тоже может ожидать долгую работу.

F#
agent.Complete() |> ignore
try
    do! agent.Completion
with
| :? OperationCanceledException -> printfn "Aborted"
| error -> printfn "Faulted: %s" error.Message

После остановки StopReason, уведомления об остановке и Completion описывают один исход. Ссылки из очереди очищаются до публикации завершения. Отбрасывание сообщения не вызывает автоматический Dispose произвольных ресурсов внутри него; правила владения и освобождения payload задаёт прикладной протокол.

OnStopped и обработчики событий должны быть короткими. Completion публикуется после завершающей очистки и callbacks остановки, поэтому callback не должен ожидать Completion собственного агента. Примеры с use явно завершают и ожидают агента на успешном пути; при более ранней ошибке освобождение области запрашивает abort.

09

Ошибки и наблюдаемость

#

Стандартная политика останавливает агент при необработанном исключении обработчика. Он сообщает Errored, завершает текущий запрос ошибкой, если тот ещё ждёт, отбрасывает очередь и публикует завершение с исключением. Выбор Continue меняет решение о жизненном цикле, но не превращает неуспешный Ask в успех.

Вид агентаПолитикаВарианты
БазовыйAgentOptions.OnError(name, error)Continue или Stop.
Неизменяемое состояниеOnUnhandled(state, error)KeepStateAndContinue, ReplaceStateAndContinue s, Stop, StopWithState s.
Изменяемое состояниеOnUnhandled(state, error)Continue или Stop. Автоматического отката нет.

Явный OnUnhandled обёртки с состоянием имеет приоритет над AgentOptions.OnError. Если он отсутствует, используется базовая политика; если отсутствуют обе, агент останавливается. Исключение из callback политики тоже приводит к остановке. Исключение проекции чтения завершает ошибкой этот запрос и не считается ошибкой команды, останавливающей агент.

F#
let options =
    { StatefulAgentOptions.create "party" with
        AgentOptions =
            { AgentOptions.create "party" with
                Mailbox = AgentMailbox.boundedWait 64
                OnStarted = Some (fun name -> printfn "Started %s" name)
                OnStopped = Some (fun (name, reason) ->
                    printfn "Stopped %s: %A" name reason) }
        OnUnhandled = Some (fun (_state, error) ->
            eprintfn "Party failure: %s" error.Message
            StatefulErrorAction.Stop) }

События — наблюдение

Started, Errored и Stopped — текущие уведомления. Агент запускается до возврата Start, поэтому последующая подписка Started.Add может пропустить старт. Если он важен, задай OnStarted до Start. Поздние подписки на события завершения тоже не получают повтор старого уведомления; для текущего результата используй Completion / StopReason.

OnTransition вызывается после замены состояния и получает предыдущее/новое состояние. Это наблюдение, а не транзакционная валидация. Не меняй полученные объекты и не запускай неотслеживаемую работу, которая изменит их позже. Наблюдающие callbacks жизненного цикла и переходов не должны блокироваться или выбрасывать исключения; их исключения изолированы от обработки агента.

Владеющий сервис должен наблюдать Completion, чтобы сбой попадал в логи и логику остановки. Супервизор и автоматический перезапуск не предоставляются: политика перезапуска должна определять судьбу состояния, ожидающей работы, native-ресурсов и повторяющихся побочных эффектов.

Владение и интеграция с сервером

#

Последовательность обработчиков не означает выделенный поток

Цикл ожидает обработчик до чтения следующего сообщения. Его продолжения могут выполняться на разных потоках пула. При allowSynchronousContinuations = true часть продолжений также может выполняться на потоке завершающего операцию отправителя. Это специальная настройка планирования, а не гарантия привязки к потоку.

В Dreamsleeve явно задай владельца операций ENet host/service/send. Агент способен сериализовать доступ, если все операции проходят через эту границу; сам по себе он не гарантирует выделенный поток сетевого цикла. Если native-интеграции нужен фиксированный поток ОС, создай отдельного владельца этого цикла и обменивайся с доменными агентами командами и данными с явным владением.

Не создавай циклические ожидания

  • Не ожидай Ask/Read собственного агента внутри текущего обработчика: запросу нужен потребитель, уже занятый этим обработчиком.
  • Не ожидай собственный PostAsync, если ограниченная очередь может заполниться. Для базового агента один из вариантов — ctx.TryPost с явной обработкой Full; другой — явное планирование команды следующей итерации.
  • Схема A спрашивает B, пока B спрашивает A, тоже может заблокироваться. Используй направленный поток запросов, асинхронные ответы или координирующего владельца.
  • Не блокируй асинхронную работу через .Result / .Wait() внутри обработчиков и callbacks.

Модуль не добавляет периодические таймеры, приоритеты, сохраняемые очереди, автоматическое объединение обновлений или распределённую доставку. Таймер может публиковать тики, но нужно определить судьбу накопленных тиков при отставании потребителя.

Три публичных типа агентов и привычная схема использования сохранены. Исправления уточняют завершение, запросы с ответом и учёт потерь; при переходе с приложенного исходника нужно учесть следующие изменения поведения.
