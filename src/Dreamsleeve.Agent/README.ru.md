# Dreamsleeve.Agent

Последовательные агенты F# внутри одного процесса, построенные на `System.Threading.Channels` и `Task`. Целевая платформа — **.NET 10+**; используются только стандартные зависимости F#/.NET.

**[Интерактивное руководство — Русский / English](docs/index.html#ru)** · **[English README](README.md)** · [Исходник](Agent.fs) · [Запускаемые примеры](examples)

Открой `docs/index.html` прямо в браузере. Это одна автономная адаптивная страница: переключение языка, поиск разделов, светлая и тёмная темы, кнопки копирования. Сервер, сборка сайта, CDN и подключение к сети не требуются.

## Выбор владельца работы

| Тип | Модель | Где удобно начать |
|---|---|---|
| `Agent<'Message>` | Последовательные асинхронные действия; протокол задаёт обработчик. | Очередь исходящих действий, запросы на сохранение, ограниченный поток заданий. |
| `StatefulAgent<'State,'Command>` | Команда возвращает `Stay`, `SetState` или переход с корректным завершением. | Правила партии/гильдии, жизненный цикл сессии, небольшое неизменяемое состояние. |
| `MutableStatefulAgent<'State,'Command>` | Команда изменяет один экземпляр состояния, принадлежащий агенту. | Словарь присутствия, индексы, счётчики с частыми обновлениями. |

Все три варианта обрабатывают сообщения последовательно, включая асинхронную работу внутри обработчика. Выделенный поток они не создают. Изменяемое состояние безопасно, пока все ссылки на него остаются у агента; запросы должны возвращать снимки.

## Сборка и запуск

Из корня репозитория при установленном SDK .NET 10:

```sh
dotnet build src/Dreamsleeve.Agent/Dreamsleeve.Agent.fsproj -c Release
dotnet run --project src/Dreamsleeve.Agent/examples/Dreamsleeve.Agent.Examples.fsproj -c Release
dotnet run --project tests/Dreamsleeve.Server.Tests -c Release -- --filter-test-list Dreamsleeve.Agent
```

Программа примеров запускает обычный агент исходящих действий, неизменяемое состояние партии и изменяемый реестр присутствия со снимками. Вывод детерминирован, все агенты завершаются. Исходники: [Outbound.fs](examples/Outbound.fs), [Party.fs](examples/Party.fs), [Presence.fs](examples/Presence.fs).

## Минимальный запрос с ответом

```fsharp
open System
open Dreamsleeve.Agent

type Command = Echo of string * ReplyChannel<string>

let example () = task {
    let options =
        { AgentOptions.create "echo" with
            Mailbox = AgentMailbox.boundedWait 64
            DefaultAskTimeout = Some (TimeSpan.FromSeconds 2.) }

    use agent =
        Agent<Command>.Start(options, fun _ (Echo (text, reply)) -> task {
            reply.Reply text
        })

    let! text = agent.AskAsync(fun reply -> Echo ("hello", reply))
    printfn "%s" text
    agent.Complete() |> ignore
    do! agent.Completion
}
```

`TryPost` сразу пытается поставить сообщение в очередь. `PostAsync` ждёт места в ограниченной очереди с режимом `Wait` и возвращает `AgentPostResult`. `Posted` означает приём, а не завершение обработки. `TryAskAsync` возвращает `AgentAskResult<'Reply>`; `AskAsync` превращает неуспешные исходы в исключения. Оба варианта с состоянием поддерживают команды с ответом и запросы проекции состояния через `TryReadAsync` / `ReadAsync`.

## Основные контракты

- **Обратное давление:** для чата, команд гильдии и запросов с ответом начинай с `boundedWait`. Ожидай публикации или ограничивай их число; ёмкость очереди не ограничивает бесконечное количество ожидающих отправителей.
- **Потери:** режимы drop удаляют новое либо уже ожидающее сообщение. Это отражают `Dropped` и `DroppedCount`; ранее принятая публикация тоже может быть вытеснена позже. Политика действует на всю очередь, а не отдельно на каждого игрока.
- **Дедлайны:** таймаут Ask/Read охватывает ожидание места и ответа. Ноль сразу завершает запрос, не создавая команду. Таймаут или отмена вызывающего кода не откатывают принятую команду и не отменяют её обработчик.
- **Владение:** проекция выполняется внутри агента, но возврат живого словаря, ленивой последовательности, изменяемого массива или вложенного объекта может нарушить изоляцию. Создавай независимый снимок внутри проекции.
- **Завершение:** `Complete()` закрывает приём и обрабатывает накопленные сообщения. `Abort()` запрашивает кооперативную отмену и отбрасывает остаток очереди. Для фактического завершения ожидай `Completion`.
- **Ошибки:** стандартная политика останавливает агент с `Faulted`. Текущий неуспешный Ask получает `Faulted`, даже если выбранная политика продолжает работу. `OnUnhandled` обёртки с состоянием имеет приоритет над базовым `OnError`; без него используется базовая политика.
- **Completion:** успешна для `Completed`, отменена для `Aborted`, содержит исключение для `Faulted`. Публикуется после очистки и обработчиков остановки. `IDisposable.Dispose` запрашивает abort; `IAsyncDisposable.DisposeAsync` завершает корректно и ожидает остановки.
- **Взаимные блокировки:** не ожидай собственный Ask/Read, собственный `PostAsync` при заполненной ограниченной очереди, собственный `Completion` внутри callback жизненного цикла или циклические запросы между агентами.
- **Старт:** `Start` запускает работу сразу. Для гарантированного наблюдения старта задавай `OnStarted` в options; событие `Started` не воспроизводится для поздних подписчиков.

[Полное руководство](docs/index.html#ru) содержит таблицы результатов, детали завершения и политик ошибок, изменения поведения и рекомендации для сервера Dreamsleeve. Модуль не предоставляет автоматические перезапуски, дерево супервизоров, гарантированное сохранение сообщений, объединение обновлений по ключу или протокол распределённых акторов.

## Адресаты и конечные автоматы

`agent.Ref` и `context.Ref` предоставляют AgentRef с TryPost/PostAsync без управления
жизненным циклом. `Ref.Map(Constructor)` сужает адрес до одного случая DU. StatefulAgent
и MutableStatefulAgent тоже предоставляют Ref команд. IsNonDropping показывает,
может ли mailbox отбрасывать принятые сообщения; это не подтверждение обработки.

В обработчике базового Agent вызывайте `context.PipeToSelf(operation, toMessage)`.
operation принимает CancellationToken и возвращает Task; toMessage преобразует
Result<_, exn> в сообщение. Работа выполняется вне mailbox, затем результат
обрабатывается обычным обработчиком. Обе функции должны захватывать только
неизменяемые входные данные, не изменять состояние агента.

Требуется unbounded или bounded-wait mailbox. Вызов разрешён только из обработчика;
количество выполняющихся операций ограничивает прикладной компонент. Agent учитывает
задачи, наблюдает ошибки и ждёт их завершения перед освобождением ресурсов. Abort
и аварийная остановка отменяют работу. Ошибка операции приходит сообщением;
ошибка формирования сообщения завершает агент, в том числе во время остановки.

Complete сразу закрывает приём: ещё не отправленные результаты уже не будут
обработаны, хотя Completion дожидается работы. Для дренирования используйте
прикладную команду Stop и вызывайте context.Complete после обработки всех завершений.
Отмена кооперативна; операция, игнорирующая её, может задержать Completion.

Для протокола с обязательной доставкой без отбрасывания используйте
`Ref.TryReliable()`: Some содержит `ReliableAgentRef`, None означает несовместимую
политику mailbox. Проверка выполняется при сборке адресов. `ReliableAgentRef.Map`
сохраняет гарантию, а PostAsync возвращает только Posted/Closed/Canceled;
заполненная очередь означает асинхронное ожидание. При остановке необработанные
сообщения всё ещё могут быть потеряны: Posted подтверждает только приём.

Владелец наблюдает `child.Completion` через `context.Own(child, stopped)` или
`context.Watch(target, stopped)` и получает сообщение о завершении. При сбое приходит исходное исключение; позднее
наблюдение тоже работает. Перезапуск — создание нового агента после Completion
и обновление адреса у потребителей. Библиотека сама не перезапускает агент,
не восстанавливает его состояние и не повторяет принятые команды.
Событие Stopped не воспроизводится поздним подписчикам; OnStopped в options
устанавливается до запуска, но вызывается до завершения Completion.

## Ограниченные последовательные отправки

Для каждого независимого маршрута создаётся AgentOutbox(capacity, destination).
В обработчике владельца вызывается `TrySend(context, message, onFailure)`.
False означает заполнение локального лимита: сообщение не запланировано.
True означает приём в outbox, а не доставку или обработку адресатом. Лимит включает
очередь, текущую отправку и незавершённое уведомление об ошибке. Фактически выполняется
один допуск в mailbox; порядок отправок сохраняется.

Библиотека сама продолжает очередь и освобождает ёмкость. Pump, Acknowledge,
публичных подтверждений и сообщений об успешном допуске больше нет. В mailbox
владельца через onFailure приходит только AgentSendFailure: Closed, Canceled или
Faulted с исходным исключением. Маппер работает вне обработчика и должен только
составлять сообщение из неизменяемых данных. Перегрузка TrySend без onFailure
отменяет владельца при недоступности адресата и завершает с ошибкой при исключении.
Отмена самим владельцем не порождает сообщений об ошибке доставки.

Complete автоматически дренирует принятые отправки, даже после закрытия входного
mailbox. Abort отменяет ожидающие отправки и дожидается их завершения. Если ошибка
доставки уже не может попасть в mailbox владельца во время Complete, итог меняется
на отмену или исходное исключение: ошибка не превращается в успешное завершение.
Окончательная причина остановки фиксируется после завершения отслеживаемых работ.
Для терминальной ошибки с предварительной отправкой уведомлений есть
`AbortAfterDrain(context)`: вызвать один раз и больше не отправлять по этому маршруту.

Внутренний механизм ограничения доставок общий с обработчиками запросов ниже.
SemaphoreSlim синхронизирует только библиотечные резервы; состояние приложения
остаётся у последовательного обработчика. Mailbox владельца должен быть non-dropping.
Автоматических ретраев, дедупликации и гарантии выполнения команды outbox не даёт.
PipeToSelf остаётся для фоновых операций, результат которых нужен владельцу,
а для наблюдения Completion ребёнка есть Own/Watch; обычная отправка его больше не требует.

## Обработчики запросов с ответами

`AgentOutbox.createHandler capacity output execute` сохраняет порядок ответов одному
адресату. `AgentReplyDispatcher.createHandler capacity replyTo execute` доставляет
ответы разным адресатам независимо. Порядок независимых ответов может меняться;
сопоставляйте их по OperationId. Каждый обработчик создаётся один раз для своего агента.

Место резервируется ДО execute, который выполняется в обработчике владельца.
При полном лимите следующая команда ждёт до изменения состояния. Доставка освобождает
место без сообщения в mailbox владельца. Медленный получатель занимает часть общего
лимита; когда заняты все места, следующие команды ждут. Это не квота на игрока.

Complete дренирует доставки; Abort отменяет ожидание лимита и доставки. Закрытие
единственного упорядоченного выхода отменяет владельца; закрытый адресат независимого
ответа не останавливает остальных и не откатывает запись. Исключение доставки видно
через Completion. Если живой адресат не читает, штатная остановка может ждать;
ограничить это ожидание через Abort должен владелец жизненного цикла.

### Фоновое выполнение запросов

`AgentReplyDispatcher.createAsyncHandler capacity replyTo execute` принимает
`execute: CancellationToken -> Request -> Task<Reply>`. Место резервируется до
запуска операции в существующем отслеживаемом фоновом worker. Даже синхронный код
execute до первого await выполняется вне mailbox handler: дополнительный Task.Run
вокруг синхронного вызова зависимости не нужен. Резерв удерживается до окончания
операции и допуска ответа в mailbox получателя. Свободное место асинхронно ожидает
обработчик, а освобождает worker без обратного сообщения через mailbox владельца.

Передавайте неизменяемые запросы и зависимости, допускающие конкурентное применение.
Одновременно могут работать несколько execute, в пределах общего capacity. Нельзя
захватывать изменяемое состояние владельца или ждать работы, которую способен
выполнить только его уже насыщенный обработчик. Функция replyTo по-прежнему вызывается
у владельца и должна лишь выбрать адрес. Для изменения состояния внутри владельца
остаётся синхронный createHandler; его поведение не меняется.

Complete обрабатывает принятые mailbox-команды, затем ждёт их операции и доставку
ответов. Abort запрашивает кооперативную отмену и ждёт очистку отслеживаемых задач;
синхронный вызов, игнорирующий token, принудительно не прерывается. Необработанное
исключение операции или доставки завершает Completion с ошибкой. Закрытый requester
освобождает резерв после окончания операции, не откатывая эффект и не останавливая
остальных. Медленный получатель продолжает занимать своё место. Этот общий лимит
не является квотой на игрока, таймаутом или отдельным пулом потоков.

Оба dispatcher позволяют Request отличаться от DU владельца: одна ветка обработчика
вызывает `dispatch context request`, остальные обслуживают другие команды. Асинхронный
execute не получает state или context владельца. Если результат должен изменить
состояние агента, отправьте отдельное сообщение результата либо используйте PipeToSelf.

## Владение детьми и наблюдение зависимостей

`context.Own(child, stopped)` вызывается один раз из обработчика владельца.
Маппер получает Result<unit, exn> после фактического Completion ребёнка, в том числе
если ребёнок завершился до присоединения. Abort или сбой родителя отменяет ребёнка
и ждёт его очистку. Штатный Stop ребёнка задаёт приложение: сначала завершить детей,
затем вызывать Complete родителя. Игнорирующая отмену очистка может задержать родителя.
Библиотека не перезапускает ребёнка и не восстанавливает его состояние.

`context.Watch(target, stopped)` наблюдает общую зависимость без владения ею.
Перегрузка `Watch(completion: Task, stopped)` даёт то же наблюдение, когда наружу
доступна только задача жизненного цикла; перегрузка с Agent делегирует ей работу.
При Complete или Abort наблюдателя ожидание отключается, не останавливая target
и не дожидаясь его завершения. Мапперы работают вне обработчика и только создают
сообщение. Обоим механизмам нужен non-dropping mailbox владельца.

## Перенаправленные запросы

`AgentReplyScope.create context target capacity closedReply busyReply` создаёт одну
область ожиданий на маршрут. `scope.Forward(reply, send)` ограничивает незавершённые
ReplyChannel и вызывает синхронную функцию планирования отправки. Она работает вне
библиотечного lock и может использовать outbox для сохранения порядка с другими
командами адресата. False означает отказ планирования и завершает запрос closedReply;
исключение завершает запрос ошибкой и передаётся политике ошибок владельца.

При завершении адресата или остановке владельца ожидания закрываются автоматически,
даже если mailbox владельца занят. `scope.Close()` закрывает маршрут раньше, например
при Disconnect. После закрытия новые запросы получают closedReply; при полном лимите —
busyReply. Завершённые и отменённые запросы удаляются при следующем Forward, все ссылки
очищаются при Close. Повторная передача того же незавершённого ReplyChannel не создаёт
вторую команду. Правило первого результата в ReplyChannel защищает успешный ответ
от конкурентного закрытия и отклоняет поздние ответы.

Короткий lock внутри библиотеки согласует резервирование и завершение запросов;
функция send под ним не выполняется. Состояние приложения остаётся у обработчика.
Закрытие ожиданий не отзывает уже принятые команды и не останавливает target.
Доменные ответы, маршрутизация и порядок штатного выхода остаются в приложении.

## Допуск со служебным резервом

`AgentMailbox.boundedWithControl ordinaryCapacity controlReserve` создаёт одну FIFO
с общей ёмкостью `ordinaryCapacity + controlReserve`. В `Agent.Start` передаётся
именованный чистый классификатор `isControl = isControlMessage`. Он выполняется
на отправителе, включая Map и Ask, и не обращается к состоянию получателя.
Существующие варианты mailbox и вызовы Start не меняются.

Обычные сообщения занимают не более ordinaryCapacity мест. Служебные могут занять
свободные места общей очереди, но не обходят ранее принятые сообщения. Обычный поток
не может исчерпать служебный резерв; это гарантия допуска, а не приоритет обработки.
Ёмкости считают очередь, без текущего обработчика. Место освобождается при dequeue,
даже если обработчик ещё работает или позднее завершается ошибкой.

`ReliableAgentRef.TryPost` возвращает `AgentTryDeliveryResult.Posted/Full/Closed`.
`PostAsync` ждёт подходящую ёмкость; отменённое ожидание ничего не резервирует.
Complete/Abort закрывают и будят ожидающих отправителей. Отмена после Posted
не отзывает уже принятую команду. Оба способа отправки применяют один классификатор
и один FIFO, в том числе после сужения адреса через Map.

Резерв не делает безграничным поток управления и не резервирует места в исходящем
AgentOutbox. Его владелец отдельно ограничивает обычные незавершённые операции,
оставляет место для Stop/Detach в своём ordered outbox и закрывает обычный допуск
перед завершением. Порядок между независимыми конкурирующими отправителями
определяется фактическим приёмом, а не временем начала PostAsync.


`AgentTicker.start interval context toMessage` создаёт один owned PeriodicTimer.
После обработки tick владелец вызывает `Acknowledge()`: до этого новые периоды
объединяются. Callback строит только сообщение, не читает mutable state агента.
Complete/Abort останавливают worker. `startWithTimeProvider` позволяет проверять
расписание без wall-clock sleeps. Timestamp поля AgentTick относятся к TimeProvider.
