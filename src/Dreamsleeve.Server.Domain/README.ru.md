# Домен Dreamsleeve: первый MVP

Целевой runtime — .NET 10. Домен описывает глобальный чат, список игроков,
их профиль и текущее игровое состояние для таблицы онлайна и светлячков.
Сервер передаёт показания Skyrim, не моделируя авторитарную игровую симуляцию.

## Файлы и порядок компиляции

`Library.fs` заменён следующими файлами; порядок уже задан в `.fsproj`:

1. `Primitives.fs` — UMX, ошибки, создание и извлечение примитивов.
2. `Spatial.fs` — ключи форм, места, координаты, углы и расстояния.
3. `ActorValues.fs` — показания, их метаданные и закрытое хранилище.
4. `Players.fs` — профиль, текущее состояние игрока и снимки.
5. `Chat.fs` — сообщения, участники, ограниченная история и каналы.

После копирования обновлённого проекта старый `Library.fs` можно удалить:
он больше не входит в компиляцию. Production-зависимость остаётся одна:
`FSharp.UMX 1.1.0`.

## Сверка с согласованным MVP

Проверены ранее предоставленные `DomainSpecRu.MD` (§3.1, §4.1.1, §6),
`ProductSpecRu.MD`, `TechnicalHandbookRu.MD` и примеры `.proto`.
Поздние решения из обсуждения имеют приоритет над старыми примерами.

| Задача | Данные и операции |
|---|---|
| Идентичность | Выдаваемые сервером `uint64` ID, `Username`, `DisplayName` |
| Текущий персонаж | Необязательные `CharacterName` и `PlayerLocation`, показания Actor Value |
| Таблица онлайна | `PlayerSnapshot`; состав онлайна хранит владелец реестра |
| Светлячки | `LocationId` + исходная позиция/вращение, сравнение пространства и радиуса |
| Глобальный чат | Автор, канал, текст, серверные ID/время, участники по `PlayerId` |
| Короткая история | Ограниченный FIFO и страницы после курсора с признаками пропуска/продолжения |
| Переименование | Неизменяемый профиль и операции замены; ID игрока сохраняется |
| Смена персонажа | Явная очистка позиции, имени персонажа и старых показаний |

Дополнительные обязательные поля в этих сущностях не потребовались.
`Location = ValueNone` означает неизвестное положение, а не отключение от чата.
Новый уникальный `Username`, неуникальный `DisplayName` и `CharacterName`
уточняют старые документы, где было только одно поле `nickname`.

Выдача ID, резервирование уникального username (включая офлайн-профили),
онлайн-реестр, события репликации, peer/session, последовательности пакетов
и codec относятся к владельцу состояния и транспортным контрактам.
В частности, `PlayerData.create` проверку глобальной занятости имени не выполняет.
Расширенный старый список MVP с гильдиями, авторизацией и модерацией здесь
не реализуется: текущий шаг ограничен согласованным доменом.

## Создание и ошибки

Примитивы создаются через одноимённые модули:

```fsharp
Username.create 32 " Newrite "       // Ok username, значение "newrite"
DisplayName.create 64 "Неревар"      // Ok displayName; совпадения допустимы
PlayerId.create 42UL                 // Ok playerId
Position.create 100.0f 200.0f 30.0f  // Ok position
Rotation.create 0.0f 0.0f 7.0f      // угол 7 радиан сохраняется
```

`create`, способный отказать, возвращает `Result<_, DomainError>`.
Отсутствие найденных данных выражается через `voption`, например
`ActorValueStorage.tryFind` или расстояние между разными пространствами.
Предикаты и операции добавления/удаления участника возвращают `bool`.

Составные фабрики, которые лишь объединяют уже принятые значения, возвращают
готовое значение: `PlayerData.create`, `Location.create`, `ChatMessage.create`.
Их внутренние представления закрыты. Для чтения остаются свойства; для
изменений используются функции одноимённых модулей.

**Граница UMX:** алиас `string<username>` или `uint64<playerId>` можно создать
напрямую через UMX. Фабрики задают путь проверки входа, но не превращают алиасы
в типы с непроходимым приватным конструктором. Не создавайте алиасы вручную из
входящих пакетов; составные фабрики доверяют переданным типизированным значениям.

## Текстовая политика

Все текстовые `create` принимают `maxLength` явно. Это значение передаёт слой
конфигурации; приведённые в примерах числа не являются серверными defaults.
Длина считается в Unicode scalar values, а не в UTF-16 code units или графемах.
Например, одна supplementary emoji занимает один scalar, составная emoji может
содержать несколько. Некорректный UTF-16 и неположительные лимиты отклоняются.

| Тип | Политика |
|---|---|
| `Username` | Пробелы по краям убираются; ASCII `A-Z a-z 0-9 _ .`; канонический нижний регистр |
| `DisplayName`, `LocationName`, `ActorValueName`, `ChatChannelName` | Trim + NFC, регистр сохраняется |
| `CharacterName` | Исходная строка игры сохраняется, включая регистр и крайние пробелы |
| `ChatMessageText` | Исходный текст сохраняется; допустимы переносы строк и tab; пустые/пробельные сообщения отклоняются |
| `PluginName` | Имя файла с `.esp/.esm/.esl`, без пути; только ASCII case folding, без Trim/NFC |
| `ActorValueKey` | `namespace:name`, ASCII namespace; ASCII case folding, остальной Unicode сохраняется без Trim/NFC |

Однострочные имена отклоняют управляющие символы и разделители строк даже
на краях исходного текста. Для сообщений допускаются CR/LF/tab.
Ключи Actor Value не допускают пробелы на границах namespace/name.

Внешние машинные ключи нельзя NFC-нормализовать как display name: внешняя
система может различать составной Unicode-символ и эквивалентную последовательность.
У ASCII `AVG:Health` и `avg:health` ключ одинаков; не-ASCII регистр намеренно
не склеивается автоматически. Клиент должен передавать фактическое имя плагина
и зарегистрированное служебное имя AVG, не локализованную подпись.

Снимайте UMX через `.value`, например `Username.value profile.Username`.
Уникальность username проверяется после канонизации в одной операции владельца
реестра; уникальность display name и имени персонажа не требуется.

## Положение и показания

`FormKey` содержит плагин происхождения и локальный ID. Клиент извлекает его
с учётом full/light plugins; сервер не выводит load order из полученного числа.
Нулевой local ID и значения за пределами 24 бит отклоняются. Эта модель не
представляет динамические runtime-формы без плагина происхождения.

`LocationId` — ключ WRLD в экстерьере или CELL в интерьере. Для определения
общего пространства сравнивается именно этот ключ. Подпись `LocationName`
может отличаться и на сравнение пространства не влияет.

Координаты и углы остаются `float32` в нативных единицах Skyrim и радианах.
Отклоняются NaN и бесконечности. Диапазоны координат, скорость, телепорты,
диапазон углов, отрицательное HP и превышение текущего значения над максимумом
не проверяются как игровые правила.

`Position.distanceSquared` возвращает `float<worldUnit^2>`, `distance` —
`float<worldUnit>`. Промежуточный `float64` исключает переполнение при вычитании
и возведении в квадрат любых конечных float32 координат.
Для игрового отбора используйте `PlayerLocation.isWithinRadius` — он сначала
проверяет пространство. Отрицательный/нечисловой радиус является ошибкой.

Показания создаются через `ActorValueState.scalar` / `resource`.
Для чтения есть `current`, `tryMaximum` и `fold`; для замены текущего показания —
`withCurrent`. Максимум передаёт клиент; сервер не выводит его из base value.

## Владение состоянием

`ActorValueStorage`, `Player`, `Chat` и `ChatChannel` принадлежат одному агенту.
Они не предоставляют живые `Dictionary`, `HashSet` или `Queue` через API.
Все чтения, включая создание снимка, выполняются внутри владеющего агента.

`Player.withLocation`/`withProfile` возвращают новую запись, сохраняя то же
внутреннее хранилище показаний. Старую запись нельзя считать независимым снимком.
Для публикации используйте `Player.snapshot` и `Chat.snapshot`: вложенные
коллекции там неизменяемы и отделены от текущего состояния.

```fsharp
// До этого key/info созданы и проверены своими фабриками.
Player.setActorValue key info player
let published = Player.snapshot player

// published не изменится при дальнейшей записи в player.
Player.clearActorValues player
```

`setMany` сначала полностью перечисляет источник, затем применяет готовые
типизированные значения. Ошибка перечисления не оставляет частично применённую
пачку. Повторяющийся ключ в пачке получает последнее переданное значение.

`withCharacterName` переименовывает текущего персонажа, сохраняя его показания.
`beginCharacter` начинает новое игровое состояние и очищает старые показания
и позицию, даже когда имена персонажей совпадают. `clearGameState` оставляет
серверный профиль, но убирает всю текущую игровую информацию.

## История чата

```fsharp
// channelId/name — принятые значения. Capacity приходит из конфигурации.
let chatResult = Chat.create channelId 100
// Внутри обработчика владельца:
// Chat.join player.Data.PlayerId chat |> ignore
// Chat.append message chat                  : Result<unit, DomainError>
// Chat.historyAfter ValueNone 20 chat       : Result<ChatHistoryPage, DomainError>
// Chat.historyAfter page.NextCursor 20 chat : следующая страница
```

Добавление сообщения проверяет канал, членство автора по `PlayerId` и строгое
возрастание ID. Проверки выполняются до изменения состояния. Сервер назначает
ID и `SentAt`; фабрика сообщения приводит время к UTC, сохраняя момент времени.

История ограничена количеством сообщений. `HasMore` означает наличие следующей
страницы. `HasGap` означает, что после переданного курсора были вытеснены
сообщения этого канала. Пропуски ID, занятые другими каналами, не создают
ложный gap. При `ValueNone` возвращается начало доступной истории без gap.
`clearHistory` не разрешает повторно использовать ранее принятые ID.

Курсор относится к текущему жизненному циклу истории. Перезапуск сервера должен
либо продолжить выдачу ID, либо объявить клиенту сброс истории через контракт
сессии; `Chat` не хранит счётчик на диске. Будущий курсор возвращает пустую страницу.

`ChatMessage.Author` — снимок профиля при отправке. Клиент может отображать
актуальный DisplayName из каталога профилей, сохраняя снимок как fallback.
Открытие карточки автора всегда производится по `PlayerId`.

## Сборка и проверки

Из корня репозитория:

```sh
dotnet build src/Dreamsleeve.Server.Domain/Dreamsleeve.Server.Domain.fsproj -c Release
dotnet run --project tests/Dreamsleeve.Server.Domain.Tests -c Release
```

Тестовый проект использует указанные в техническом справочнике Expecto и Faqt.
Проверяются нормализация и внешние ключи, конечность и точность вычислений,
снимки, смена персонажа, членство и ошибки чата, вытеснение и продолжение истории.
