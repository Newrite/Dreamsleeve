# Домен Dreamsleeve: первый MVP

Целевой runtime — .NET 10. Домен описывает глобальный чат и системный канал объявлений,
список игроков, их профиль, публичную личность и текущее игровое состояние для таблицы
онлайна и светлячков, метки на земле, словарь модерации, наказания и правила веб-админки.
Сервер передаёт показания Skyrim, не моделируя авторитарную игровую симуляцию.

## Файлы и порядок компиляции

Порядок файлов уже задан в `.fsproj`:

1. `Primitives.fs` — UMX, ошибки, создание и извлечение примитивов.
2. `Spatial.fs` — ключи форм, места, координаты, углы и расстояния.
3. `ActorValues.fs` — показания, их метаданные и закрытое хранилище.
4. `PlayerDetails.fs` — раса, уровень, занятие и описательные сведения о месте.
5. `Players.fs` — профиль, публичная личность, команды наблюдений, состояние игрока и снимки.
6. `Pseudonyms.fs` — серверный словарь псевдонимов и книга имён, показанных онлайн.
7. `Chat.fs` — сообщения, участники, ограниченная история и каналы.
8. `GroundMarks.fs` — метки на земле: вид и текст, положение, правила, срок жизни, видимость и хранилище с квотами.
9. `Moderation.fs` — словарь `[block]`/`[flag]` и публичная проекция профиля.
10. `Admin.fs` — правила веб-админки: администраторы, роли игроков, действия аудита, одноразовые коды, сессии панели и проекция игрока для панели.
11. `Sanctions.fs` — муты и баны: вид, срок, причина, кто выдал, действие во времени.
12. `Addresses.fs` — адреса входа и баны диапазонов IP.
13. `Devices.fs` — устройства игроков и баны устройств.
14. `Guilds.fs` — гильдии: имя, роли и права, лимиты, приглашения, гильдейский мут, книга всех гильдий с индексами для лимитов ([GuildsRu.md](../../docs/GuildsRu.md)).
15. `Core.fs` — преобразование серверного времени в Unix milliseconds и обратно.

Production-зависимость домена: `FSharp.UMX 1.1.0`.

## Сверка с согласованным MVP

Проверены ранее предоставленные `DomainSpecRu.MD` (§3.1, §4.1.1, §6),
`ProductSpecRu.MD`, `TechnicalHandbookRu.MD` и примеры `.proto`.
Поздние решения из обсуждения имеют приоритет над старыми примерами.

| Задача | Данные и операции |
|---|---|
| Идентичность | Выдаваемые сервером `uint64` ID, `Username`, `DisplayName` |
| Текущий персонаж | `CharacterGeneration`, необязательные `CharacterName` и `PlayerLocation`, показания Actor Value, `PlayerDetails` |
| Таблица онлайна | `PlayerSnapshot`; снимки и состав онлайна хранит PresenceAgent |
| Светлячки | `LocationId` + исходная позиция/вращение, сравнение пространства и радиуса |
| Глобальный чат | Автор, канал, текст, серверные ID/время, участники по `PlayerId` |
| Короткая история | Ограниченный FIFO и страницы после курсора с признаками пропуска/продолжения |
| Переименование | Неизменяемый профиль и операции замены; ID игрока сохраняется |
| Смена персонажа | Явная очистка позиции, имени персонажа и старых показаний |

`CharacterGeneration` отличает загрузки персонажей даже с одинаковым именем.
`Location = ValueNone` означает неизвестное положение, а не отключение от чата.
Новый уникальный `Username`, неуникальный `DisplayName` и `CharacterName`
уточняют старые документы, где было только одно поле `nickname`.

Выдача ID, резервирование уникального username (включая офлайн-профили),
онлайн-реестр, события репликации, peer/session, последовательности пакетов
и codec относятся к владельцу состояния и транспортным контрактам.
В частности, `PlayerData.create` проверку глобальной занятости имени не выполняет.
Авторизация и сохранение профиля в SQLite реализованы вне игрового домена.
Гильдии и партии остаются дальнейшими расширениями; словарь модерации — `Moderation.fs`,
наказания — раздел «Админка».

## Создание и ошибки

Сервер проверяет входящие клиентские значения один раз при создании примитивов.
Хранилища и составные фабрики принимают уже созданные значения без повторной
проверки их строк и чисел. Политика допустимого текста, ограничения размера и
конечность координат относятся к этой границе. Сервер не проверяет игровые
правила: скорость перемещения, допустимую величину HP или существование формы
в установленном у клиента моде.

Примитивы создаются через одноимённые модули:

```fsharp
Username.create 32 " Newrite "       // Ok username, значение "newrite"
DisplayName.create 64 "Неревар"      // Ok displayName; совпадения допустимы
PlayerId.create 42UL                 // Ok playerId
Position.create 100.0f 200.0f 30.0f  // Ok position
Rotation.create 0.0f 0.0f 7.0f      // угол 7 радиан сохраняется
```

`create`, способный отказать, возвращает `Result<_, DomainError>`.
Отсутствие найденных данных выражается через `voption`, например
`ActorValueStorage.tryFind` или расстояние между разными пространствами.
Предикаты и операции добавления/удаления участника возвращают `bool`.

Составные фабрики, которые лишь объединяют уже принятые значения, возвращают
готовое значение: `PlayerData.create`, `Location.create`, `ChatMessage.create`.
Их внутренние представления закрыты. Для чтения остаются свойства; для
изменений используются функции одноимённых модулей.

**Граница UMX:** алиас `string<username>` или `uint64<playerId>` можно создать
напрямую через UMX. Фабрики задают путь проверки входа, но не превращают алиасы
в типы с непроходимым приватным конструктором. Не создавайте алиасы вручную из
входящих пакетов; составные фабрики доверяют переданным типизированным значениям.

## Текстовая политика

Все текстовые `create` принимают `maxLength` явно. Это значение передаёт слой
конфигурации; приведённые в примерах числа не являются серверными defaults.
Длина считается в Unicode scalar values, а не в UTF-16 code units или графемах.
Например, одна supplementary emoji занимает один scalar, составная emoji может
содержать несколько. Некорректный UTF-16 и неположительные лимиты отклоняются.

| Тип | Политика |
|---|---|
| `Username` | Пробелы по краям убираются; ASCII `A-Z a-z 0-9 _ .`; канонический нижний регистр |
| `DisplayName`, `ChatChannelName` | Trim + NFC, регистр сохраняется; пустое имя отклоняется |
| `LocationName`, `ActorValueName` | Исходная игровая подпись сохраняется, включая пробелы и Unicode-представление; пустая подпись допустима |
| `CharacterName` | Исходная строка игры сохраняется, включая регистр и крайние пробелы |
| `ChatMessageText` | Исходный текст сохраняется; допустимы переносы строк и tab; пустые/пробельные сообщения отклоняются |
| `PluginName` | Непустой ограниченный ключ плагина; только ASCII case folding, без Trim/NFC и проверки расширения/правил Windows-файла |
| `ActorValueKey` | `namespace:name`, ASCII namespace; ASCII case folding, остальной Unicode сохраняется без Trim/NFC |

Однострочные имена отклоняют управляющие символы и разделители строк даже
на краях исходного текста. Для сообщений допускаются CR/LF/tab.
Ключи Actor Value не допускают пробелы на границах namespace/name.

Для игровых подписей сохраняются ограничения длины, корректности Unicode и
управляющих символов; `null` отклоняется. Отсутствующая подпись не должна мешать
принять координаты или показание: интерфейс может показать FormKey/ActorValueKey.
Сервер не открывает файл по PluginName. Извлечение фактического basename игры
остаётся задачей клиентского адаптера; сервер использует строку как часть ключа.

Проверка Unicode и управляющих символов использует `System.Text.Rune` за один
проход по исходной строке. Если преобразование вернуло исходную строку, её длина
повторно не считается. Для Trim/NFC лимит по-прежнему относится к результату.

Внешние машинные ключи нельзя NFC-нормализовать как display name: внешняя
система может различать составной Unicode-символ и эквивалентную последовательность.
У ASCII `AVG:Health` и `avg:health` ключ одинаков; не-ASCII регистр намеренно
не склеивается автоматически. Клиент должен передавать фактическое имя плагина
и зарегистрированное служебное имя AVG, не локализованную подпись.

Снимайте UMX через `.value`, например `Username.value profile.Username`.
Уникальность username проверяется после канонизации в одной операции владельца
реестра; уникальность display name и имени персонажа не требуется.

## Публичная личность

Модель — [DomainSpecRu.MD §3.1](../../docs/DomainSpecRu.MD). `PublicIdentity` — то, что видят
другие игроки: `Profile of PlayerData` (профиль после `Moderation.publicProfile`) или
`Pseudonymous of PlayerId * Pseudonym`. `PlayerId` доступен у обоих вариантов.
`PublicIdentity.ofProfile pseudonym profile` выбирает вариант, `PublicIdentity.pseudonym`
извлекает псевдоним. `PlayerSnapshot.Identity` (прежнее поле `Data`) и
`ChatMessage.Author` имеют этот тип; `PlayerSnapshot.withPseudonym` заменяет профиль
псевдонимом и убирает имя персонажа, не трогая `CharacterNameWithheld`, игровые данные и
позицию. `GroundMark.Pseudonym` — псевдоним на момент размещения,
`GroundMark.authorIdentity profile mark` — автор метки для wire (её псевдоним, иначе текущий
профиль).

`Pseudonym.create` — запись словаря: одна строка, 1–48 байт UTF-8, без пробелов по краям,
управляющих символов и `< >`, текст хранится как есть (не разметка); `Pseudonym.restore` —
то же с запасом до 64 байт для номера (чтение из хранилища); `Pseudonym.numbered n`
добавляет номер («Страж 2»). `PseudonymDictionary.create` принимает уже созданные записи,
убирает повторы (без регистра после NFC, `PseudonymDictionary.key`) и возвращает `ValueNone`
для пустого списка; `builtIn` — 24 имени клиентского `aliases.toml`.

`HiddenIdentity = Shown | Everywhere | ExceptGroundMarks` — где другие видят псевдоним:
присутствие и чат всегда вместе, метки на земле — по выбору (`HiddenIdentity.isHidden`,
`coversGroundMarks`).

`PseudonymBook` (закрытый `Dictionary`, один владелец — `SessionTable` runtime) хранит
профиль каждого онлайн-игрока, его псевдоним и вариант: `show` регистрирует показанный
профиль, `apply pick hiding profile` при `Shown` показывает профиль, иначе оставляет уже
выданный псевдоним или выбирает запись словаря по индексу `pick` (случайно у владельца,
детерминированно в тестах) и нумерует её, пока имя совпадает с уже показанными — username и
display name других игроков (и скрывших имя «кроме меток»), их псевдонимы и собственные
настоящие имена игрока; `tryFind`, `tryProfile`, `release`. Псевдоним не выводится из имени и
не хранится между сессиями.

## Положение и показания

`FormKey` содержит плагин происхождения и локальный ID. Клиент извлекает его
с учётом full/light plugins; сервер не выводит load order из полученного числа.
Нулевой local ID и значения за пределами 24 бит отклоняются. Эта модель не
представляет динамические runtime-формы без плагина происхождения.

`LocationId` — ключ WRLD в экстерьере или CELL в интерьере. Для определения
общего пространства сравнивается именно этот ключ. Подпись `LocationName`
может отличаться и на сравнение пространства не влияет.

Координаты и углы остаются `float32` в нативных единицах Skyrim и радианах.
Отклоняются NaN и бесконечности. Диапазоны координат, скорость, телепорты,
диапазон углов, отрицательное HP и превышение текущего значения над максимумом
не проверяются как игровые правила.

`Position.distanceSquared` возвращает `float<worldUnit^2>`, `distance` —
`float<worldUnit>`. Промежуточный `float64` исключает переполнение при вычитании
и возведении в квадрат любых конечных float32 координат.
Для игрового отбора используйте `PlayerLocation.isWithinRadius` — он сначала
проверяет пространство. Отрицательный/нечисловой радиус является ошибкой.

Показания создаются через `ActorValueState.scalar` / `resource`.
Для чтения есть `current`, `tryMaximum` и `fold`; для замены текущего показания —
`withCurrent`. Максимум передаёт клиент; сервер не выводит его из base value.

## Владение состоянием

`ActorValueStorage`, `Player`, `Chat` и `ChatChannel` принадлежат одному агенту.
Они не предоставляют живые `Dictionary`, `HashSet` или `Queue` через API.
Все чтения, включая создание снимка, выполняются внутри владеющего агента.

`Player.withLocation`/`withProfile` возвращают новую запись, сохраняя то же
внутреннее хранилище показаний. Старую запись нельзя считать независимым снимком.
Для публикации используйте `Player.snapshot` и `Chat.snapshot`: вложенные
коллекции там неизменяемы и отделены от текущего состояния.

```fsharp
// До этого key/info созданы и проверены своими фабриками.
Player.setActorValue key info player
let published = Player.snapshot player

// published не изменится при дальнейшей записи в player.
Player.clearActorValues player
```

`setMany` принимает готовый массив `(ActorValueKey * ActorValueInfo) array`.
Декодирование и создание всех значений заканчиваются до передачи пачки владельцу;
дополнительной материализации произвольного ленивого `seq` внутри хранилища нет.
После передачи массива отправитель его не изменяет. Повторяющийся ключ в пачке
получает последнее переданное значение.

Сетевой путь использует `PlayerUpdate` и `Player.applyUpdate`:

- `BeginCharacter name` начинает новое состояние и увеличивает поколение.
- `RenameCharacter name` сохраняет поколение, показания и метаданные.
- `SetLocation(contextRevision, location)` задаёт надёжную границу положения; `SetActorValues(map)` — только карту показаний;
  пропущенные ключи удаляются, `ValueNone` очищает прежнее положение.
- `SetDetails details` целиком заменяет редко меняющиеся сведения.
- `LeaveGame` увеличивает поколение и очищает персонажа, место, показания и
  метаданные. Серверный профиль остаётся доступен для чата.

Поколение начинается с нуля. Даже повторный `BeginCharacter` с тем же именем
очищает прежнюю информацию. `SetActorValues` создаёт отдельное внутреннее
хранилище до замены игрока; предыдущий объект не получает часть нового сэмпла.
Сессионный владелец допускает `SetLocation`, `SetActorValues` и переименование только при активном
персонаже, а также проверяет бюджет `MaxActorValues` из конфигурации.
Кодек отклоняет повторяющиеся ключи после канонизации до создания `Map`.
Низкоуровневые `setMany` и `withCharacterName` остаются операциями владельца,
их поведение не заменяет этот входной контракт.

`PlayerDetails` хранит необязательную расу (`NamedForm`), уровень, занятие,
описание места и сообщённое клиентом время начала процесса игры. Уровень
ноль допустим, игровые максимумы не задаются. Типизированное занятие
отделяет чтение, разговор, крафт, взлом, меню и другие состояния; его фабрика
проверяет, что target, сложность замка и ключ меню соответствуют виду занятия.
Menu/NewGame/Loading допустимы до загрузки персонажа; раса и уровень требуют
активного персонажа на сессионной границе.

Метки worldspace/location/ближайшего маркера описательные и могут быть пустыми.
Они не подменяют `LocationId` и не используются для расстояний.
Время процесса игры является клиентским наблюдением; оно не определяет
серверное время подключения. В полном снимке эти сведения передаются вместе
с игровым состоянием, а изменение только позиции позволяет отправить
`PlayerMoved` без повторной отправки показаний и метаданных.

## История чата

```fsharp
// ChannelId выводится из вида канала. Capacity приходит из конфигурации.
let chatResult = Chat.create ChatChannelKind.Global 100
// Внутри обработчика владельца:
// Chat.join player.Data.PlayerId chat |> ignore
// Chat.append message chat                  : Result<unit, DomainError>
// Chat.historyAfter ValueNone 20 chat       : Result<ChatHistoryPage, DomainError>
// Chat.historyAfter page.NextCursor 20 chat : следующая страница
```

Добавление сообщения проверяет канал, членство автора по `PlayerId` и строгое
возрастание ID. Проверки выполняются до изменения состояния. Сервер назначает
ID и `SentAt`; фабрика сообщения приводит время к UTC, сохраняя момент времени.

`Core.toUnixMilliseconds` и `fromUnixMilliseconds` — тонкие оболочки .NET для
доверенных значений времени. Обратное преобразование требует диапазона
`DateTimeOffset`; при будущем декодировании произвольного int64 эту границу
должен обработать codec. Время сообщения сейчас задаётся сервером.

История ограничена количеством сообщений. `HasMore` означает наличие следующей
страницы. `HasGap` означает, что после переданного курсора были вытеснены
сообщения этого канала. Пропуски ID, занятые другими каналами, не создают
ложный gap. При `ValueNone` возвращается начало доступной истории без gap.
`clearHistory` не разрешает повторно использовать ранее принятые ID. `Chat.remove` — удаление
модератором одного хранимого сообщения: его ID больше не принимается, gap для него не сообщается.

Курсор относится к текущему жизненному циклу истории. Перезапуск сервера должен
либо продолжить выдачу ID, либо объявить клиенту сброс истории через контракт
сессии; `Chat` не хранит счётчик на диске. Будущий курсор возвращает пустую страницу.

### Объявления

`ChatChannelKind` — вид канала: `Global` (чат игроков) и `System` (объявления); партия,
гильдия и личные сообщения — будущие виды. У серверных видов по одному каналу, поэтому
`ChatChannelKind.channelId` выводит ChannelId из вида (1 и 2), `tryOfChannelId` — обратно.
`Chat.create kind capacity` создаёт канал вида; `Chat.append` требует, чтобы объявления
были ровно в системном канале (`carriesAnnouncements`), иначе `ChannelMismatch`.

`ChatMessage.Announcement` (`voption`) отмечает сообщение системного канала:
`Announcement { Source; Kind; Signature }`. `AnnouncementSource` — `Server` /
`TrustedClient` / `ThirdParty`; запрос клиента несёт отдельный `ClientAnnouncementSource`
без значения сервера, и `Announcement.fromClient` переводит его в источник.
`AnnouncementKind` — `Announcement` / `Event` / `Admin` / `Periodic`;
`Announcement.clientMayRequest` допускает клиентам только первые два.
`AnnouncementSignature.create` хранит подпись мода как есть: одна строка без
управляющих символов, не пустая, длина — в скалярах Unicode.

`ChatMessage.Author` — `PublicIdentity voption`: его нет только у серверного объявления
(`ChatMessage.serverAnnouncement`), которое `Chat.append` принимает без членства.
Объявления клиентов требуют членства автора, как обычные сообщения. Модель доверия и
поведение — [DomainSpecRu.MD §4.8](../../docs/DomainSpecRu.MD).

`ChatMessage.Author` — снимок публичной личности при отправке. Клиент может отображать
актуальный DisplayName из каталога профилей, сохраняя снимок как fallback.
Открытие карточки автора всегда производится по `PlayerId`.

## Метки на земле

Модель — [DomainSpecRu.MD §4.9](../../docs/DomainSpecRu.MD). Примитивы в `Primitives.fs`:
`GroundMarkId` (ненулевой uint64), `GroundNoteText.create` (правила текста чата),
`DeathMarkText.create` (одна строка без управляющих, пустая допустима). В `GroundMarks.fs`:
`GroundMarkBody = Note | Death` (вид выводится из тела), `GroundMarkPlacement`
(`isNear` — мягкая проверка положения по последней известной позиции, `isVisibleFrom` —
то же пространство и радиус с включённой границей), `GroundMarkRules.create` (квоты ≥ 1,
сроки в днях, 0 — бессрочно, конечные радиусы), `GameDate.create` (игровая дата у автора:
только диапазоны календаря, без високосных; `InvalidGameDate` с именем поля; не влияет на порядок
и срок жизни), `GroundMark` (`create`, `withFlagged`, `withGameDate`, `isExpired`, `expiresAt`) и
`GroundMarkStorage` — владелец всех меток: `add` вытесняет самую старую метку того же автора и
вида при достижении квоты и возвращает её (`DuplicateGroundMark` при повторе id), `remove`,
`expired`, `evictionCandidate`, `countOf`, `ofAuthor` (все метки автора для модератора),
`snapshot`. Id монотонны, поэтому самая старая — наименьший id.
Пространственный индекс и доставка принадлежат владельцу в Server.Core.

## Админка

`Admin.fs` ([docs/AdminPanelRu.md](../../docs/AdminPanelRu.md)) задаёт правила, хранилище и HTTP
живут вне домена:

- `AdminId` (положительный int64), `AdminAccount` (логин по правилам `Username`) — администратор
  не игрок.
- `PlayerRole = Player | Moderator` с `toInt`/`ofInt` (0/1, хранится в БД) и `key`/`ofKey`
  (формы и API); `PlayerRole.assign` — роль только зарегистрированному игроку (`PlayerNotFound`);
  `PlayerRole.outranks` — кого роль может наказать (модератор — только игроков).
- `AdminAction` (`SetRole`, `RenamePlayer`, `ResetPlayerPassword`, `RevokePlayerAccess`,
  `Announced`, `CreatedApiToken`, `RevokedApiToken`, `ResetAdminPassword`, `CreatedAdmin`,
  `SanctionedPlayer`, `LiftedSanction`, `KickedPlayer`; удалённый модератором в игре контент —
  `RemovedGroundMark`, `ClearedGroundMarks`, `DeletedChatMessage`) с
  неизменяемыми ключами аудита, `AuditTarget` (`player:42`, `admin:3`, `token:…`, `server`),
  `AuditRecord.create` (подробности до 512 символов, без секретов), `AuditActor`
  (администратор панели или модератор-игрок), `AuditEntry` (без исполнителя, если профиля модератора уже нет).
- `Sanctions.fs`: `SanctionKind` (`Mute`/`Ban`), `SanctionScope` (сейчас `Server`), `SanctionTerm`
  (от минуты до десяти лет или `UntilLifted`), `SanctionReason` (обязательна, одна строка до 200
  символов), `SanctionIssuer` (администратор или модератор), `Sanction.issue`/`expiry`/`activeAt`/
  `find`; `SanctionError` (`PlayerNotFound`, `NotAllowed`, `NotActive`).
- `AdminCodes` — чистое состояние одноразовых кодов: по одному на назначение (`Setup` или
  `ResetPassword adminId`), выпуск заменяет предыдущий и выбрасывает истёкшие, `redeem` тратит код
  первой попыткой и отличает `CodeExpired`. Хранятся только хеши; I/O и время передаёт владелец.
- `PanelSession` — срок и отзыв новой сменой пароля (`revokedBy`).
- `ApiTokenLabel` (1–64 символа, одна строка), `AdminAnnouncement` (текст по лимиту чата и
  ручные виды `admin`/`announcement`/`event`; `Periodic` — только расписание).
- `AdminPlayerView.create` — единственная сборка настоящей личности скрытого игрока для показа:
  хранимые username/display name, имя персонажа (и когда оно скрыто словарём), вариант скрытия и
  псевдоним, роль, место, фаза и время открытия сессии. Её вызывает только `PlayerSession`
  по запросу панели; в игровой протокол она не попадает (см. «Скрытое имя», абзац «Админка.» в
  [ModerationAndNamesRu.md](../../docs/ModerationAndNamesRu.md)).

`PseudonymBook.rename` сохраняет псевдоним и вариант скрытия переименованного игрока и меняет
только учитываемые настоящие имена.

## Сборка и проверки

Из корня репозитория:

```sh
dotnet build src/Dreamsleeve.Server.Domain/Dreamsleeve.Server.Domain.fsproj -c Release
dotnet run --project tests/Dreamsleeve.Server.Tests -c Release -- --filter-test-list Dreamsleeve.Server.Domain
```

Тестовый проект использует указанные в техническом справочнике Expecto и Faqt.
Проверяются нормализация и внешние ключи, конечность и точность вычислений,
снимки, смена персонажа, членство и ошибки чата, вытеснение и продолжение истории.

Общий запуск всех тестов: `python Scripts/run_tests.py`.
[Организация тестов](../../tests/README.md).

Движение после SetLocation принимает `Player.tryApplyMovement`: только текущий
ContextRevision и возрастающий Sequence. Устаревшие samples ничего не изменяют.
Новый SetLocation сбрасывает sequence; BeginCharacter/LeaveGame очищают активный
контекст, сохраняя его high-water mark на всё соединение. Downstream ViewRevision
принадлежит проекции Presence, а не самому Player.
