# Измерения серверных владельцев состояния

`Scripts/benchmark_server.ps1` собирает baseline `f4eef57` из отдельного архива в `build/benchmark-baseline`, затем текущий код. Основной checkout не переключается. Требуются .NET 10, Git и зависимости проектов.

```powershell
./Scripts/benchmark_server.ps1 -Requests 32768 -Repetitions 3
```

При другом расположении NuGet cache можно передать `-PackagesPath C:/Users/newri/.nuget/packages`. Результаты и сведения об окружении записываются в `build/benchmarks/comparison.json`; каталог меняется через `-OutputDirectory`.

## Общий сценарий до и после разделения

Граница измерения: **допуск декодированной команды → обработаны сформированные protobuf-пакеты всех получателей**. Сеть, разбор входного ClientPacket и поиск адреса сессии исключены. Тестовый получатель разбирает каждый исходящий ServerPacket и сопоставляет request_id; эта стоимость входит в оба варианта и может существенно влиять при большом fanout.

Сессии открываются заранее, затем выполняются 1024 прогревочных запроса. Текущий вариант использует protocol v3 и отдельный тестовый SessionAuthenticator с фиксированными ticket→PlayerData; HTTP, пароль и SQLite в этот прикладной microbenchmark не входят. Production runtime не содержит обхода авторизации. Baseline компилируется со своим старым protocol v1. Исторические таблицы результатов сохраняют версии исходников на момент замера и не обновляются автоматически при изменении текущего протокола. Один канал, N=1/16/32 отправителей, по одному незавершённому запросу на отправителя, одинаковый текст и история на 64 сообщения. Число запросов одинаково для каждого N; работа рассылки растёт с N. Автор получает одну публикацию, её request_id одновременно подтверждает запрос.

Baseline вызывает SessionRegistry.SendChat; его выходной агент сериализует ответы. Новый вариант один раз получает адреса сессий и вызывает PlayerSession.SendChat; штатный runtime сериализует ответы и продолжает опрашивать пустой тестовый транспорт. В baseline нет реализованного runtime, поэтому это сравнение определённого прикладного пути, а не двух сетевых серверов. Стоимость нового исходящего runtime и его пустого poll остаётся внутри границы.

Окончание прохода ждёт всех публикаций, а не только ответов авторам. P50Ms/P95Ms/P99Ms измеряются до коррелированной публикации автору. AdmissionP50Ms/AdmissionP95Ms/AdmissionP99Ms заканчиваются после awaited PostAsync: это наблюдаемый вызывающим кодом допуск в очередь, включая возможную задержку возобновления вызывающего кода; это не время выполнения обработчика. Процентили считаются отдельно для каждого прохода.

## Дополнительные сценарии нового кода

- `independent-rooms-1` и `independent-rooms-4`: четыре отправителя подписаны на каждую комнату. Запросы равномерно распределяются между одним или четырьмя ChatRoomAgent; общее число операций и публикаций совпадает. Адрес комнаты известен заранее. Тестовые агенты получателей сериализуют и разбирают выходные пакеты; PlayerSession и runtime отсутствуют. Эти два варианта можно сравнивать между собой, но не с основным сценарием и не использовать как доказательство параллельности сетевого выхода runtime.
- `player-update-read`: N=1/16/32 независимых PlayerSession. Операция начинает персонажа с тем же именем, ждёт коррелированного `PlayerUpdateAccepted`, затем читает снимок. Это тот же прикладной поток, который публикует состояние в Presence; runtime сериализует ACK и периодические обновления через тестовый транспорт. UDP и входного декодирования нет. Для каждого игрока создан отдельный тестовый агент с mailbox=1, его переход входит в измерение. Admission percentiles равны null. `PublishedPackets=0` означает отсутствие публикаций чата, а не отсутствие всех пакетов. Исторический результат этого сценария до telemetry имел другую границу и напрямую с текущим не сравнивается.

Каждый сценарий прогревается отдельно. В процессах измерения задан DOTNET_TieredCompilation=0, чтобы поздние сценарии не получали преимущество от перехода общих методов на другой уровень JIT. Значение переменной окружения восстанавливается после запуска. Скрипт выполняет baseline, затем новый вариант; это локальный диагностический benchmark, без рандомизации порядка, доверительных интервалов и изоляции ОС от сторонней нагрузки.

## Память, очереди и завершение

Записываются общие allocations/GC, private bytes процесса до/после, наблюдавшийся максимум ThreadPool queue и суммы очередей доступных агентов с шагом 10 мс, доставка PlayerLeft оставшимся игрокам и завершение всей сборки. Private bytes не являются пиком памяти или объёмом утечки. Доставка PlayerLeft измерена один раз на сценарий с точностью ожидания около 1 мс; это не распределение задержек транспорта. DisconnectFanoutMs=-1 означает отсутствие измерения: N=1 либо сценарий отдельных комнат. ShutdownMs охватывает завершение созданных агентов; сетевой drain здесь не измеряется.

Очереди имеют конечные увеличенные ёмкости, чтобы сравнивать принятую нагрузку. Это не тест производственных значений по умолчанию:

| Вариант | Настроенные границы |
| --- | --- |
| Baseline | registry mailbox 1024, player mailbox 1024, pending/player 16, pending channel 2×N+8, pending chat 256, pending output 65536; выходной mailbox 65536; chat mailbox/replies 256 |
| Новый общий путь | runtime mailbox 65536 и control reserve 3×N+4; player mailbox/output/pending updates 1024, pending chat 16, control reserve 32; chat mailbox 256/control 64, pending controls 128; presence mailbox 128/control 64, pending controls 128 |
| Отдельные комнаты | mailbox каждой комнаты 1024/control 64, pending controls 128, mailbox каждого получателя 1024 |
| Update/Read | границы общего нового пути плюс один тестовый mailbox=1 на игрока |

Это настроенные ёмкости. Поле PeakObservedQueueLength отдельно содержит наблюдавшийся максимум суммы Agent.QueueLength только для перечисленных в ObservedQueues владельцев: baseline — registry и выходной агент, новый общий путь — runtime и тестовые агенты чтения, отдельные комнаты — комнаты и получатели. Глубина не включает исполняемый обработчик и отправителей, ожидающих допуска. Выборка раз в 10 мс может пропустить краткий пик. Скрытые player/chat/presence владельцы runtime не раскрываются ради benchmark, поэтому поле не показывает весь backlog сервера; разные наборы наблюдаемых очередей нельзя напрямую сравнивать как одинаковый ресурс. ThreadPool queue — отдельный показатель, не длина mailbox. Время ожидания внутри каждой очереди здесь не профилируется.

Поведение медленного получателя проверяется детерминированными тестами ChatRoomAgentTests и PresenceAgentTests: получатель удерживается gate, единственный слот mailbox заполнен, здоровые участники продолжают работу до освобождения gate. Источник удаляет медленную подписку и сообщает SlowConsumer. У этих тестов source mailbox=4, control reserve=2, pending controls=4; у чата history=2. Переполнение пути управляющих ответов проверяется отдельно с pending controls=1 и заполненным host mailbox=1. Это проверка границ и изоляции, без утверждений о численной задержке или throughput под перегрузкой.

Старые API находятся только под `#if BASELINE` и компилируются с исходниками архивного коммита. Они не нужны текущему серверу и не возвращаются в Core ради benchmark.
